# S1.5.1 — Protocol zod schemas + server-side inbound validation

## Goal

Give `@skervik/protocol` **runtime** validation: zod schemas for the WS envelope
`{ v: 1, type, payload }` and its variants (`intent`, `event.batch`, `state.snapshot`,
`intent.rejected`, `intent.error`), plus a schema for the inbound `PlayerIntent`
payload. Wire the **server** to zod-parse inbound `intent` messages BEFORE core
`validate` (replacing the ad-hoc structural guard S1.4.2 added). This turns the
type-only envelope (S1.4.1) into an enforced contract at the trust boundary.

**Scope fence:** server + protocol only. Do NOT wire the CLIENT (it doesn't consume WS
messages until E1.6 — the client imports these schemas THEN). Do NOT touch
`packages/core`. Do NOT build the handshake/versioning (`auth.connect` / `room.state`)
— that's **S1.5.2**. Builds on `main` HEAD (E1.4 complete).

## Key decision — pin schemas to core's types (avoid a drifting second representation)

Core (`@skervik/core`) owns the canonical `PlayerIntent` / `GameEvent` TS types. The
zod schemas here MUST NOT become a silently-diverging duplicate (the same trap that
retired `EventLogLine` in ADR-0009 Fork 2). Enforce single-source-of-truth:

- Type the intent schema as **`z.ZodType<PlayerIntent>`** (and event as
  `z.ZodType<GameEvent>`), or add an explicit `satisfies`/assignability check, so a
  future core change to `PlayerIntent`/`GameEvent` **fails the protocol build** until
  the schema is updated — compile-time drift detection.
- If typing the FULL discriminated union as `z.ZodType<T>` fights zod's inference too
  hard, fall back to per-variant schemas combined with `z.discriminatedUnion('type'|
  'kind', …)` PLUS a compile-time exhaustiveness guard (a `never`-assignment over the
  variant discriminants, mirroring core's `types.test.ts` pattern) so a new variant
  breaks the build. Either way, adding a core intent/event variant must not silently
  bypass the protocol. **If neither approach is clean, STOP and report** — do not ship
  an unpinned duplicate.
- **Core `validate` stays the authoritative semantic validator.** zod checks WIRE SHAPE
  (envelope well-formed, known `type`, payload structurally valid) — it does NOT
  re-implement game rules. Depth: validate the discriminant + each variant's required
  fields/types; leave semantic legality (turn, affordability, adjacency…) to core.

## Spec

- **Envelope:** `v: z.literal(1)`; `type` a known string; `payload` validated per type.
  Unknown `type` / wrong `v` / missing payload → parse failure.
- **Inbound (`ClientMessageSchema`):** what the server accepts = the `intent` envelope
  (M1 has one inbound message type; author it extensibly). Server: `safeParse` the raw
  message; on `!success` reply privately with `MALFORMED_INTENT` (no throw, no
  broadcast, no state change); on success pass the typed intent into the existing
  pipeline (core `validate` then does semantic checks).
- **Outbound (`ServerMessageSchema`):** `event.batch` / `state.snapshot` /
  `intent.rejected` / `intent.error` schemas authored for E1.6's client to validate
  inbound — export them; no server behavior change required beyond ensuring the messages
  the server already sends satisfy the schemas (add a test that a real broadcast payload
  parses).
- **Drift guard:** the compile-time pin (above) — a test/type-level assertion that the
  schema covers every `PlayerIntent`/`GameEvent` variant.

- `packages/protocol/package.json`: added `zod` (resolved `4.4.3`, range `^4.1.13`) as protocol's
  first runtime dep; description drops "planned".
- `packages/protocol/src/messages.ts`: kept the S1.4.1 type-only envelope interfaces (added
  `ErrorMessage`/`intent.error` to `WsMessage`, which existed server-side but wasn't in the
  union). Added per-variant zod schemas for all 17 `PlayerIntent` types (with `intent.playDevCard`
  as a nested `z.discriminatedUnion('card', …)` of its 4 card kinds) and all 25 `GameEvent` types,
  combined into `PlayerIntentSchema` / `GameEventSchema` via `z.discriminatedUnion('type', …)`.
  Added `PublicGameStateSchema` and the 5 envelope schemas (`IntentEnvelopeSchema`,
  `EventBatchEnvelopeSchema`, `StateSnapshotEnvelopeSchema`, `RejectEnvelopeSchema`,
  `ErrorEnvelopeSchema`), plus `ClientMessageSchema` (inbound, currently just `intent`) and
  `ServerMessageSchema` (outbound union of the other 4).
- Drift pin mechanism chosen: **`z.discriminatedUnion` + compile-time exhaustiveness-style
  `Equals`/`AssertTrue` type assertions**, not `z.ZodType<PlayerIntent>` — the latter fights zod's
  discriminated-union inference too hard for a 17/25-variant union (tried it first; TS couldn't
  narrow the literal `type`/`card` discriminants against the interface shapes cleanly). Three pins
  live at the bottom of `messages.ts`: `_PLAYER_INTENT_VARIANT_PIN` (schema `type` literals ===
  core `PlayerIntent['type']`), `_PLAY_DEV_CARD_VARIANT_PIN` (nested `card` literals), and
  `_GAME_EVENT_VARIANT_PIN` (schema `type` literals === core `GameEvent['type']`). Mirrored again
  as real (non-`_`-prefixed, actually invoked) assertions inside `messages.test.ts`'s "drift guard"
  describe block, so both `tsc --noEmit` and `vitest run` exercise the pin.
  **Proved the mechanism catches a real divergence**: temporarily added a `DriftDemoIntent` variant
  to `packages/core/src/types.ts`'s `PlayerIntent` union (uncommitted, reverted immediately after),
  rebuilt core, and ran `pnpm --filter @skervik/protocol typecheck` — it failed exactly at the pin
  lines (`messages.ts:586: Type 'false' does not satisfy the constraint 'true'` and the mirrored
  assertion in `messages.test.ts:330`), plus core's own `validate.ts` exhaustiveness switch also
  broke (`Type 'DriftDemoIntent' is not assignable to type 'never'`) — confirming core changes are
  caught at both layers. `git checkout -- packages/core/src/types.ts` fully reverted; `git status`
  showed zero core diff before continuing.
- `packages/protocol/src/index.ts`: re-exports all new schemas + the `ErrorMessage` type.
- `packages/protocol/src/messages.test.ts` (new): round-trips every `PlayerIntent`/`GameEvent`
