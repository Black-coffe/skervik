# S1.4.4b — Durable event-log writer + pipeline persist-ordering fix

## Goal

Make the match event log **durable**: implement the real `FsEventSink` (fulfilling the
`GameEventSink` seam S1.4.2 shipped) that appends each validated `GameEvent` as one
ndjson line to `matches/{id}/events.ndjson`, wire it as the room's production sink, and
prove the round-trip (`parseGameEventLog` → `replay` reconstructs the exact state).
**AND fix S1.4.2 NIT-1** — the pipeline currently commits state before persistence is
confirmed, which a durable writer would turn into a real log-divergence + node-crash
bug. This story closes E1.4.

**Scope:** server-only. Uses core's `parseGameEventLog` (merged in S1.4.4a) for the
read path — do NOT edit `packages/core`. Does NOT build the `/matches/{id}/verify` REST
endpoint or Fastify (S1.7.3). Builds on S1.4.2 (pipeline + seam) and S1.4.3 (reveal) —
dispatch only AFTER both merge (all three touch `GameRoom.ts`).

## 🔴 Precondition: fix S1.4.2 NIT-1 (state-before-persist) — do this FIRST

Current pipeline (from S1.4.2, `GameRoom.ts`): `this.gameState = <reduce-fold>` runs,
THEN `await eventSink.append(events)`, THEN broadcast. With the in-memory sink (sync,
never rejects) this is inert — but `FsEventSink` (this story) can reject transiently
(disk/FS error), and today the reduce-fold + `await append` sit OUTSIDE the try/catch
(which wraps only `validate`) on a voided floating-promise handler. So a sink rejection
would: (a) leave `gameState` advanced past an event that never hit the log → replay
divergence; (b) escape uncaught → Node unhandled-rejection → **whole-node crash (all
rooms)**.

**Fix (reviewer's direction — implement exactly):**
1. Compute the next state into a LOCAL (`const nextState = events.reduce(reduce,
   this.gameState)`) — do NOT assign `this.gameState` yet.
2. `await this.eventSink.append(events)` — persist FIRST.
3. ONLY on success: `this.gameState = nextState`, refresh the schema projection,
   broadcast `event.batch`, and (S1.4.3) fire the reveal on `game.ended`.
4. Wrap the reduce-fold + append (the whole async body) in try/catch → on error, send a
   PRIVATE error reply to the sender and DO NOT advance state / broadcast; nothing may
   escape the voided handler (no unhandled rejection). Log the failure with `seedHash`
   only, never the seed.
- Invariant after the fix: **no client ever sees (via broadcast) or acts upon an event
  that was not durably recorded first**, and a sink failure degrades gracefully (reject
  to sender, state untouched) instead of crashing the node.

### Follow-up commit — lead-review TOCTOU fix (same branch)

Lead-review found the NIT-1 reorder opened a concurrency race: Colyseus dispatches
`onMessage` via a synchronous EventEmitter and does NOT serialize an async handler, so
with a genuinely async sink (`FsEventSink`'s `await appendFile`) a SECOND intent arriving
while the first is still awaiting `append` would `validate` against the still-uncommitted
`this.gameState` — a TOCTOU double-spend window, invisible only because the in-memory sink
never suspends.

- `packages/server/src/room/GameRoom.ts`: added a per-room `#queue: Promise<void>` field +
  `#enqueueIntent` — every `intent` message is now chained onto this queue
  (`this.#queue = this.#queue.then(() => this.#handleIntent(...)).catch(...)`) instead of
  dispatched as an independent floating promise. Guarantees intent N's full pipeline
  (validate → persist → commit → broadcast → reveal) settles before intent N+1 starts.
  `#handleIntent` itself already catches every error internally, so the `.catch` on the
  queue link is a pure safety net (prevents a hypothetical regression from wedging the
  queue or escaping as an unhandled rejection) — not load-bearing today. One queue per room
  instance (an own field), so rooms never serialize against each other.
- **Concurrency test** (`GameRoom.test.ts`, "concurrency: two intents in the same tick are
  SERIALIZED..."): player `a` holds exactly one bank-trade's worth of timber (4), a sink
  whose `append` suspends 30ms (simulating real disk I/O), then the SAME `intent.bankTrade`
  is sent twice back-to-back with no `await` between. **Manually verified the test's
  discriminating power**: temporarily reverted `onMessage` to the old
  `void this.#handleIntent(...)` (bypassing the queue), reran just this test — it FAILED
  (`batches` had length 2, i.e. both trades broadcast, proving the double-spend); restored
  the queue, reran — 31/31 pass, `diff` confirmed the file was restored byte-identical to
  the fixed version before committing. With the fix: exactly one `bank.trade` broadcasts,
  the second intent gets `CANNOT_AFFORD` (validated against the committed, 0-timber state),
  and the player ends at exactly 0 timber (not negative).
- **Async throwing-sink fix**: the NIT-1 throwing-sink test's `append` was changed from a
  synchronous `throw` to `async append() { throw ... }`, so `await this.eventSink.append(...)`
  genuinely suspends before rejecting — the synchronous version never exercised the real
  async-rejection path (a real `FsEventSink` failure is always an async rejection).
- **matchId path-safety** (`eventSink.ts` `FsEventSink` constructor): rejects a `matchId`
  containing `/`, `\`, `..`, or the empty string before it becomes a path segment — a
  defensive assert on the fairness/anti-cheat boundary (matchId = Colyseus `roomId` today,
  never client-controlled, but asserted rather than trusted silently). Covered by 6 new
  `eventSink.test.ts` cases (5 rejections + 1 "normal roomId still works").
- **String-pin test** (`GameRoom.test.ts`, new `describe` block after the main suite): calls
  core's real exported `validate()` directly with (a) an unrecognized top-level
  `intent.type` and (b) an unrecognized `playDevCard` card kind (with the bogus card
  pre-"held" so it clears the CARD_NOT_HELD guard and reaches the switch), asserting the
  thrown messages match `/^unhandled intent type: /` and `/^unhandled playDevCard card
  kind: /` respectively — the exact prefixes `isUnknownIntentError` string-matches. A future
  core reword of either message now fails this test instead of silently flipping
  `MALFORMED_INTENT` → `INTERNAL_ERROR` for a legitimate (if malformed) intent.
- Fixed one typecheck error along the way: the string-pin test's crafted `devCards.held`
  object needed `as unknown as NonNullable<GameState['devCards']>` (the real type is a
  strict `DevCardKind` union, and the test's bogus key isn't one).
