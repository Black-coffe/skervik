# S1.7.1 — Guest auth + server boot (the real `listen()`)

## Goal

Make the server **actually run**. Today `createGameServer()` returns a bare Colyseus `Server`
with no transport and no `listen()` (a factory used only by boot-free unit tests). This story
adds the real HTTP+WebSocket boot on one port via **Fastify + a Colyseus WS transport**, a
minimal **guest identity** endpoint (`POST /auth/guest`), a `GET /health` probe, and wires the
quick-match join so 3–4 real `colyseus.js` clients can connect over a socket and land in one
`GameRoom`. This is the spine E1.7 stands on: **S1.7.2's scripted 3–4-client match needs a
process that listens**, and **S1.7.3's `/verify` endpoint needs a Fastify REST surface** — both
begin here.

**Right-sized on purpose:** room-create/**join-by-code** (invite-a-friend UX) is split out to
**S1.7.1b** — it is NOT needed for the M1 gate (quick-match `joinOrCreate` already seats 4
clients in one room) and layering it on the now-existing Fastify boot is a small fast-follow.
This story is the boot + auth + quick-match; do not build room codes here.

## 🔴 STEP 0 — apply ADR-0011: align the client to colyseus 0.17 FIRST (RESOLVED fork)

The original Step-0 spike **fired the STOP-gate**: `colyseus.js@0.16` client CANNOT join a
`colyseus@0.17` server — the seat-reservation response shape changed between majors (nested
`{room:{…}}` in 0.16 → flat in 0.17), so `Client.consumeSeatReservation` throws
`TypeError: …reading 'name'` **before any WebSocket connect** (schema sync never reached). See
this story's `## Findings` for the reproduced evidence. **The Queen resolved it — ADR-0011.**

**Do this FIRST (it unblocks everything else):**
1. **Migrate the client SDK** (`packages/client`): drop `colyseus.js@^0.16`, add
   `@colyseus/sdk@^0.17.x` (confirm the exact patch against the installed server `colyseus@0.17.x`;
   the package already resolves in the tree via `@colyseus/testing`). Both sides now on
   `@colyseus/schema@4`.
2. **Retarget the S1.6.5 net layer** to the 0.17 SDK: `net/wsClient.ts` (imports `Client`,
   `joinOrCreate`, `room.onMessage`/`send`/`onLeave`/`onStateChange`/`sessionId`) and
   `net/connection.ts` (parses `ServerError`/close codes for the version-reject path). Keep the
   framework-free / structural-`RoomLike` design intact — only the `connect()` wrapper + the
   `Client` import + the `ServerError`/close-code extraction should change.
3. **Re-green S1.6.5's net/store tests against the real 0.17 SDK API** — confirm `joinOrCreate`,
   `onMessage`, `onStateChange`, `room.send`, `leave`/`onLeave`, `sessionId`, and the
   `ServerError`/close-code shapes `connection.ts` depends on hold on the 0.17 `Client`. If the API
   drifted, adapt `connection.ts`/`wsClient.ts` (NOT the Trade-UI components, NOT the store's
   public actions) and NOTE the deltas.
4. **Commit this migration as its own step** on the branch (e.g. `feat(client): migrate to
   @colyseus/sdk 0.17 (ADR-0011)`) BEFORE building the boot — a clean, separately-reviewable point.

Then the real-socket join proof (0.17 client ↔ 0.17 booted server) below becomes the end-to-end
proof that the alignment works — it retires the S1.6.5 v3/v4 flag with both sides on schema v4.
If the 0.17 client STILL cannot join the 0.17 server after the migration → STOP and report (that
would be a deeper problem than a major mismatch).

## The boot contract (build to THIS)

- **One port, two protocols — use `attachToServer`, NOT the bare shared-server shape (ADR-0011).**
  The spike proved `new Server({ transport: new WebSocketTransport({ server: fastify.server }) })` +
  `serverless()` + `fastify.listen()` **double-binds HTTP**: colyseus core's `bindRouterToTransport`
  does `server.prependListener('request', …)`, so both Fastify and the colyseus router answer every
  request (incl. `/health`) → `ERR_HTTP_HEADERS_SENT`. **Correct shape:** Fastify owns the HTTP
  server; bind Colyseus WS via **`gameServer.attachToServer(fastify.server)`** (WS upgrades ONLY, no
  `request` listener) **and mount the colyseus `/matchmake/*` HTTP handler INTO Fastify** (proxy to
  the colyseus router, or core's node matchmaking middleware) so the client's
  `POST /matchmake/joinOrCreate/<room>` is served. Confirm the exact 0.17 API
  (`Server`/`WebSocketTransport`/`attachToServer`/matchmaking-middleware export names) against the
  installed lib; if an API name differs, adapt and NOTE it — don't force a shape that doesn't exist.
- **`createGameServer` stays a factory; boot injects the transport.** Extend `createGameServer` with
  an OPTIONAL transport/server injection (backward-compatible: no-arg still works for the existing
  boot-free tests) OR add a sibling `createHttpServer(opts)` that composes Fastify + the Colyseus
  `Server` + routes and returns a `{ fastify, gameServer, listen(port), close() }` handle. Either
  way the existing `createGameServer()` signature keeps working and **`GameRoom` logic is byte-
  untouched** (only bootstrap + join-options shape change — scout's hard constraint).
- **`GET /health`** → `200 { status: 'ok' }` (LB/readiness; no auth).
- **`POST /auth/guest`** → `200 { guestId, displayName }`. Issues an **anonymous** guest identity:
  `guestId` = an opaque random id (crypto), `displayName` = the client-supplied name if valid, else
  a generated one (e.g. `Guest-XXXX`). **In-memory store for M1** (a `Map`), no DB, no password, no
  real token. This is NOT a security boundary in M1 and MUST say so in a code comment — the
  authoritative game identity is still the unspoofable Colyseus `sessionId`. Structure it so a
  signed token / DB-backed account can slot in later (return shape stable), but do not build that now.
- **Identity stays `sessionId` (do NOT rewire).** `guestId`/`displayName` are **display/lobby**
  metadata, NOT the authoritative `PlayerId`. The client MAY pass `{ guestId, displayName }` in the
  join options; `onAuth` accepts them (optional fields on `ConnectOptionsSchema`) but the seat's
  `playerId` remains `client.sessionId` exactly as today. The anti-spoof invariant (S1.4.2 / S1.5.2:
  `validate` binds `intent.playerId` to the seat) is unchanged. If wiring `displayName` onto a seat
  for HUD display requires touching `SeatSchema`/`GameRoom`, DEFER that to S1.7.1b/S1.6.6 and just
  carry the guest fields in room metadata or drop them for now — do not touch authoritative room logic.
- **Quick-match join is already correct.** `joinOrCreate(GAME_ROOM_NAME, { protocolVersion, guestId?,
  displayName? })` seats up to `maxSeats` (4) clients in one room — that IS the S1.7.2 4-player path.
  No room codes, no `filterBy` here.
- **Config:** `PORT` from env (default `2567` to match the S1.6.5 client `ws://localhost:2567`
  default), `HOST` default `0.0.0.0`. A `start`/`serve` npm script that boots for real. CORS: allow
  the dev client origin for `POST /auth/guest` (Fastify CORS, dev-permissive, documented — tighten
  later).

## Findings

### STOP-GATE HIT — Step 0 version-compat spike FAILED (2026-07-06)

**Result: the `colyseus.js@0.16` client CANNOT join a `colyseus@0.17` server.**
The break is at HTTP seat reservation — *more fundamental* than the schema
v3↔v4 risk the story anticipated (the socket/schema never even opens).

**Exact failure (reproduced twice, isolated from the Fastify boot):**
- 0.17 server matchmaking `POST /matchmake/joinOrCreate/skervik_game` → `200`
  with a **FLAT** body:
  `{"name":"skervik_game","sessionId":"…","roomId":"…","processId":"…"}`
- 0.16 client `Client.consumeSeatReservation` (colyseus.js@0.16.22
  `build/esm/Client.mjs:106`) reads a **NESTED** shape:
  `response.room.name`, `response.room.roomId`, and
  `buildEndpoint(response.room, …)` (needs `response.room.processId` /
  `.publicAddress`). Since the 0.17 body has no `response.room`, it throws
  `TypeError: Cannot read properties of undefined (reading 'name')` **before**
  any WebSocket connect. Schema sync (the flagged v3/v4 risk) is therefore
  never reached — this is a matchmaking-protocol break, not a schema break.

The seat-reservation response shape changed between colyseus majors
(nested `{ room: {...} }` in 0.16 → flat in 0.17). No amount of server-side
Schema/message-bus work fixes it; the two majors are wire-incompatible at
matchmaking. This is the ADR-level version-alignment fork the story reserves
for the Queen + `lead-architect`.

### Secondary finding — Fastify + colyseus one-port boot shape

The story's preferred shape
`new Server({ transport: new WebSocketTransport({ server: fastify.server }) })`
+ `gameServer.serverless()` + `fastify.listen()` **half-works but collides on
HTTP**: `bindRouterToTransport` (core 0.17 `router/index.cjs`) does
`server.prependListener('request', … toNodeHandler(router.handler))`, which runs
on EVERY request and writes a response even for non-matchmake routes — so Fastify
*and* the colyseus router both answer `GET /health`, yielding
`ERR_HTTP_HEADERS_SENT`. (In the spike `/health` still returned ok because Fastify
won the race, but the double-write error fired.) The clean coexistence patterns
core actually supports:
- **express path**: `new Server({ transport, express: (app) => {…} })` removes the
  express listener and builds a combined `next` that falls through to express for
  unmatched routes (matchmaking + custom routes coexist) — but that's Express, not
  Fastify.
- **`attachToServer(fastify.server)`** binds ONLY WS upgrades (no request
  listener), leaving Fastify to own all HTTP — but then the `/matchmake/*` HTTP
  routes the client POSTs to must be mounted INTO Fastify (proxy to the colyseus
  router, or use `createNodeMatchmakingMiddleware` from core).

So "one HTTP server, WS transport attached to it" needs the matchmaking HTTP
route explicitly bridged into Fastify (via `attachToServer` for WS +
mounting the matchmaking handler), NOT the bare `serverless()` + shared-server
shape, which double-binds `request`. Worth capturing in the same ADR/next
dispatch. Deps added on the branch this run (uncommitted, reverted at STOP):
`fastify@^5.10.0`, `@fastify/cors@^11.2.0`, `@colyseus/ws-transport@^0.17.13`.
