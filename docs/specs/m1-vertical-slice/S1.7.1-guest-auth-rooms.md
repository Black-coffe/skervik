# S1.7.1 — Guest auth + server boot (the real `listen()`)

## Goal

Make the server **actually run**. Today `createGameServer()` returns a bare Colyseus `Server`
with no transport and no `listen()` (a factory used only by boot-free unit tests). This story
adds the real HTTP+WebSocket boot on one port via **Fastify + a Colyseus WS transport**, a
minimal **guest identity** endpoint (`POST /auth/guest`), a `GET /health` probe, and wires the
quick-match join so 3–4 real `colyseus.js` clients can connect over a socket and land in one
`GameRoom`. This is the spine E1.7 stands on: **S1.7.2's scripted 3–4-client match needs a
process that listens**, and **S1.7.3's `/verify` endpoint needs a Fastify REST surface** — both
begin here.

**Right-sized on purpose:** room-create/**join-by-code** (invite-a-friend UX) is split out to
**S1.7.1b** — it is NOT needed for the M1 gate (quick-match `joinOrCreate` already seats 4
clients in one room) and layering it on the now-existing Fastify boot is a small fast-follow.
This story is the boot + auth + quick-match; do not build room codes here.

## 🔴 STEP 0 — colyseus version-compat spike (do this FIRST, it is a STOP-GATE)

The server runs `colyseus@0.17.x` + `@colyseus/schema@4.0.x`; the S1.6.5 client pinned
`colyseus.js@^0.16.22` (there is no 0.17.x client line) bundling `@colyseus/schema@^3`. S1.6.5
flagged that **gameplay rides the message bus (stable across these) but the Colyseus *Schema*
state-sync (the public seat/phase projection) is UNVERIFIED across schema v3-client ↔ v4-server**.
This story is the first real socket, so prove it before building anything else:

1. Stand up the real boot (Fastify + WS transport + `listen()` on an ephemeral port).
2. Connect a real `colyseus.js` `Client`, `joinOrCreate(GAME_ROOM_NAME, { protocolVersion })`.
3. Assert the client receives BOTH: the `state.snapshot` message (message bus — should work) AND
   a coherent **Schema** state (`room.state` / `onStateChange` — the v3/v4 risk). Do a one-intent
   round-trip and confirm the client sees the resulting `event.batch` + any schema delta.

**If the Schema sync is broken or throws across the version gap → STOP and report.** Do NOT hack a
workaround. That is an ADR-level fork (align to a single colyseus/schema major — e.g. pin server
to a 0.16 line that has a matching client, or find a 0.17-compatible client, or drop the Schema
projection to message-bus-only). The Queen will bring `lead-architect` + write an ADR before you
proceed. If the spike PASSES (both message bus and schema sync work), delete the throwaway spike,
keep a permanent real-socket smoke test (below), and build the rest. **Report the spike result
either way** — this retires the S1.6.5 flag.

## The boot contract (build to THIS)

- **One port, two protocols.** Fastify owns the HTTP server; the Colyseus WS transport attaches to
  Fastify's underlying `http.Server` (`fastify.server`) so REST and WS share `:PORT`. Preferred:
  `new Server({ transport: new WebSocketTransport({ server: fastify.server }) })` from
  `@colyseus/ws-transport` (confirm the exact transport package + version that matches the installed
  `colyseus@0.17.x`; if the API differs, adapt and NOTE it — don't force a shape that doesn't exist).
- **`createGameServer` stays a factory; boot injects the transport.** Extend `createGameServer` with
  an OPTIONAL transport/server injection (backward-compatible: no-arg still works for the existing
  boot-free tests) OR add a sibling `createHttpServer(opts)` that composes Fastify + the Colyseus
  `Server` + routes and returns a `{ fastify, gameServer, listen(port), close() }` handle. Either
  way the existing `createGameServer()` signature keeps working and **`GameRoom` logic is byte-
  untouched** (only bootstrap + join-options shape change — scout's hard constraint).
- **`GET /health`** → `200 { status: 'ok' }` (LB/readiness; no auth).
- **`POST /auth/guest`** → `200 { guestId, displayName }`. Issues an **anonymous** guest identity:
  `guestId` = an opaque random id (crypto), `displayName` = the client-supplied name if valid, else
  a generated one (e.g. `Guest-XXXX`). **In-memory store for M1** (a `Map`), no DB, no password, no
  real token. This is NOT a security boundary in M1 and MUST say so in a code comment — the
  authoritative game identity is still the unspoofable Colyseus `sessionId`. Structure it so a
  signed token / DB-backed account can slot in later (return shape stable), but do not build that now.
- **Identity stays `sessionId` (do NOT rewire).** `guestId`/`displayName` are **display/lobby**
  metadata, NOT the authoritative `PlayerId`. The client MAY pass `{ guestId, displayName }` in the
  join options; `onAuth` accepts them (optional fields on `ConnectOptionsSchema`) but the seat's
  `playerId` remains `client.sessionId` exactly as today. The anti-spoof invariant (S1.4.2 / S1.5.2:
  `validate` binds `intent.playerId` to the seat) is unchanged. If wiring `displayName` onto a seat
  for HUD display requires touching `SeatSchema`/`GameRoom`, DEFER that to S1.7.1b/S1.6.6 and just
  carry the guest fields in room metadata or drop them for now — do not touch authoritative room logic.
- **Quick-match join is already correct.** `joinOrCreate(GAME_ROOM_NAME, { protocolVersion, guestId?,
  displayName? })` seats up to `maxSeats` (4) clients in one room — that IS the S1.7.2 4-player path.
  No room codes, no `filterBy` here.
- **Config:** `PORT` from env (default `2567` to match the S1.6.5 client `ws://localhost:2567`
  default), `HOST` default `0.0.0.0`. A `start`/`serve` npm script that boots for real. CORS: allow
  the dev client origin for `POST /auth/guest` (Fastify CORS, dev-permissive, documented — tighten
  later).

## Scope — build THIS, defer the rest

**Build:**
- **Boot module** (`packages/server/src/boot.ts` or `httpServer.ts`, NEW): composes Fastify + Colyseus
  WS transport + routes; exposes `createHttpServer(opts)` returning a listenable handle and a real
  `startServer()` (reads `PORT`/`HOST`, calls `listen`). Framework wiring only — no game logic.
- **REST routes** (`packages/server/src/routes/`, NEW): `GET /health`, `POST /auth/guest`. Body
  validation via zod (reuse the protocol zod dependency style; a small `GuestAuthRequestSchema`).
  Responses are machine-shaped JSON (`{ guestId, displayName }` / `{ error: '<code>' }`), NOT
  translated strings — the client maps codes to localized UI with its existing i18n.
- **Guest store** (`packages/server/src/auth/guestStore.ts`, NEW): in-memory `Map<guestId, {displayName}>`,
  `issueGuest(displayName?)` → `{ guestId, displayName }`, name sanitization/length clamp. Pure +
  unit-tested. Seam-shaped for a future DB impl.
- **Join options** (`packages/protocol`): add OPTIONAL `guestId?: string`, `displayName?: string` to
  `ConnectOptionsSchema` (the S1.5.2 handshake schema). `protocolVersion` stays required. Drift-pins
  intact. `onAuth` continues to reject on version mismatch first; guest fields are optional + ignored
  by authoritative logic.
- **Real-socket smoke test** (kept from Step 0): boot on an ephemeral port, connect a real
  `colyseus.js` client, `POST /auth/guest` over HTTP, `joinOrCreate` with the guest fields + version,
  assert `state.snapshot` + schema sync + a one-intent `event.batch` round-trip + a version-mismatch
  join is rejected over the real socket. This is the first cross-process proof; S1.7.2 scales it to a
  full 3–4-client match.
- **Client bootstrap (light):** a `fetchGuest(apiBaseUrl)` net helper (`packages/client/src/net/`) that
  `POST`s `/auth/guest` and returns `{ guestId, displayName }`; call it in the client bootstrap before
  `connect()` and pass the fields into the join options. Keep the no-server fixture dev-view working
  (guest fetch failure → fall back to fixture, don't hard-require the server). `VITE_API_URL` env
  (default derived from / same origin as `VITE_WS_URL`'s host). Any NEW user-facing client string =
  typed `t()` ×ru/uk/en (build-gated). If no new visible string is needed, none is fine.

**DEFER — do NOT build here:**
- **Room create / join-by-code** — S1.7.1b (`POST /rooms` + `joinById`/room-code metadata on the now-
  existing Fastify boot). Not gate-critical.
- **The scripted 3–4-client full-match E2E + determinism/replay-equality assertion** — S1.7.2 (this
  story proves ONE client joins over a real socket; S1.7.2 drives a whole match to victory).
- **`GET /matches/{id}/verify` + seed reveal recompute** — S1.7.3 (needs the persisted log + revealed
  seed; the `MatchMetadataStore`/`FsEventSink` prod impls land around there).
- **Real accounts / passwords / signed tokens / DB / Postgres** — post-M1. M1 guest is in-memory,
  anonymous, explicitly not a security boundary.
- **Reconnect grace / bot-fill / matchmaking queues / Redis presence** — M2.
- **Server-enforced turn timers** — M2.
- **Rewiring PlayerId off `sessionId`** — out of scope forever for M1; identity stays the seat.

## Key decisions (surface any deviation)

1. **Fastify comes in now (ADR-0009 deferral resolved).** ADR-0009 deferred Fastify "until REST is
   needed"; E1.7 needs it (auth + verify). This is executing the plan, not a new fork — no fresh ADR
   required UNLESS Step 0's version spike fails (then an ADR for colyseus version alignment).
2. **One HTTP server, WS transport attached to it** — REST + WS on one port (`fastify.server`).
   Simplest deployable shape; no second process.
3. **Guest identity is display-only; authoritative identity stays the Colyseus `sessionId`** — keeps
   the anti-spoof invariant and the scout's "don't touch GameRoom" constraint. In-memory, anonymous,
   not a security boundary in M1 (commented as such).
4. **Room-by-code split to S1.7.1b** — quick-match `joinOrCreate` already satisfies the S1.7.2 gate;
   codes are UX, layered later.
5. **Version-compat is a STOP-GATE, not a workaround** — if 0.16-client ↔ 0.17-server schema sync
   breaks, that's escalated to an ADR, not patched in this story.
