# S1.6.4 — Trade UI: the offer builder (the product's heart)

## Goal

Build the **player↔player Trade UI** — the offer builder + incoming/outgoing/history
offer cards + the two-step "seal the deal" interaction — as DOM "Instruments" (DESIGN.md
§1) docked in the trade zone of the S1.6.3 game screen. This is **the product's heart**
(PRODUCT.md; CLAUDE.md "Trade UI is the heart, not a feature — fast, error-proof,
expressive"). DESIGN.md **§7 is the binding constitution** for this story; every one of its
six rules is an acceptance gate. Every string flows through the `t()` layer in RU/UA/EN.

The UI composes/edits **typed `PlayerIntent` objects** (from `@skervik/core`) and hands them
to a store **dispatch seam** — but the actual network send stays a **stub** until S1.6.5
wires WebSocket. The full *interaction* (compose → arm → seal, counter-in-place, decline,
cancel, pending-seal, anti-misclick) is real, tested, and demoable against the dev fixture.

## The scope seam (READ FIRST — this is the load-bearing decision)

S1.6.4 (Trade UI) is sequenced **before** S1.6.5 (WS client) on purpose, so the two don't
cyclically block. The seam that makes this clean:

- The Trade UI reads the authoritative offer from **`store.gameState.openTradeOffer`**
  (the real `TradeOffer` slot S1.3.2 put on `GameState`) and reads my hand from
  `store.gameState` — never invents trade state.
- Composing/responding produces a **typed `PlayerIntent`** (`intent.proposeTrade` /
  `acceptTrade` / `rejectTrade` / `counterTrade` / `cancelTrade`) handed to a new store
  action **`dispatchIntent(intent: PlayerIntent)`**.
- In S1.6.4 `dispatchIntent` is a **STUB**: it records the intent + flips local
  "pending-seal" UI state, and MAY (dev-only) apply it through the real core `reduce` to a
  local *preview* copy so the fixture demo advances — but it performs **NO network I/O** and
  is NOT the authority. Per DESIGN.md §7.6 ("optimistic UI may preview but never confirm; an
  offer is pending seal until the server event returns") the UI must render a visibly
  distinct **pending-seal** state that, with no server yet, simply stays pending (or a
  dev-only "simulate server ack" affordance settles it). **S1.6.5 replaces `dispatchIntent`'s
  body** with WS send + server-echo reconciliation; the component layer must not change then.
- **Trace (§7.4):** every dispatched trade action is pushed to a store-held ordered
  `tradeLog` list (structured entries: who → whom, give ⇄ get, kind, turn). Rendering it in
  the ship's-log panel is a LATER story (log content was deferred in S1.6.3) — S1.6.4 only
  accumulates the entries so nothing is verbal-only.

If any of this forces a non-client edit or a DESIGN.md deviation, **STOP and report** — do
not silently widen scope.

## Scope — build THIS, defer the rest

**Build (§7 + §11):**
- **OfferBuilder** (docked, fixed-geometry panel in the trade zone — NOT a modal, §7.1):
  give-column | receive-column, columns never swap sides; per-resource steppers (−/count/+)
  drawing from the §2.3 resource palette WITH icon+count (never hue-only). Selectable
  targets = all other players (M1: all-others; render the flotilla emblems+names of who the
  offer goes to). Only enabled when it's my turn and no offer is already open
  (`openTradeOffer` absent) — mirrors core's `TRADE_OFFER_ALREADY_OPEN` / current-player
  rule as a UI affordance.
- **Impossible-offer prevention (§7, anti-misclick):** the builder must make an illegal
  offer *unsendable* — can't offer resources I don't hold (steppers clamp to my hand), can't
  seal an empty give or empty get bundle, can't offer/receive negatives. Use a **pure,
  unit-tested client predicate** `canComposeOffer(hand, give, get)` (same discipline as
  `renown.ts`) — do **NOT** call core `validate` client-side (it needs the server-secret
  `seed` as its 4th param, which the client must never hold; the server stays the real
  authority per §7.6). The seal button is disabled with a localized reason until the offer
  is legal.
- **Two-step seal (§7.2):** compose → explicit **"Скрепить сделку"** confirm that shows the
  full deal **in words** (localized: "Вы отдаёте 2 руно, получаете 1 железо") + a **150ms
  disabled-then-armed** guard against double-click. Sealing calls `dispatchIntent(propose…)`
  and enters pending-seal.
- **OfferCard** with its §11 states **incoming / outgoing / history**:
  - **Incoming** (an `openTradeOffer` where I'm in `targets`): a **docked card in the trade
    zone, NEVER a screen-blocking modal** (§7.5) showing give⇄get in words + emblems.
    Actions: **Accept** (primary), **Decline** (quiet), **Counter**. Accept and decline are
    **≥16px apart**, decline is the quiet style, accept primary (§7.5 anti-misclick). Accept
    is disabled (with reason) if I can't afford the `get` (client predicate).
  - **Counter (§7.3):** edits the incoming offer **in-place, pre-filled** (roles swapped to
    my perspective), bounded to ONE counter (core enforces `depth`/`TRADE_COUNTER_LIMIT_
    REACHED`; the UI disables "Counter" on a card that is already a counter, `depth >= 1`).
  - **Outgoing** (my open proposal, pending seal / awaiting response): shows the deal + a
    **cancel** action (`cancelTrade`) and the visibly-distinct pending-seal state (§7.6 —
    e.g. a wax-seal pulse; the ONLY exception to "no pulsing" is timer-critical + this
    pending seal, keep it gentle, respect `prefers-reduced-motion`).
  - **History:** a compact past-deal row (settled/declined/cancelled) — the visual grammar
    the ship's-log will reuse; S1.6.4 renders these from the store `tradeLog` inside the
    trade zone (a short "recent deals" strip), NOT the full log panel.
- **Quick-reactions (§7.3):** predefined, **localized** responses (e.g. "Согласен",
  "Слишком дорого", "Давай подумаю") as buttons — NO free-text (design decision: bounded
  pressure, not chat). Dispatched as trace entries (M1: they annotate the tradeLog; wiring
  to opponents is S1.6.5).
- **Store extension:** add `dispatchIntent(intent)` + `tradeLog` + a `pendingSeal` marker to
  `hud/store.ts` (UI-state only; `gameState` still authoritative-from-core/fixture). Pure
  selectors: `selectOpenOffer`, `selectIsIncomingToMe`, `selectIsMyOutgoing`. Unit-test them.
- **i18n:** every user-facing string a typed `t()` key in `i18n/keys.ts`, authored in
  `ru`/`uk`/`en` (missing key = build fail). Includes the "in words" deal sentence
  (parameterized/pluralized via the i18n `formatNumber`/plural layer — RU/UA plural rules),
  seal/accept/decline/counter/cancel labels, quick-reactions, disabled-reason strings, empty
  state. Resource & flotilla names reuse existing `resource.*` / flotilla keys.
- **Dev demo harness (real, through `reduce`):** to exercise incoming/outgoing/counter
  states with no server, seed demo `openTradeOffer`s by applying real `proposeTrade`/
  `counterTrade` through core `reduce` on top of `devFixtureState` (same "fixtures are real,
  not invented" discipline as S1.6.2/S1.6.3). A minimal dev-only toggle to switch demo states
  is fine; it must NOT fake authoritative state beyond what `reduce` produces, and must be
  clearly dev-scoped.

**DEFER — do NOT build here:**
- **WebSocket / real intent send / server-echo reconciliation / real pending→sealed
  settlement** — S1.6.5. `dispatchIntent` stays a stub; no `socket`, no `fetch`.
- **Ship's-log panel CONTENT / full trade-history feed** — later log story. S1.6.4 only
  accumulates `tradeLog` entries + the small in-zone "recent deals" strip.
- **Bank/port trade UI (4:1/3:1/2:1)** — that's a separate affordance (core S1.3.3 exists);
  keep S1.6.4 to **player↔player** trade to stay focused on the heart. Note it as a follow-up.
- **Embargo (§7.3 "explicit, visible, reversible action")** — no core support yet; DEFER and
  note. Do not invent an embargo rule client-side.
- **§8 fairness/tide-lot dashboards, histograms** — unrelated stories.
- **Board-click build interactions / other intents** (S1.6.5). Only trade intents here.
- **Mobile ≤768px structural collapse** — build with the same components (so the later
  collapse reuses them); desktop ≥1280px zoning is the S1.6.4 target.
- **Colorblind-mode / theme toggle** — M4.

## Core data contract (verified 2026-07-05 — exact shapes)

Import from `@skervik/core`. Intents carry NO `playerId` (that's `validate`'s 3rd param /
the server's seat binding). Construct exactly:

- `ProposeTradeIntent` = `{ type: 'intent.proposeTrade', give: Record<ResourceType,number>, get: Record<ResourceType,number> }`
- `AcceptTradeIntent`  = `{ type: 'intent.acceptTrade' }`
- `RejectTradeIntent`  = `{ type: 'intent.rejectTrade' }`
- `CounterTradeIntent` = `{ type: 'intent.counterTrade', give: Record<ResourceType,number>, get: Record<ResourceType,number> }`
- `CancelTradeIntent`  = `{ type: 'intent.cancelTrade' }`
- Use the exported `PlayerIntent` union type for `dispatchIntent`'s param.

Read the open offer from `GameState.openTradeOffer?: TradeOffer`:
- `TradeOffer = { proposerId: PlayerId, give: Record<ResourceType,number>, get: Record<ResourceType,number>, targets: readonly PlayerId[], depth: number }`.
- `give`/`get` are ALWAYS from `proposerId`'s perspective (`give` leaves the proposer, `get`
  arrives at the proposer). When I'm a **target** viewing an incoming offer, from MY seat I
  would *give* the proposer's `get` and *receive* the proposer's `give` — get this flip right
  and unit-test it (it's the classic trade-UI bug).
- **Incoming to me** = `openTradeOffer` exists AND `targets.includes(myPlayerId)` AND
  `proposerId !== myPlayerId`.
- **My outgoing** = `openTradeOffer.proposerId === myPlayerId`.
- `depth === 0` original, `depth === 1` a counter (disable further "Counter").
- Hand = `state.players.find(p => p.id === id)?.resources` (`Record<ResourceType,number>`);
  reuse the S1.6.3 hand-sum pattern. `ResourceType` = `timber|clay|fleece|barley|iron`.

Do NOT expect on core (client/stub): the identity of who I am beyond `store.myPlayerId`, any
network/connection state, timers.

## Key decisions (surface any deviation)

1. **`dispatchIntent` is a stub seam** (see "The scope seam"). This is the whole reason
   S1.6.4 can precede S1.6.5. Do not add networking; do not mutate authoritative `gameState`
   as if a server confirmed — pending-seal stays pending (or a dev-only ack settles a
   preview copy).
2. **Client affordability is a UI affordance, not authority** — pure `canComposeOffer` /
   `canAffordBundle` mirrors; the server (via S1.3.2 `validate`) remains the truth (§7.6).
   Precedent: `renown.ts` mirrors core constants for display.
3. **No modal for trade** (§7.1/§7.5) — the OfferBuilder and incoming OfferCard are docked
   panels in the trade zone; a `Dialog` is explicitly NOT used here.
4. **Quick-reactions are bounded predefined phrases, not chat** (§7.3) — a deliberate
   product choice; do not add a free-text field.
5. **Follow the reference mockup** `docs/design/mockups/game-table.html` for the trade
   zone's placement/proportions; DESIGN.md §6 says trade history lives in the right log zone
   and the builder is a fixed panel. If the mockup and §6/§7 leave the exact docking
   ambiguous, pick the least-surprising placement, implement it, and flag it for owner
   sign-off rather than guessing silently.

## Acceptance criteria (each maps to a §7 rule or a §10 gate)

- [ ] **§7.1 stable geometry:** OfferBuilder is a fixed docked panel; give/receive columns
      never swap; no control reflows between renders or on state change (verify: composing,
      arming, pending all keep button positions).
- [ ] **§7.2 two-step seal:** compose → confirm-in-words → 150ms armed guard; the confirm
      text is a localized, pluralized sentence of the exact deal.
- [ ] **Impossible-offer prevention:** pure tested `canComposeOffer`/`canAffordBundle`;
      steppers clamp to my hand; empty give/get or unaffordable = seal disabled with a
      localized reason. Core `validate` is NOT called client-side (no seed on client).
- [ ] **§7.3 expressive/bounded:** counter edits the incoming offer in-place, pre-filled,
      roles flipped correctly (unit-tested), bounded to one counter (`depth>=1` disables).
      Quick-reactions are predefined + localized; no free-text.
- [ ] **§7.4 trace:** every propose/counter/accept/decline/cancel appends a structured
      `tradeLog` entry (rendered as a compact in-zone recent-deals strip; full log deferred).
- [ ] **§7.5 anti-misclick:** incoming offer is a docked card (never a blocking modal);
      accept (primary) and decline (quiet) ≥16px apart; accept disabled if I can't afford
      `get`.
- [ ] **§7.6 server-truth:** sealing enters a visibly-distinct pending-seal state via the
      `dispatchIntent` stub; no optimistic *confirmation*; reduced-motion respected on the
      pending pulse.
- [ ] **OfferCard** ships incoming/outgoing/history states; **OfferBuilder** ships
      default/hover/focus/active/disabled (+ pending) states (§11 "or it doesn't merge").
- [ ] **The give/get perspective flip** (proposer-perspective → my-seat perspective) is
      correct and unit-tested.
- [ ] **§10 gates:** every string a typed `t()` key in ru/uk/en (missing = build fail);
      numbers via `formatNumber` (tabular); no hue-only info (resource icon+count, flotilla
      emblem+color); keyboard-reachable with visible `--accent` focus ring, focus order =
      visual order; incoming offer announced via `aria-live="polite"`; hit targets ≥44px;
      panels tested at the longest locale (RU/UA ~25–35% longer) with no truncation; no
      ALL-CAPS Cyrillic.
- [ ] Store: `dispatchIntent` + `tradeLog` + `pendingSeal` + selectors, unit-tested; UI-only,
      `gameState` still authoritative-from-fixture.
- [ ] DEFERRED items NOT built (WS/send, log content, bank/port UI, embargo, dashboards,
      board-build, mobile collapse, colorblind toggle).
- [ ] No non-client edits; `pnpm --filter @skervik/client {test,typecheck,lint,build}` +
      `pnpm -r {typecheck,lint,test,build}` all green; §13 slop test passes.
