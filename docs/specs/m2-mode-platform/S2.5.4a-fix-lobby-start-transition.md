# S2.5.4a — Fix the dead lobby Start button (LobbyScreen → GameScreen)

**Epic:** E2.5 · **Tier:** 2 · **Model:** Sonnet · **Priority: 0 (playability blocker)**
**Status:** materialized 2026-07-10 · fixes a defect S2.5.4 shipped (`a2d1f77`)
**Branch base:** tip of `feat/s2.5.3-private-rooms` (`faadc0e`), NOT `main` — see "Branching".

## The defect

Clicking the lobby **Start** button connects to the server but **never switches the screen to
the game**. `App.tsx:24` renders `started ? <GameScreen/> : <LobbyScreen/>`, and the only caller
of `useLobbyStore.getState().start()` is `main.tsx:83` — gated on `coldLoadAction.kind !== 'lobby'`,
so it fires **only** on a cold-load resume / invite-link path. The Start handler
(`main.tsx:88` → `startConnection`) connects but never flips `started`. Result: a human picks a
preset, clicks Start, the socket connects — and the screen stays on the lobby forever. The game
is reachable only by reloading the page (which hits resume-first).

This is the [[spec-goal-must-match-acceptance-criteria]] shape: S2.5.4's Goal ("picks a preset,
presses Start, and plays") went green with the promised capability shipped as non-functional
scaffolding, because no forcing criterion bound the terminal observable — *GameScreen visible
after Start*. It reproduces on `main` @ `a2d1f77`. See [[lobby-start-button-dead]].

## The fix (bind the transition to connection success, not to the click)

`connect()` (`wsClient.ts:320`) **never throws**: it returns a `WsClientHandle` on success and
`null` on any failure (expired resume, rejected join, absent server). `startConnection`
(`main.tsx:54`) already receives that value and calls `setConnection(handle)` unconditionally.

Flip `started` **only when the Start-initiated connect returned a non-null handle** — that is the
terminal observable that the room is actually live. Do NOT flip synchronously in `onStart` or
before `connect()` resolves: a failed connect must leave the user on the lobby (the existing
"failed/absent server just leaves the fallback view" contract, `main.tsx` docstring), never on a
blank GameScreen.

`.start()` is idempotent, so the cold-load resume path (which already calls it at `main.tsx:83`)
is unaffected — calling it again after a resumed `startConnection()` is a no-op.

## Why a test didn't catch it, and what the test must therefore be

The client has **no jsdom**; its only render path is `renderToStaticMarkup`, and zustand v5's
`getServerSnapshot` returns `getInitialState()` — so a store `setState()` is invisible to a
static render ([[zustand-store-not-observable-in-static-render]]). A test that renders `<App/>`
after a simulated Start would falsely see the initial (`started:false`) state regardless.

**Therefore the transition decision must be a pure, React-free unit.** Extract the "did this
connect succeed → should we show the game" decision so it can be asserted directly. Mirror the
existing `deriveLobbyViewState` / `hud/trade.ts` "pure helper, separately tested" split. The
forcing test drives the real code path (a `startConnection` with a mocked `connect`), not a
re-implementation.

## Acceptance criteria (forcing)

1. **Success flips the screen.** A Start-initiated `startConnection` whose `connect` resolves a
   **non-null** handle results in `useLobbyStore.getState().started === true` (→ `<App/>` would
   render `<GameScreen/>`). This test must FAIL against the current code (prove it: it does today).
2. **Failure stays on the lobby.** A `startConnection` whose `connect` resolves **`null`** (server
   down / rejected join) leaves `started === false` — the user remains on `<LobbyScreen/>`. Prove
   by making the mocked `connect` return `null` and asserting no transition.
3. **Resume path unchanged.** The S2.3.2a cold-load resume still shows the game (it flips
   `started` at `main.tsx:83` before `startConnection()`), and the S2.3.2a forcing cold-load test
   stays green. Calling `.start()` again inside a resumed `startConnection` is a harmless no-op —
   assert it does not throw / double-fire anything observable.
4. **Guard-removal proof.** Remove the new flip and show criterion 1 fails; revert. (Same
   discipline the S2.5.4 / S2.5.3 workers used.)

- `packages/client/src/main.tsx` — `startConnection` is now `export`ed; on success it

### Follow-up commit — narrow the flip to quickMatch only (review feedback)

Review caught a regression against S2.5.3: the first commit's flip fired for ANY
Start-initiated `lobbySelection`, including `createPrivate`/`joinByCode`. Since
`App.tsx` renders `<GameScreen>` XOR `<LobbyScreen>`, flipping `started` for
`createPrivate` unmounted `<LobbyScreen>` the instant `connect()` resolved — exactly
where S2.5.3 renders the just-created invite link (`deriveLobbyViewState`'s
`showInvite`), deleting that feature's visible effect. `joinByCode`/`createPrivate`
also have no live `gameState` yet (no seats-full auto-start), so `<GameScreen>` would
render blank.

- `shouldStartAfterConnect` (`lobbyStore.ts`) now takes a second parameter,
  `joinMode: JoinMode | undefined`, and returns `handle !== null && joinMode?.kind ===
  'quickMatch'` — still pure, still directly unit-tested (5 cases: quickMatch+handle
  → true; null handle → false; createPrivate+handle → false; joinByCode+handle →
  false; undefined joinMode+handle → false, covering the cold-load resume shape).
- `main.tsx`'s call site now passes `joinMode` through:
  `shouldStartAfterConnect(handle, joinMode)`.
- `main.test.ts` gained two new forcing regression-guard tests: a `createPrivate`
  Start with a LIVE handle asserts `started === false` (host stays put, sees the
  invite link) and a connection handle IS still set; a `joinByCode` Start with a LIVE
  handle likewise asserts `started === false`. Both were proven to FAIL against the
  first commit's un-narrowed logic (temporarily reverted `shouldStartAfterConnect`'s
  call to `handle !== null` with no join-mode check, ran `vitest run src/main.test.ts`
  — both regression tests failed with `expected true to be false`, the other 4 stayed
  green), then restored (byte-identical `diff` against the narrowed version) and
  reran — all 6 green.
- Re-verified full chain after the narrowing: build green all packages; test — core
  334, protocol 41, bots 82, server 138, **client 210** (205 prior + 2 in
  `main.test.ts` + 3 in `lobbyStore.test.ts`); lint clean; typecheck clean.
- `createPrivate`/`joinByCode` Start still has NO transition to `<GameScreen>` after
  this narrowing — that's intentional per review (belongs to the ready-up /
  match-started work, S2.5.2), not a residual defect of this story.
