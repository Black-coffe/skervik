# S2.1.4 — Server-enforced turn timers (soft/hard) + anti-AFK

## Goal

Realize the anti-"dead time" product rule — *"no dead time: turn timers"* + *"≤60 min hard cap"* +
*"no karmic bans"* (CLAUDE.md · roadmap principles 4/5) — with **server-authoritative** per-turn
timers. A player who stalls gets a **soft** warning (a visible countdown), and at the **hard** deadline
the server **auto-plays a minimal legal default** for them so the match never hangs — then tracks
consecutive time-outs (**anti-AFK**) so a later story (S2.3.3) can bot-fill a truly absent player. No
punishment, no lost game: the turn simply advances.

**The load-bearing invariant: wall-clock lives ONLY in the Colyseus room; the deterministic core and
the event log never see a clock.** On the hard deadline the room computes a **deterministic default
action**, forges a normal `PlayerIntent`, and pushes it through the SAME `#queue`-serialized
`validate → persist → commit → broadcast` pipeline as a human intent. The event log records only the
RESULTING event (`turn.ended` / `dice.rolled` / `resources.discarded` / `robber.moved`) — **no
timestamp, no "timeout" marker** — so replay and the S1.7.3 verifier reproduce the match byte-identically
and can't even tell a turn was auto-played. Timers are `RuleProfile` config **read only by the server**;
`reduce`/`validate` stay timer-agnostic and Classic/Balanced/Blitz play is byte-unchanged.

## What to build

### 1. `TimerProfile` in the core config (server-consumed only)
Add a `TimerProfile` sub-profile to `RuleProfile` (following the `RobberProfile`/`VictoryProfile`
pattern, `ruleProfile.ts:23-107`) — durations in ms, per decision phase:
```
interface TimerProfile {
  readonly softWarningMs: number;    // when the client should start visibly warning (< hard)
  readonly rollMs: number;           // 'roll' phase hard deadline
  readonly mainMs: number;           // 'main' phase hard deadline
  readonly discardMs: number;        // 'robber' + playersToDiscard hard deadline
  readonly robberMs: number;         // 'robber' move (+ steal) hard deadline
}
```
Set `timers` on **CLASSIC / BALANCED / BLITZ** (Blitz tighter — e.g. Classic main 120s, Blitz 60s;
values are v1, documented as tunable — calibrate against telemetry in M3). **`reduce`/`validate` MUST
NOT read `timers`** (grep-confirm) — the field is resolved by the server only. Adding it is safe for
determinism because `GameState` carries only `profileId` (not the profile object), so no golden fixture
or serialized state changes — confirm the existing core+server suites stay green unchanged.

### 2. The deterministic forced-default-action resolver (server, PURE + unit-tested)
A pure function (server package, e.g. `packages/server/src/room/forcedAction.ts`)
`resolveForcedAction(state: GameState): { playerId: PlayerId; intent: PlayerIntent } | null` that, for
the current phase, returns the minimal legal default + WHO acts:
- **`'roll'`** → the current player's `intent.rollDice` (seed-derived roll; already in the log/verify —
  no change).
- **`'main'`** → the current player's `intent.endTurn` (no resource choice — simplest legal exit).
- **`'robber'` with `playersToDiscard` non-empty** → for EACH still-owing player, an `intent.discard`
  selecting cards by a **deterministic policy** (discard down to `floor(hand/2)` from the LARGEST
  resource stacks first, ties broken by a fixed canonical resource order). **This is a server default
  policy, NOT a core rule and NOT seed-derived** — so verify is unchanged and no new PRNG slot is used.
- **`'robber'` with `playersToDiscard` empty** → the current player's `intent.moveRobber` to a
  **deterministic default tile** (e.g. the lowest-index tile ≠ current robber tile that is legal); the
  steal victim/resource then follows the normal seed-derived rule inside validate/reduce (verify already
  covers it — no change).
- **`'setup'`** → **return `null` (DEFERRED)** — auto-placement needs board topology (distance rule +
  road connectivity); do NOT implement here (see Scope). During setup the room arms only a soft warning,
  no hard forced action (surface this gap).
- **`'lobby'`/`'finished'`** → `null` (no timer).
This function is **pure, deterministic, wall-clock-free** and gets exhaustive per-phase unit tests.

### 3. Server enforcement in GameRoom (the wall-clock boundary)
- **Arm/disarm via `this.clock`** (Colyseus room clock — lifecycle-bound, auto-cleared on dispose; NOT
  `Date.now()` scattered around, NOT bare `setTimeout`). After every committed state change, re-arm:
  cancel the prior timer and, based on the NEW `state.phase`/`playersToDiscard`, arm a hard timer sized
  by `loadRuleProfile(state.profileId).timers` for the acting player; arm a soft-warning at
  `softWarningMs`. On a real intent for the active decision, disarm.
- **Refactor the pipeline tail into ONE shared authoritative method.** Extract the
  `validate → fold → persist(await append) → commit → update schema → broadcast` tail (currently inside
  `#handleIntent`, `GameRoom.ts:399-524`) into a private method taking `(playerId, intent)`, so BOTH
  `#handleIntent` (real client) and the new forced-action path call the identical path. Re-arm the timer
  at the END of this shared tail from the new state.
- **Inject the forced action onto `#queue`** (NEVER race a live intent — [[server-intent-pipeline-serialization]]):
  on hard-timeout, enqueue a link that computes `resolveForcedAction(this.gameState)` **at execution
  time** (not at arm time — state may have moved) and runs the shared tail for each `(playerId, intent)`
  it returns. If `resolveForcedAction` returns `null` (e.g. state already advanced, or setup), it's a
  no-op. Multiple owing discarders → enqueue each forced discard in turn.
- **Determinism guard:** the forced action carries NO wall-clock data; the seed passed to `validate` is
  the same server secret as for real intents; the resulting event(s) are persisted + broadcast exactly
  like a human action. Grep the core after: still zero wall-clock, zero ambient RNG.

### 4. Presentational deadline in the room schema (NOT in GameState/log)
- Add a **wall-clock deadline to the Colyseus `RoomSchema`** (`RoomSchema.ts:31-44`) — e.g.
  `turnDeadline: number` (epoch ms) + optionally `turnSoftWarnAt: number` — set when the hard timer is
  armed, cleared/updated on re-arm. The client renders `remaining = turnDeadline − Date.now()`.
- **This is presentational projection ONLY** — it lives in the Colyseus schema (which already carries
  `phase`/`currentPlayerId`), **NEVER in the deterministic `GameState`, never in a `GameEvent`, never in
  the persisted log.** That separation is what keeps the log timestamp-free. Confirm no event/GameState
  field gains a deadline.

### 5. Anti-AFK tracking (server session state, not game rules)
- Track `consecutiveTimeouts` per player in the ROOM (server memory / RoomSchema seat projection), NOT
  in `GameState`/the log (it's session metadata, not a game rule → keeps the core clean & deterministic).
  Increment when a player's turn is force-completed; reset to 0 on any real intent from that player.
- Expose an **idle flag** on the seat projection (e.g. `seat.idle`/`seat.consecutiveMisses`) once a
  player crosses a threshold (a documented constant, or a `TimerProfile.afkThreshold`), so the HUD can
  show "away" and **S2.3.3 bot-fill can later consume it**. S2.1.4 does NOT replace the player with a
  bot and does NOT remove them (no karmic ban) — it only flags + keeps auto-advancing.

## Key decisions (surface any deviation)

1. **Wall-clock is server-only; the event log stays timestamp-free.** Timers use `this.clock` in
   GameRoom; on expiry the room injects a DETERMINISTIC default action through the authoritative
   pipeline, and the log records the resulting normal event (no timeout marker, no timestamp). Why: the
   deterministic-isomorphic-core invariant + replay/verify integrity — a replayed match must be
   byte-identical regardless of the real timing that produced it. Rejected: a `turn.timedOut` event
   carrying a timestamp (pollutes the log with wall-clock, breaks the "no wall-clock in core" contract);
   a timer inside `reduce` (impossible — core has no clock).
2. **Forced action enters `#queue`, computed at execution time.** Why: [[server-intent-pipeline-serialization]]
   — Colyseus doesn't serialize async handlers, so a floating timer callback that mutated state would
   TOCTOU-race a real intent arriving at the same instant. Enqueuing (and re-reading state inside the
   link) guarantees FIFO ordering and that a just-taken real action cancels the now-moot forced one
   (resolver returns `null`).
3. **Forced defaults are the MINIMAL legal move, discard by a DETERMINISTIC server policy (not seed).**
   Why: `intent.endTurn`/`rollDice`/`moveRobber` reuse existing events (log unchanged in shape) and the
   seed-derived bits (roll, steal) are already verify-covered; discard is player-chosen so it needs a
   default, and a deterministic largest-stacks policy avoids adding a new seed draw + verify branch.
   Reject: random/seed-derived discard (would expand the S1.7.3 verifier for a mere timeout default).
4. **`timers` is core config but server-consumed; `reduce`/`validate` never read it.** Why: durations
   are wall-clock policy, not game logic — keeping them out of the core preserves determinism while still
   letting the profile be the single config source (the server resolves `loadRuleProfile(profileId).timers`).
5. **The deadline is a RoomSchema presentational field, never GameState/event.** Why: clients need a
   countdown, but a wall-clock deadline in `GameState`/the log would break the timestamp-free invariant.
   The Colyseus schema is the correct home for ephemeral presentational projection.
6. **Anti-AFK is server session state, not a game rule.** Why: consecutive-timeout counts + an idle flag
   are matchmaking/resilience metadata (S2.3.3 will act on them); putting them in `GameState`/the log
   would make the deterministic core depend on session liveness. Kept in the room.
7. **Setup-phase hard timeout deferred; Opus worker.** Why: setup auto-placement is genuinely complex
   (topology) — out of a timer story's scope; and the wall-clock↔core boundary + pipeline injection are
   the hard, high-stakes part → Opus, not Sonnet.
8. **No ADR needed** — determinism + authoritative server + #queue are locked; this is their application.
   Flag for an ADR only if the shared-tail refactor or the schema-deadline placement proves contentious.
