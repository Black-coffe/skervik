# Client: one per-match topology seam, six migrated call sites

## Goal

The client stops baking a radius-2 board into module scope. A new `board/matchTopology.ts` exports
`topologyForProfile(profileId)` (a thin wrapper over core's `loadRuleProfile` + memoized
`topologyForRadius`) and a `useMatchTopology()` hook that reads the active match's `profileId` from
the HUD store. The five module-level `buildTopology()` constants and the dev fixture route through
it, so rendering, hit-testing and placement legality follow whatever board the match is actually on.

## Implementation notes
- Assumption 1 resolved without a new store field: `GameState.profileId` already exists and is
  already folded from `match.started` via `applyEventBatch`'s `reduce`/`applySnapshot`. Added
  `selectProfileId(state: GameState)` to `hud/store.ts` (same pure-selector pattern as
  `selectSeatOrder`) rather than duplicating state; `useMatchTopology()` reads it via that selector.
- `devFixture.ts` deliberately does NOT import `matchTopology.ts`'s `topologyForProfile`, even though
  it's the identical one-liner: `hud/store.ts` reads `devFixtureState` at MODULE TOP LEVEL
  (`DEV_MY_PLAYER_ID`), so `devFixture.ts -> matchTopology.ts -> hud/store.ts -> devFixture.ts` is a
  real load-order cycle (confirmed by a failing test run: `devFixtureState` was `undefined` inside
  `store.ts` at import time), not the benign "only touched inside a hook body" kind. Fixed by having
  `devFixture.ts` call `loadRuleProfile` + `topologyForRadius` inline (same core primitives, no second
  cache) instead of routing through the seam module.
