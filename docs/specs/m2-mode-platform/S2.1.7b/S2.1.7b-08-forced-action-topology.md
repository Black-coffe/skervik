# Forced-action fallback uses the room's per-match topology

## Goal

`forcedAction.ts:210` still calls no-arg `buildTopology()` to pick a robber tile when a
hard-timeout forces a move. In an `expanded` room that samples a 19-tile radius-2 topology
inside a 37-tile match — a wrong-board pick that validate may reject or, worse, accept
silently. Found by the S2.1.7b-04 worker (its `## Findings`), out of that story's scope.
After this story every forced-action path resolves the same per-match topology the room
resolved at `#startMatch`.

- packages/server/src/room/forcedAction.test.ts

## Implementation notes
- `resolveMoveRobber` now resolves `loadRuleProfile(state.profileId ?? 'classic')` once and calls
  `topologyForRadius(profile.board.radius, profile.board.ports.length)` instead of the no-arg
  `buildTopology()` — the exact pattern `validate.ts`'s own `topology(state)` helper already uses, so
  forcedAction and validate now share one topology source. The pre-existing `loadRuleProfile` call for
  `robber` settings was folded into this single profile resolution (no behavior change).
- Confirmed by proof, not just test: `enumerateTileCoords` builds rings 0..radius, so Classic's 19-tile
  array is an order-identical PREFIX of `expanded`'s 37-tile array. Since `resolveMoveRobber` excludes
  only the single current `robberTileId`, the picked default tile is mathematically always within that
  shared prefix for BOTH the old and new code — this sub-bug is not black-box-observable as an
  old-code-fails/new-code-passes regression test. Added a test anyway (`forcedAction.test.ts`, new
  describe block) using an `expanded` room whose CURRENT robber tile is itself an outer-ring
  (radius-3-only) tile past the 19-tile range, asserting the forced move resolves against the real
  37-tile board and validates end-to-end — a forward-looking regression/documentation test, not a
  characterization of a currently reachable defect.
