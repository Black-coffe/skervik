# 5–6 player expanded e2e: single-player, multi-client, and verify

## Goal

Prove the whole pack end to end: a 6-seat `expanded` room really seats 6, really plays the 37-tile
board, really terminates with a winner, and its event log really re-verifies — through the same
socket path a production client uses. This is the acceptance evidence for ADR-0013's "2–6 players"
criterion and the gate that catches any call site the migration stories missed (ADR-0013 names
"a missed call site silently renders/validates the wrong board" as the fail-quiet risk).

## Files
- packages/server/src/e2e/expandedMatch.e2e.test.ts
- packages/server/src/e2e/expandedMultiClient.e2e.test.ts

## Non-goals
- Do NOT modify production code. If a test cannot pass, the finding goes in `## Findings` and back
  to the Queen — a test story that patches `GameRoom` to make itself green defeats its own purpose.
- Do NOT modify `scriptedDriver.ts`, `fullMatch.e2e.test.ts` or `twoPlayerMatch.e2e.test.ts`. Read
  them as templates (`fullMatch` for the socket/ephemeral-port/N-client shape, `N_SEATS=3` at `:59`;
  `twoPlayerMatch` for the boot-free non-Classic-profile shape and its pinned-terminating-seed
  comment at `:39`), then write NEW files.
- Do NOT change `routes/matchVerify.ts` — scouting says it is board-size-agnostic; this story
  proves that claim rather than assuming or "fixing" it.
- Do NOT add balance assertions (who won, how fast, resource fairness). Termination and determinism
  only; 5–6p balance is M3.
- Do NOT introduce sleeps/timeouts as synchronisation. Follow the existing e2e's event-driven waits;
  a 6-seat match is longer than a 3-seat one, so raise the vitest timeout rather than polling.

## Acceptance criteria
- [ ] **Boot-free 6-player expanded match** (`expandedMatch.e2e.test.ts`): a pinned terminating seed
      drives a full `expanded` match to a winner with 6 seats. Reuse the seed story 02 reports in its
      `## Implementation notes` if it terminates here too; otherwise pin a new one and say so.
- [ ] **Determinism:** the same seed replays to the identical final state and identical event stream,
      twice in the same process — with a Classic match run in between, so the per-radius memo is
      proven not to leak radius-2 topology into the expanded run or vice versa.
- [ ] **Verify leg:** the expanded match's event log re-verifies clean through the same recompute the
      `matchVerify` route uses (`board.generated` reproduced from `loadRuleProfile(profileId).board`),
      and a deliberately corrupted expanded layout is FLAGGED. Both directions, as S2.1.7a's core
      test did — this is the fairness guarantee, not a smoke test.
- [ ] **Single-player** (`expandedMultiClient.e2e.test.ts`): one real socket client selects
      `{profileId:'expanded', bots:5}`, the room reports `maxClients === 6`, bot-fill seats the other
      five, and the match reaches a winner. Proves the lobby→server→bots→core chain with no seat
      count anywhere on the wire.
- [ ] **Multi-client:** five real socket clients join one expanded room (ephemeral port, in-process
      `@colyseus/testing`, `fullMatch` shape), all receive `match.started` carrying
      `profileId:'expanded'`, and the match reaches a winner.
- [ ] **Seed secrecy** still holds on the expanded path: no client-visible message ever carries the
      raw seed (only `seedHash`) — assert it as `fullMatch.e2e.test.ts` does.
- [ ] A 6th player cannot join a 6-seat room, and a `classic` room still caps at 4 in the same run.
- [ ] Both new files pass with the rest of `@skervik/server` green and no existing e2e edited.

## Implementation notes

- **`expandedMatch.e2e.test.ts`** (boot-free, mirrors `twoPlayerMatch.e2e.test.ts`): reused
  story 02's pinned seed `'grand-chart'` — it terminates under THIS file's driver too
  (`decideAction`/v0, not story 02's v1-`medium` harness bots), 250 steps. Three tests: (1) a
  6-seat winner on the 37-tile board (`vpToWin` read from `loadRuleProfile('expanded').victory`,
  not hardcoded); (2) determinism — the same seed run twice, WITH a real Classic
  (`'skervik-s1.7.2-e2e-match-seed'`, duplicated as a literal per the template's own convention)
  match run in between, asserting the interleaved Classic board stays 19 tiles and both expanded
  runs stay 37 tiles (proves `topologyForRadius`'s per-radius memo doesn't leak either direction);
  (3) verify leg — `verifyMatchRandomness(seed, events)` (the exact call `routes/matchVerify.ts`
  makes) passes clean on the real log, and a corrupted `robberTileId` is flagged, both directions
  per the story's S2.1.7a core-test precedent.
- **`expandedMultiClient.e2e.test.ts`** (socket-based, mirrors `fullMatch.e2e.test.ts`): three
  independent server boots. (1) single-player: 1 real client + `bots:5` fills a room whose
  `maxClients` derives PURELY from `loadRuleProfile('expanded').maxSeats` (no `maxSeats` on the
  wire or at `createHttpServer`) — asserted server-side via `matchMaker.getLocalRoomById(...).
  maxClients === 6` — and reaches a winner. (2) multi-client: 5 real sockets (room-level
  `maxSeats:5` override, within the profile's own 5-6 range) all receive `match.started` carrying
  `profileId:'expanded'` (checked per-client, not just the folding client) and reach a winner;
  seed secrecy checked on every socket. (3) seat-cap boundaries in one server run, no `maxSeats`
  override anywhere: 6 real clients fill an expanded room, then a 7th `joinById` on that same
  room is rejected; separately 4 real clients fill a Classic room, then a 5th `joinById` is
  rejected — proves both caps are profile-derived, not hardcoded, in the same process. (Read
  literally as "a 6th/5th player cannot join" — interpreted as "one beyond the profile's own
  cap can't join an already-full room," since a 6-seat room's 6th seat obviously CAN join, that's
  how it starts.)
- **Teardown note (test-infra only, not production):** the two seat-cap `it`s deliberately skip
  `room.leave()` after asserting the rejection — the match there is still mid-`setup` (never
  driven to a winner), so a consented leave triggers `#botFillSeat`, which raced this block's
  `afterAll` (`handle.close()` + `rm(matchesDir)`) and produced harmless-but-noisy
  `[GameRoom] failed to persist a validated batch` log lines (best-effort, caught internally,
  never failed a test). `handle.close()` tears every socket down anyway. `rm(matchesDir, ...)`
  also grew `maxRetries`/`retryDelay` (Node's own documented mitigation for a Windows
  file-still-flushing race), not a synchronization sleep.
- Full suite: `pnpm -s --filter @skervik/server test` — 29 files / 205 tests, all green. No
  existing e2e file edited. `typecheck` and `lint` both clean on `@skervik/server`.

## Findings

- **A stale `packages/bots/dist/` build produced a false-looking production defect (worth
  flagging even though it isn't code this story may fix).** `@skervik/bots`'s `package.json`
  resolves `@skervik/server`'s import ONLY through `dist/index.js` (the `"import"`/`"default"`
  conditions), never `src/`. On this run, `packages/bots/dist` was dated 2026-07-14 — BEFORE
  story 02 (2026-08-16) landed the per-radius topology fix — so `@skervik/server`'s test process
  was silently running the OLD module-level `TOPO = buildTopology()` (hardcoded radius-2, 9
  ports) inside `v0.ts`'s bank-rate mirror. Symptom: EVERY 6-player expanded seed I tried
  (`'grand-chart'` plus 9 others) failed within ~250 steps with `intent.bankTrade ... WRONG_RATE_COUNT`
  — the driver's own `bestBankRate` mirror was indexing an 11-port `board.portContents` array
  through a stale 9-slot topology, misreading a phantom "generic port" and proposing rate 3
  instead of the true 4. I confirmed this by temporarily instrumenting `v0.ts`'s `bestBankRate`
  (immediately reverted — `git diff` on the file is empty) and comparing against a hand-rolled
  recompute of the SAME algorithm: with the stale dist, `owned` diverged from what the identical
  source-level algorithm computed; after `pnpm --filter @skervik/bots build`, every seed
  terminated cleanly (`'grand-chart'`: 250 steps, winner `p2`). **This is a workspace-hygiene /
  CI-ordering risk, not a `v0.ts` bug** — `v0.ts` on disk was already correct; only the compiled
  artifact was stale. Root cause candidate: `.github/workflows/ci.yml`'s `verify` job runs the
  `Test` step (`pnpm test`) BEFORE the `Build` step (`pnpm build`), and `packages/bots/dist` is
  gitignored (never committed) — a genuinely fresh CI checkout would have NO `dist/` at all when
  `@skervik/server`'s tests try to resolve `@skervik/bots`, not merely a stale one. I could not
  fully verify from this workspace whether CI is currently green despite this (some other
  lifecycle hook I didn't find may pre-build), but the ordering as written does not guarantee
  `@skervik/bots` is built before `@skervik/server`'s tests run. Recommend the Queen check whether
  CI needs a `pnpm -r build` (or a bots-specific build) inserted before the `Test` step, or a
  `pretest` hook on `@skervik/server` that builds its workspace deps first — the exact "a missed
  call site silently renders/validates the wrong board" fail-quiet risk ADR-0013 names, just at
  the build-artifact layer instead of a call site.
