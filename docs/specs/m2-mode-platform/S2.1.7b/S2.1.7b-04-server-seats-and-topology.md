# Protocol + server: `expanded` on the wire, seats and topology from the profile

## Goal

A room's seat count and board stop being independent constants. `GameRoom` takes `maxClients` from
`loadRuleProfile(profileId).maxSeats` and builds its topology from the same profile's board, so
selecting `expanded` yields a 6-seat room on the 37-tile board. The protocol accepts `expanded` as a
shipping profile and raises the lobby bot cap to 5 so a single player can fill a 6-seat room.

## Non-goals
- Do NOT add a seat-count field to the wire. Seats are server-owned and derived from the preset
  (plan D3); `joinOptionsSecurity.e2e.test.ts:80`'s "client-supplied maxSeats is rejected" assertion
  must still hold after this story — strengthen it if anything, never relax it.
- Do NOT touch bot-fill internals (`#botFillSeat`, `#driveBotTurn`) — scouting confirms they are
  seat-count-agnostic. If a 6th seat exposes a bug there, report it in `## Findings` first.
- Do NOT add matchmaking changes: `.filterBy(['profileId'])` already separates expanded queues.
- Do NOT enforce `minSeats` at match start. It is advisory metadata in this pack; a start gate would
  break existing 1–3 seat room tests.
- Do NOT write the 5–6p e2e here — story 07 owns it. Unit/room-level coverage only.
- Do NOT touch `routes/matchVerify.ts` (board-size-agnostic) or the client.

## Implementation notes
- Ordering bug fixed as named: `GameRoom.onCreate` now resolves `#profileId` FIRST, then derives
  `maxClients` from `options?.maxSeats ?? loadRuleProfile(#profileId).maxSeats`; `DEFAULT_MAX_SEATS`
  constant removed. `#startMatch` resolves its genesis topology via
  `topologyForRadius(profile.board.radius, profile.board.ports.length)` instead of the old no-arg
  `buildTopology()` (which was always radius-2, silently wrong for `expanded`).
- `boot.ts`/`index.ts` needed NO functional changes: `.filterBy(['profileId'])` (D3, already present
  on both `define()` sites) already segregates `expanded` quick-matches; `CreateHttpServerOptions`
  doesn't need a seat-cap default change since the room derives it per-profile now.
- ADR-0012 confirmation (assumption 4): `MatchStartMetadata.profile: RuleProfile` is persisted
  as-is (jsonb, `pgMatchMetadataStore.ts:52`) — no zod schema, no hand-written literal pinning its
  shape. `pgMatchMetadataStore.test.ts` asserts against `CLASSIC_PROFILE` imported directly from
  core, so the additive `minSeats`/`maxSeats` fields round-trip with zero test changes needed.
- Root-caused a build-freshness trap during verification: `@skervik/protocol`'s dist was stale after
  editing `messages.ts` (workspace `exports` resolve to `dist/index.js`, not source) — `pnpm --filter
  @skervik/protocol build` was required before `@skervik/server test` would see `'expanded'`/`.max(5)`.
  Also ran the full suite twice back-to-back to confirm the one apparently-unrelated multi-file
  flake seen mid-session (`maxClients` reading `undefined` in files this story never touched) was
  Windows/CPU-contention noise from many real-WS-server test files running in parallel, not a real
  regression — it did not reproduce on a clean re-run once the dist rebuild was in place.

## Findings
- `packages/server/src/room/forcedAction.ts:210` (`resolveMoveRobber`) still calls no-arg
  `buildTopology()` (radius-2/19-tile) to pick a default forced-robber-move tile on a hard-timeout
  forced action. This file is NOT in this story's `## Files`, so it was left untouched (Law 3) — but
  it means a hard-timeout-forced robber move in an `expanded` (radius-3) room would resolve against
  the WRONG topology (could pick a tile id that doesn't exist on the actual 37-tile board, or the
  fallback `if (!defaultTile) return null` never triggers because the wrong-topology tile always
  exists). Same latent-bug shape as this story's own headline fix, one file over. Recommend a
  follow-up story (or folding into whichever wave-3 story exercises forced actions under `expanded`)
  to route it through `state.board`'s own radius via `topologyForRadius`, mirroring this story's
  `GameRoom.ts:743` fix.
