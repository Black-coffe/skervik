# Protocol + server: `expanded` on the wire, seats and topology from the profile

## Goal

A room's seat count and board stop being independent constants. `GameRoom` takes `maxClients` from
`loadRuleProfile(profileId).maxSeats` and builds its topology from the same profile's board, so
selecting `expanded` yields a 6-seat room on the 37-tile board. The protocol accepts `expanded` as a
shipping profile and raises the lobby bot cap to 5 so a single player can fill a 6-seat room.

## Non-goals
- Do NOT add a seat-count field to the wire. Seats are server-owned and derived from the preset
  (plan D3); `joinOptionsSecurity.e2e.test.ts:80`'s "client-supplied maxSeats is rejected" assertion
  must still hold after this story — strengthen it if anything, never relax it.
- Do NOT touch bot-fill internals (`#botFillSeat`, `#driveBotTurn`) — scouting confirms they are
  seat-count-agnostic. If a 6th seat exposes a bug there, report it in `## Findings` first.
- Do NOT add matchmaking changes: `.filterBy(['profileId'])` already separates expanded queues.
- Do NOT enforce `minSeats` at match start. It is advisory metadata in this pack; a start gate would
  break existing 1–3 seat room tests.
- Do NOT write the 5–6p e2e here — story 07 owns it. Unit/room-level coverage only.
- Do NOT touch `routes/matchVerify.ts` (board-size-agnostic) or the client.

## Acceptance criteria
- [ ] `ShippingProfileIdSchema` (`messages.ts:300`) includes `'expanded'`; both consumers
      (`MatchStartedEvent` `:312`, `JoinLobbySelectionSchema` `:706`) accept it.
- [ ] `JoinLobbySelectionSchema.bots` cap goes `.max(3)` → `.max(5)` (`:709`) — a widening, so
      previously-valid payloads stay valid. The server additionally **clamps/rejects** `bots >
      maxSeats − 1` for the selected profile, so `{profileId:'classic', bots:5}` is still refused;
      a test covers exactly that pair.
- [ ] `GameRoom` seat default comes from the profile: `options?.maxSeats ?? loadRuleProfile(
      profileId).maxSeats`, replacing `DEFAULT_MAX_SEATS = 4` (`:58`, `:474`). **Ordering:**
      `#profileId` is currently assigned at `:485`, AFTER `maxClients` at `:474` — resolve the
      profile first; a room created with `profileId:'expanded'` must report `maxClients === 6`
      without any caller passing `maxSeats`.
- [ ] Explicit server-side `options.maxSeats` still wins (the existing 1–4 seat `GameRoom.test.ts`
      cases pass unchanged) — this is a default change, not a removal of the override.
- [ ] `GameRoom.ts:743`'s `buildTopology()` becomes
      `topologyForRadius(board.radius, board.ports.length)` with `board` from the room's profile.
      No no-arg `buildTopology()` remains in `packages/server/src`.
- [ ] A room-level test proves an `expanded` room generates a 37-tile board and a `classic` room in
      the same process still generates 19 — i.e. the per-radius memo serves two live rooms
      correctly, which the old process-global singleton could not.
- [ ] Classic rooms are byte-unchanged: same seats, same board bytes, same event stream.
- [ ] Confirm (and note in `## Implementation notes`) whether `matchMetadata` / ADR-0012
      `matches.profile` persists the full profile object; if it does, verify the two additive seat
      fields break no schema or contract test.
