# S2.4.2a — Core bank-conservation fix (resources destroyed on build/buy/discard)

## The bug (confirmed by two independent agents 2026-07-08)

The M1 core models a **finite bank** (`GameState.bank?`, 19 per resource = 95 total, `types.ts:242` /
`ruleProfile.ts:323`). Production is **gated all-or-nothing** on it: a roll pays out only if the bank can
cover the full amount owed, else NOBODY gets that resource (`validate.ts:992-995`), and the bank is
decremented on payout.

**But builds / dev-card buys / discards NEVER credit the bank back.** The events are created WITHOUT a bank
credit and the reducer never touches the bank for them:
- `road.built` (`validate.ts:1360-1366`), `settlement.built` (`:1403-1409`), `city.built` (`:1438-1444`),
  `devCard.bought` (`:1467-1474`), `resources.discarded` (`:1658-1664`) — the cost/discard leaves the
  player's hand and **vanishes** (no `bank` field; no reduce bank-credit).
- The ONLY bank refill in the whole core is `bank.trade`'s give-side (`validate.ts:2020`). Year-of-plenty
  DRAWS from the bank. Both rare.

**Consequence — conservation is broken:** `bank + Σ(all player hands)` STRICTLY DECREASES on every
build/buy/discard. In physical Catan (which `ruleProfile.ts:47` claims parity with — *"Physical-Catan
parity: 19"*) building/buying/discarding RETURNS cards to the bank (a closed, conserved loop). Here they
are destroyed. Over a long match the pool drains toward 0, production rolls start failing the all-or-nothing
gate, and the game **freezes** (measured: 8 of 95 resources left at a stall; several bank resources at 0).

**Why M1/S1.7.2 missed it:** the E2E golden match reached `game.ended` in ~278 turns on one seed — short
enough (few builds) to finish before the bank starved. Long / build-heavy matches (bot self-play; a long
real game) hit the wall. This is the ROOT of [[v0-seed-fragility-carryforward]] — NOT a bot-quality issue.

## The fix (owner-approved 2026-07-08) — restore conservation, reduce-only

**Credit the bank back when resources leave a hand for the bank.** The production GATE reads `state.bank`
(which the reducer maintains) — so the fix is **purely in `reduce`**; `validate` (event creation + the
production gate) does NOT change, because the build/discard events ALREADY carry the payload reduce needs.

Add a bank credit to these 5 reduce cases, deriving the amount from the event's EXISTING payload (no new
event field, no protocol change):
- `road.built` / `settlement.built` / `city.built` — credit `event.cost` back: for each resource `k` in
  `cost`, `nextBank[k] = (state.bank?.[k] ?? bankPerResource) + cost[k]`.
- `devCard.bought` — credit `event.cost` back (same shape).
- `resources.discarded` — credit the discarded resources back: `nextBank[k] = (bank[k] ?? per) + discarded[k]`.

`bankPerResource` comes from `loadRuleProfile(state.profileId).…` (the reducer already resolves the profile
for S2.2.x logic — reuse it; do NOT hardcode 19). Preserve the existing `bank?` optionality/shape and the
`?? bankPerResource` fallback used at the production gate (`validate.ts:992`) so validate and reduce agree.

**Approach note (surface if you deviate):** credit IN REDUCE from the event's existing `cost`/discarded
payload — this needs NO event-schema change, NO protocol drift-pin, and the SMALLEST re-golden surface
(only STATE changes, events are byte-identical). If you find a build/discard event does NOT already carry
the resources it removed (so reduce genuinely can't derive the credit), STOP + report — do NOT silently add
an event field / protocol change without flagging it (that's the heavier "approach B" and needs a call).

## Out of scope — do NOT change

- **The production all-or-nothing gate** (`validate.ts:992-995`) — its LOGIC is correct-enough and unchanged;
  it will simply trigger far less once the bank conserves. (Refining short-bank partial payout is a separate
  rule nuance, not this fix.)
- **year-of-plenty / monopoly / steal** — already conserve (steal + monopoly move resources player↔player;
  YoP draws FROM the bank). Do NOT touch them.
- **The seed / RNG / commit-reveal / `verify.ts` LOGIC** — the credit is deterministic-from-events; no PRNG
  slot, no verify branch. (verify FIXTURES re-golden like any other — see below — but its recompute logic is
  unchanged.)
- **Any bot code** (`packages/bots`) — S2.4.2 resumes from its parked WIP `5282e93` AFTER this merges.
- **Any profile/preset values** — `bankPerResource` stays 19.

## The re-golden (the real cost — do it HONESTLY, broadly)

Restoring conservation CHANGES the `bank` (and thus full-state) trajectory of **every match that contains a
build or discard**. So EVERY golden / byte-freeze / full-state fixture that captures post-build state must be
regenerated by HONEST REPLAY (fold the UNCHANGED events through the FIXED reduce, capture the new state —
never hand-edit a golden):
- **A2 determinism gate:** `golden.events.ndjson` → regenerate `golden.state.json` (the S1.4.4a conscious
  re-golden pattern); `replay.test.ts` must pass, and a fixture-corruption still fails it.
- **Every `Classic byte-frozen` test** from S2.1.x / S2.2.x that asserts a full post-build state (the flag-off
  baselines). Their PROPERTY still holds — "flag X off == Classic" — but the Classic BASELINE moved (conserved
  bank). Regenerate each baseline; confirm the property (flag-off deep-equals the NEW classic baseline), do
  NOT just make them green.
- Any **server / client** full-match snapshot fixture (e.g. the S1.7.x StateSnapshot / boot round-trip) that
  captures state after builds.
- **Find them all:** grep `golden`, `byte-frozen`/`byteFrozen`, `toEqual`/`toMatchObject` on full `GameState`,
  `.ndjson`/`.json` fixtures. Enumerate the list in your report; a MISSED fixture that still passes is a
  silent bug (it enshrined the old drained-bank state).

## Tests to ADD

- **Conservation invariant (the headline):** for a representative sequence (produce → build road/settlement/
  city → buy dev card → discard on a 7), assert `bank + Σ(all player hands)` is INVARIANT across each
  build/buy/discard step (it was strictly decreasing before). This is the property that proves the fix.
- **No long-match starvation:** a build-heavy scripted sequence that drained the bank to a production-freeze
  BEFORE the fix now keeps the bank replenished and production keeps paying out. (A focused core test — the
  full bot seed-sweep proof lands when S2.4.2 resumes.)
- **Bank never goes negative / stays bounded:** credits + the production gate keep `bank[k]` in `[0,
  bankPerResource]`… — actually assert `bank[k] >= 0` and that total conserved resources == 95 across a match.

## Key decisions (surface any deviation)

1. **Reduce-only, credit-from-existing-payload.** No event-schema / protocol change; smallest re-golden
   (events byte-identical, only state changes). If an event lacks the payload to derive the credit, STOP +
   report (don't silently add a field).
2. **Conservation is now a core invariant.** `bank + Σ(hands)` invariant across build/buy/discard. The added
   test enshrines it so this can never regress.
3. **Honest, broad re-golden.** Every affected golden/byte-freeze fixture regenerated by replay through the
   fixed reduce; the byte-freeze PROPERTIES (flag-off == Classic baseline) must still hold against the NEW
   baseline. A green test that silently kept the old drained-bank golden is a failure — enumerate + verify.
4. **Production gate + YoP/monopoly/steal untouched.** Only the missing credit is added. The all-or-nothing
   gate just triggers less.
5. **Deterministic → no seed/verify-logic change.** The credit derives from event payload; RNG/commit-reveal
   untouched; verify recompute logic unchanged (its fixtures re-golden only).
6. **This is a BUG FIX, not a rule redesign.** `ruleProfile.ts:47` already states the intent (Physical-Catan
   parity); the code just never implemented the refund. No ADR needed. If the worker thinks the finite-bank
   MODEL itself should change (e.g. make the bank infinite), STOP + report — that's a different owner decision;
   this story only restores the refund the stated model already implies.
