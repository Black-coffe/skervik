# S2.5.5 — Matchmaking by mode (quick-match segregates by preset)

## Problem (the exact defect)

The lobby (S2.5.4) lets a human pick a rule preset (`classic` / `balanced` / `blitz` /
`twoPlayer`), and the client forwards it as the `profileId` join option on a quick-match
join (`packages/client/src/net/wsClient.ts:390`, then `client.joinOrCreate(GAME_ROOM_NAME,
options)` at `:402`). But the server registers the room with a plain
`gameServer.define(GAME_ROOM_NAME, GameRoom, …)` — **no `.filterBy(...)`** — at BOTH
registration sites:

- `packages/server/src/index.ts:65` (`createGameServer`)
- `packages/server/src/boot.ts:116` (`createHttpServer` production boot)

Colyseus `joinOrCreate` therefore ignores `profileId` when choosing a room: it seats the
joiner into **any** open public room of that name. Concretely — a player who picks **Blitz**
and quick-matches is seated into an already-open **Classic** room that has a free seat, and
the room runs its own creation `profileId` (`GameRoom.ts:404`, `#profileId = options?.profileId
?? 'classic'`), silently overriding the player's pick. Quick-match does not segregate players
by mode. That's the gap this story closes.

## Goal (terminal, forcing observable)

Two quick-match clients that request **different** `profileId`s land in **different** rooms;
two that request the **same** `profileId` land in the **same** room (subject to the existing
seat cap). No room ever runs a `profileId` other than the one its occupants requested.

## Scope — the fix

**Transport / matchmaking registration only. Do NOT touch `packages/core` or
`packages/protocol`. No new wire fields — `profileId` is already on the wire and already
allow-listed in `onAuth`.**

1. **Attach `.filterBy(['profileId'])` to BOTH `define()` sites.** Colyseus's `define(...)`
   returns a `RegisteredHandler`; chain `.filterBy(['profileId'])` on it. This makes
   `joinOrCreate` only reuse an existing room whose creation `profileId` equals the joiner's
   requested `profileId`; a differing preset spawns a fresh room instead.
   - `packages/server/src/index.ts:65` — `gameServer.define(GAME_ROOM_NAME, GameRoom, …).filterBy(['profileId'])`
   - `packages/server/src/boot.ts:116` — same, on that `define(...)` call.
   Keep the existing conditional-options argument shape (`matchesDir` / `roomOptions`)
   exactly as-is; only append the `.filterBy(...)` chain.

2. **Verify — do NOT modify — the private-room and by-code paths.** Private rooms already
   unlist via `this.setPrivate(true)` (`GameRoom.ts:413`), so `filterBy` never affects them;
   `createPrivate` uses `client.create` and `joinByCode` uses `client.joinById` — neither goes
   through the `filterBy`-gated `joinOrCreate` matching. Confirm this holds; change nothing there.

## Acceptance criteria (each must be a real assertion, not prose)

- **AC1 (segregation — the forcing test):** an e2e (cross-process, real `@colyseus/sdk@0.17`,
  mirror `packages/server/src/e2e/fullMatch.e2e.test.ts` boot + guest flow) where client A
  quick-joins with `profileId: 'classic'` and client B quick-joins with `profileId: 'blitz'`
  asserts **A.roomId !== B.roomId**. Then a client C quick-joins with `profileId: 'blitz'` and
  asserts **C.roomId === B.roomId** (same bucket reuses the room, up to the seat cap).
  Place it in a new `packages/server/src/room/matchmakingByMode.e2e.test.ts` (or extend an
  existing e2e file if cleaner). This test MUST FAIL against the current registration (prove it

  Goal to a terminal observable.
- **AC2 (no preset override):** in the segregation test, read each room's public snapshot /
  `event.batch` and assert the Blitz clients' room actually runs `blitz` (e.g. the
  `match.started` payload's `profileId === 'blitz'`, or a profile-observable public field),
  i.e. the player's pick is honored, never silently downgraded to `classic`.
- **AC3 (existing e2e stays green):** `fullMatch.e2e.test.ts` and `twoPlayerMatch.e2e.test.ts`
  still pass unchanged. NOTE: those tests call `joinOrCreate` WITHOUT a `profileId` (they omit

  match each other — consistent), so they keep sharing one room. Do NOT add `profileId` to those
  tests to "fix" them; they must remain byte-unchanged. If either regresses, STOP and report —

- **AC4 (private/by-code untouched):** `privateRooms.e2e.test.ts` and the ready-up e2e stay

## Notes for the worker

- Colyseus API: `gameServer.define(name, handler, options?)` returns a chainable
  `RegisteredHandler`; `.filterBy(fields: string[])` and `.sortBy(...)` live on it. `filterBy`
  compares the listed keys from the client's join options against the room's stored options at
  matchmaking time. Verify the installed `colyseus@0.17` exposes `.filterBy` on the return of
  `define` (it does in 0.17); if the boot path's `define` return is not captured in a variable,
  just chain inline.
- The real client ALWAYS sends `profileId` (`lobbyStore.selectLobbySelection` always includes
  it), so production quick-match is always keyed; the undefined-bucket only exists for the
  bare-options e2e tests (AC3).
- One branch, one worker, SHARED worktree ([[vulyk-isolation-worktree-stale-base]]); do not
  git-write while the worker runs ([[vulyk-shared-worktree-git-race]]). Conventional commit,
  body ≤100 chars.

## Implementation notes

- `packages/server/src/index.ts` (`createGameServer`) and `packages/server/src/boot.ts`
  (`createHttpServer`): chained `.filterBy(['profileId'])` onto the existing `define(...)`
  call at both sites; the conditional-options argument shape is untouched.
- New `packages/server/src/room/matchmakingByMode.e2e.test.ts` (port 2575, mirrors
  `lobbySelection.e2e.test.ts`/`privateRooms.e2e.test.ts`'s `ColyseusTestServer` +
  `createGameServer()` pattern — lighter than `fullMatch.e2e.test.ts`'s real-HTTP-socket
  boot, and it exercises the same `index.ts` `define()` site). Two tests: (1) classic vs
  blitz quick-match → different `roomId`s; (2) two blitz quick-matches → same `roomId`,
  and `serverRoom.gameState.profileId === 'blitz'` (proves no silent downgrade).
- `gameState.profileId` is only set by the `match.started` event, so test (2) needed the
  room to actually reach genesis. `options.bots` is only read once, in `onCreate` (the
  room-creating join) — a later joiner's `bots` option is ignored. Fix: the FIRST
  (room-creating) blitz join brings 2 bots; combined with the 2 real human joins that's
  exactly 4 seats (the default `maxClients`), firing auto-start without a 3rd/4th human
  socket.
- Proved AC1 fails without the fix: temporarily removed `.filterBy(['profileId'])` from
  `index.ts`, reran the new test file. Both assertions failed as predicted — the blitz
  join was pooled into the open classic room (`classicRoom.roomId === blitzRoom.roomId`)
  and `serverRoom.gameState.profileId` read `'classic'` instead of `'blitz'` — i.e. the
  exact silent-downgrade defect the story describes. Restored the fix; reran green.
