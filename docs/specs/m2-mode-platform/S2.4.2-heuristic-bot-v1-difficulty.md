# S2.4.2 — Heuristic bot v1 (×3 difficulty, shared eval module)

## Goal

Second story of E2.4. S2.4.1 gave `@skervik/bots` the v0 brain (greedy expansion-first `decideAction`) — but
v0 is unscored (hardcoded priority) and NOT seed-robust (it stalls on some seeds — [[v0-seed-fragility-carryforward]]).
This story builds **heuristic bot v1**: a **scored** brain over a **shared weighted-feature EVALUATION module**,
at **×3 difficulty**, seeded-deterministic and **seed-robust** (a bot-fill / single-player bot that can hang is
unshippable).

**Owner-locked difficulty design 2026-07-08 (recommended option "one brain, choice noise"):** ONE weighted-feature
evaluator (the shared module). Difficulty controls the FEATURE SET + the SELECTION among scored moves:
- **Hard** — full feature set (ports, dev-card value, blocking, VP-proximity); picks the **best-scored** move
  (deterministic argmax; no noise).
- **Medium** — full feature set; picks the top move but with **light noise** (occasionally the 2nd-best).
- **Easy** — **reduced** feature set (ignores ports / dev-card value / blocking); picks a **random move from the
  top-K** (large noise) → looks human, plays weaker.

Noise comes from a **seeded bot PRNG** that is **independent of the match seed** (the bot is seed-BLIND to the
match — it can't predict rolls; it uses its OWN seed only for tie-break/exploration noise, so tests stay
deterministic).

**Two hard requirements (NOT design choices — mandatory):**
1. **Shared eval module.** The board/action scoring lives in its OWN module (`packages/bots/src/eval/`), consumed
   by the v1 brain now and the M4 E4.8 advisor later (owner directive — "bot and advisor share one brain, don't
   bury scoring in the decision loop").
2. **Seed-robustness (fixes the v0 stall).** v1 must always make progress: roads only toward open settlements, a
   bank-trade-toward-the-cheapest-target fallback, `endTurn` as the ultimate always-legal move → it can never
   have zero options and can't spin. Proven by a **seed-sweep test** (20–50 diverse seeds × all 3 difficulties,
   all reach `game.ended` within the harness cap).

**v0 stays FROZEN.** The bare `decideAction` (v0) export is the S1.7.2 E2E determinism driver (via the server
re-export shim) — do NOT change it. v1 is added ALONGSIDE; `createHeuristicBot` switches to v1. (Migrating the
E2E onto v1 is a deferred cleanup — keep the M1 gate stable.)

## Mechanic (precise)

### The shared evaluation module (`packages/bots/src/eval/`)
Pure, stateless, reusable. Separate the FEATURES from the WEIGHTS from the SELECTION:
- **`features.ts`** — pure feature extractors over `(state, playerId, ...)`:
  - `pipWeight(token: number): number` — the 2d6 frequency table (7→6, 6/8→5, 5/9→4, 4/10→3, 3/11→2, 2/12→1,
    desert/7-token→0). **Hardcode it** (core exposes no pip helper — scout Area 4).
  - `vertexProductionValue(state, vertexId)` — Σ over the vertex's adjacent tiles of `pipWeight(token)` weighted
    by resource scarcity/diversity (a settlement/city spot's raw worth). Reuse `findVertex(TOPO, v).adjacentTileIds`
    → `state.board.tileKinds`/`tileTokens`.
  - `resourceDiversity`, `portAccess` (extract v0's `ownedPortContents` logic into a shared `portsOwnedBy`
    helper), `handUtility`, `vpProximity(computePublicVictoryPoints)`, `blockingValue` — each a small pure fn.
- **`evaluate.ts`** — combines features with a WEIGHT profile:
  - `evaluateVertex(state, playerId, vertexId, weights): number` — settlement/city placement score (used in BOTH
    setup and main phase — one scorer, two call sites).
  - `evaluateAction(state, playerId, action, weights): number` — score a candidate main-phase action (build
    settlement/road/city, bank-trade, buy dev card, end turn).
  - `FEATURE_WEIGHTS: Record<Difficulty, Weights>` — `hard`/`medium` = full weights; `easy` = reduced (zero the
    port/dev-card/blocking weights so easy plays "naively").
  - Return a `{score, features}` shape (the `features` breakdown is diagnostic — the M4 advisor surfaces it as
    "why this spot"; don't discard it).

### The v1 brain (`packages/bots/src/heuristic/v1.ts`)
`decideV1(state, playerId, difficulty, rng): PlayerIntent | null` — phase dispatcher mirroring v0's structure,
but scored where strategy lives:
- **setup phase** — generate all legal settlement vertices → `evaluateVertex` → `selectByDifficulty`; then the
  legal road (v0's toward-just-placed-settlement rule). (v0 picked first-buildable; v1 scores the spot — the
  single highest-value strategic upgrade.)
- **roll phase** — roll (trivial, unchanged).
- **main phase** — GENERATE the candidate action set (buildable settlements [scored via `evaluateVertex`],
  roads-toward-open-settlement [v0's constraint — MANDATORY for termination], city upgrades [scored], viable
  bank-trades-toward-the-cheapest-reachable-target, optionally buy-dev-card, and ALWAYS `endTurn`) →
  `evaluateAction` each → `selectByDifficulty`. **Termination guards (from the scout, mandatory):** roads must
  only extend toward an open settlement (never dead-end); settlement must out-score city while production is the
  bottleneck (early game) — encode a production-bottleneck term so v1 doesn't over-upgrade and starve; the
  bank-trade fallback guarantees progress when nothing is directly affordable.
- **discard phase** — v0's largest-first is fine (keep it; not a strategy lever worth scoring in v1).
- **robber phase** — score victims by public VP (steal from the leader), RESPECTING `isStealable` (friendlyRobber
  gate) + move the robber to the highest-value blocked tile. (v0 picked first victim; v1 scores it — reuse the
  eval's `blockingValue`.)

### Difficulty selection (`selectByDifficulty`)
`selectByDifficulty(scored: {action, score}[], difficulty, rng): action`:
- **hard** — argmax (deterministic; ties broken by a stable deterministic key, NOT the rng).
- **medium** — softmax/top-K with a SMALL temperature: usually the best, occasionally the 2nd (rng draw).
- **easy** — uniform (or lightly weighted) pick from the top-K (e.g. top 25% or top-3), LARGE noise; combined with
  the reduced `easy` feature weights.
- Noise draws come from the **bot's** `rng` (below), never the match seed.

### The bot PRNG (`packages/bots/src/rng.ts` or inline)
A tiny stateful wrapper over core's `deriveValue(botSeed, counter++)` (core exports no stateful PRNG — scout Area
5): `BotRng { next(): number; pick<T>(items, weights?): T }`. Constructed with the bot's OWN `seed` (from
`BotOptions.seed`, defaulting to a fixed constant so a no-seed bot is still deterministic). **This seed is NOT the
match seed** — the bot never receives the match seed (authoritative-server invariant).

### `createHeuristicBot` (bot.ts) — the difficulty seam
```
export type Difficulty = 'easy' | 'medium' | 'hard';
export interface BotOptions { difficulty?: Difficulty; seed?: Seed; }  // difficulty default 'medium'
export function createHeuristicBot(opts?: BotOptions): Bot;             // id = `v1-${difficulty}`; decide = v1
```
`decide(state, playerId)` stays `(state, playerId)` only (NO match-seed param — invariant); difficulty + botRng
are captured in the closure at construction. The bare `decideAction` (v0) export is UNCHANGED.

## Seed-robustness (the mandatory anti-stall)

- **Always a legal move:** the main-phase candidate set ALWAYS includes `endTurn`; setup always has ≥1 legal
  settlement; so `decide` never returns `null` on a live turn where an action is required, and never has an empty
  scored set.
- **Always progress when possible:** the bank-trade-toward-cheapest-target candidate means a resource-rich but
  build-blocked bot converts surplus → the missing resource → builds next turn (this is what v0 lacked — it
  couldn't dig out of a starved position).
- **Seed-sweep test:** `simulateMatch` over 20–50 DIVERSE seeds (hand-picked + `deriveValue`-generated, NOT one
  lucky string) × the 3 difficulties (or a representative mix) → EVERY run reaches `phase:'finished'` within the
  default cap. If a seed stalls, the harness throws loudly (S2.4.1) — that's a FAILING test to fix, not a skip.
  Document any genuinely pathological seed (log it), never silently skip.

## Key decisions (surface any deviation)

1. **One eval module, difficulty = feature set + selection noise** (owner-locked). Not lookahead, not 3 separate
   brains. The eval is the shared M4-advisor brain; `selectByDifficulty` + the per-difficulty weight profiles are
   the difficulty layer.
2. **Bot is seed-BLIND to the match; noise uses an independent bot seed.** `decide` has no match-seed param; the
   BotRng seed is the bot's own. This preserves the authoritative-server invariant AND keeps tests deterministic.
3. **v0 stays frozen; v1 is additive.** The S1.7.2 E2E imports v0 `decideAction` (unchanged) → gate byte-green.
   `createHeuristicBot` switches to v1. Two brains coexist by design (v0 = the frozen test driver, v1 = the ship
   bot).
4. **Seed-robustness is mandatory, proven by a seed-sweep.** Roads-toward-open-settlement + bank-trade fallback +
   always-`endTurn` ⇒ no stall. If v1 still stalls on a swept seed, that's a blocking bug (the whole point of this
   story is to fix the v0 stall) — do NOT paper over it with a one-seed test.
5. **Provisional weights + strength signal.** The exact feature weights are tunable; the test asserts a MATERIAL
   (not exact) hard-≥-easy strength trend over N seeds, so it's not flaky. Flag the weights as provisional.
6. **Profile-aware, not Classic-hardcoded.** Costs/supplies/`catchUp` come from `loadRuleProfile(state.profileId)`;
   robber victim scoring respects `isStealable` (friendlyRobber). Works for all presets.
7. **Setup placement IS scored (high-value, same scorer).** `evaluateVertex` serves both setup and main settlement
   placement — including it is a clean reuse, not scope creep, and it's where most bot skill lives. If it balloons,
   fall back to scoring main-phase only + v0's setup, and flag it.
