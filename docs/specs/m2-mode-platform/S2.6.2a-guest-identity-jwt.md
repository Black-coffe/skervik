# S2.6.2a — Durable guest identity + signed JWT session tokens

Today guest identity is anonymous, in-memory, and display-only (`InMemoryGuestStore` mints a fresh
`randomUUID` each call; it evaporates on restart; the room ignores it — PlayerId is the Colyseus
`sessionId`). This story makes a guest a **durable `users` row** and issues a **signed session
token (JWT, HS256, `jose`)** that lets the same guest re-resolve their identity across reconnect and
page reload — the M2-critical "accounts (guest)" gate item — WITHOUT changing in-game identity.

**OUT OF SCOPE (do NOT build — later stories):** OAuth/Google/Discord + guest-upgrade (S2.6.2b);
writing `match_players.user_id` / match-history attribution (S2.6.3); changing the authoritative
in-game `PlayerId` (stays the seat `sessionId`, ADR-0009 — untouched); token revocation/refresh
(post-M2). This story makes the durable `userId` verifiable and available; consuming it for match
attribution is S2.6.3.

## Design decisions (locked — implement as stated)

- **JWT via `jose` (HS256).** Framework-agnostic sign/verify (used at both the Fastify route and the
  Colyseus `onAuth` seam). Payload claims: `sub` = the durable `userId` (the `users.id`), `name` =
  `displayName`, plus `iat`/`exp` (e.g. 30-day expiry). NO sensitive data in the token. Symmetric
  HS256 with a server secret — sufficient for guest sessions; S2.6.2b revisits for OAuth.
- **Secret from `SESSION_SECRET` env; ephemeral fallback.** If `SESSION_SECRET` is set, use it. If
  ABSENT, generate an ephemeral per-boot secret (`randomBytes(32)`) and `console.warn` that tokens
  won't survive a restart and prod MUST set `SESSION_SECRET`. Never a hardcoded default. Tests inject
  a fixed secret. Document `SESSION_SECRET` as mandatory for prod (alongside `DATABASE_URL`/`MATCHES_DIR`).
- **`guestId` becomes the durable `userId` when DB-backed.** `DbGuestStore.issueGuest` inserts a
  `users` row (id = app-generated uuid, `is_guest=true`, `auth_provider='guest'`) and returns
  `guestId = users.id`. The `InMemoryGuestStore` (no `DATABASE_URL`) is unchanged → no regression.
- **Provided-but-invalid token → REJECT the join.** A `sessionToken` that is present but fails
  verification (bad signature / expired / malformed) rejects the connection with a new
  `ServerError(AUTH_TOKEN_INVALID_CODE = 4004, ...)`. An ABSENT token proceeds as a fresh guest
  (backward compatible). Never silently downgrade a bad token — that would mask tampering.

## Scope — build exactly this

### A. Schema evolution (additive migration 0001)
- Add `display_name text` (not null) to `packages/server/src/db/schema/users.ts`. Rationale: the shown
  name is user-chosen and NON-unique; `username` stays the UNIQUE handle. For guests, `username` is a
  generated unique slug (e.g. `guest_${id}` or `guest_${randomHex}` — MUST satisfy the unique
  constraint; on the astronomically-unlikely collision, regenerate), `display_name` holds the
  sanitized chosen/generated name (reuse the existing `sanitizeDisplayName`/`generateGuestName` logic).
- `pnpm --filter @skervik/server db:generate` → produces `migrations/0001_*.sql` (additive). COMMIT it.
  Do NOT hand-edit `0000_*` (Invariant 3). `UserRepository.create` gains `displayName`; add a
  `findById`-style read that returns it.

### B. JWT helpers (`packages/server/src/auth/sessionToken.ts`)
- `signSessionToken(payload: { userId: string; displayName: string }, secret: Uint8Array, opts?): Promise<string>`
  and `verifySessionToken(token: string, secret: Uint8Array): Promise<{ userId: string; displayName: string } | null>`
  (returns `null` on any verification failure — caller decides reject-vs-ignore). Use `jose`'s
  `SignJWT` / `jwtVerify`. Pure over the secret (injectable for tests).
- A `resolveSessionSecret(env): Uint8Array` helper: `SESSION_SECRET` → bytes; absent → `randomBytes(32)`
  + warn.

### C. `DbGuestStore` (`packages/server/src/auth/dbGuestStore.ts`)
- Implements `GuestStore` over `UserRepository`. `issueGuest(displayName?)` → insert users row →
  return `{ guestId: users.id, displayName }`. Constructed with a `UserRepository` (which wraps the
  `db` client). Add an `async issueGuest` note: `GuestStore.issueGuest` is currently SYNC — widen the
  interface to `GuestIdentity | Promise<GuestIdentity>` (mirror the `MatchMetadataStore` sync|async
  precedent) so a DB insert fits; update the route + callers to `await`.

### D. `/auth/guest` route returns the token (`routes/guestAuth.ts`)
- After `issueGuest`, sign a session token for `{ userId: guestId, displayName }` and return
  `{ guestId, displayName, sessionToken }`. The route gains access to the signer (inject a
  `signToken` fn or the secret alongside the store).

### E. Protocol — accept `sessionToken` on join (`packages/protocol/src/messages.ts`)
- Add `sessionToken: z.string().optional()` to `ConnectOptionsSchema` (messages.ts:662). It is then
  automatically permitted by `JoinOptionsSchema.strict()` (messages.ts:740) — verify the strict
  allow-list now accepts it (add a test). Drift-pins intact.

### F. `onAuth` — verify the token (`GameRoom.ts` onAuth ~:773)
- New `AUTH_TOKEN_INVALID_CODE = 4004` (4000-4999 range, distinct from 4001/4002/4003).
- After the existing version + lobby + allow-list gates: if `sessionToken` is present, `verifySessionToken`
  it; `null` → `throw new ServerError(4004, ...)`. On success, attach the resolved `userId` to the
  client for downstream use — `client.userData = { userId }` (Colyseus's per-connection bag). Absent
  token → proceed (no userData / fresh guest downstream). The room needs the secret + verify fn injected
  (a `GameRoomOptions.verifySessionToken?` seam, defaulting to a no-op that treats any token as absent
  when auth isn't configured — keeps test rooms that don't exercise auth unchanged).
- **DO NOT change PlayerId / seat identity** (still `sessionId`). `client.userData.userId` is metadata
  for S2.6.3; it does not become the seat id.

### G. Boot wiring (`boot.ts`)
- Read `DATABASE_URL` (new) + `SESSION_SECRET` (new) in `startServer` (~:184, alongside PORT/HOST/MATCHES_DIR).
- `createHttpServer` options gain `databaseUrl?` + `sessionSecret?` (test seams). When `databaseUrl` is
  present: build a `db` client (`createPgDb`), a `UserRepository`, a `DbGuestStore`, and pass a
  `verifySessionToken` bound to the resolved secret into the room define options. When ABSENT: today's
  `InMemoryGuestStore` + no token verification (bad tokens simply ignored — but the route still issues
  in-memory-guest tokens signed with the ephemeral/real secret, so the loop still works in-memory).
- **No auto-migrate on boot** (Invariant 4) — operator runs `pnpm --filter @skervik/server migrate`.

### H. Client — persist + resend the token (`packages/client/src/net/`)
- `guestAuth.ts` `fetchGuest` result type gains `sessionToken`; on a successful fetch, persist it
  (extend `reconnectToken.ts`'s storage pattern — a stable `localStorage`/`sessionStorage` key, matching
  how `currentRoomId`/`reconnectionToken` are stored). On a cold load, read the stored token and pass it
  as a join option; `fetchGuest` is only called when no stored token exists (or it's rejected).
- `GuestJoinFields` (wsClient.ts:284) + `connect()` (wsClient.ts:388) gain `sessionToken?`, spread into
  join options exactly like `guestId`/`displayName`. This is the last, most separable scope item — if
  the worker is truncated, THIS is the tail to finish on resume (server A–G is the security-critical core).

## Acceptance criteria (real assertions; forcing where noted)

- **AC1 (durable guest, DB-backed):** with a PGlite-backed `DbGuestStore` (migrations run incl. 0001),
  `issueGuest('Alice')` inserts a `users` row (`is_guest=true`, `auth_provider='guest'`,
  `display_name='Alice'`, unique `username`), and `guestId === users.id`. A second `issueGuest('Alice')`
  yields a DIFFERENT `userId` and a distinct unique `username` (display names may collide, handles never).
- **AC2 (token round-trips):** `verifySessionToken(signSessionToken({userId, displayName}, secret), secret)`
  returns `{userId, displayName}`; a token signed with a DIFFERENT secret → `null`; a tampered/expired
  token → `null`.
- **AC3 (onAuth rejects a bad token — FORCING, real socket):** an e2e (real `@colyseus/sdk`, mirror
  `boot.test.ts`) where a client joins with a garbage `sessionToken` is REJECTED with code/reason
  `AUTH_TOKEN_INVALID` (4004); a client joining with a VALID token (from a prior `/auth/guest`) joins
  successfully and its `client.userData.userId` equals the token's `userId`; a client with NO token
  joins successfully as before. This binds the security boundary to a terminal observable.
- **AC4 (end-to-end durability):** `POST /auth/guest` returns `{guestId, displayName, sessionToken}`;
  re-presenting that `sessionToken` on a fresh join resolves the SAME `userId` (proves reload-survival).
- **AC5 (no regression):** with NO `DATABASE_URL`, the server boots on `InMemoryGuestStore` and every
  existing test (server 156, incl. boot/e2e/matchmaking) passes unchanged; in-game `PlayerId` semantics
  and the intent pipeline are byte-unchanged; `packages/core` git-byte-unchanged + zero-dep guard passes;
  `packages/protocol` change is limited to the additive `sessionToken` field (drift-pins intact).

## Security review focus (for /security-review before merge)
- HS256 secret never logged, never in a client-visible payload, never a hardcoded default; ephemeral
  fallback is documented + warned. Token carries only `userId`/`displayName`/`iat`/`exp` — no secrets.
- Provided-but-invalid token is REJECTED, not downgraded. Absent token = anonymous (intended).
- `client.userData.userId` is NON-authoritative metadata; the seat/PlayerId is still `sessionId`, so a
  forged/replayed token cannot impersonate another player's MOVES (it could at most re-attach a display
  identity — acceptable for M2 guests; note it explicitly). No SQL injection surface (Drizzle
  parameterized; `username`/`display_name` are inserts, not interpolated).
- `display_name` is sanitized (control-char strip, length clamp) before storage (reuse existing helper).
