# S2.1.5 — Parallel phases: concurrent trade offers (+ confirm parallel discard)

## Goal

Realize the anti-"dead time" rule — *"no dead time: parallel phases"* (CLAUDE.md · roadmap
principle 4) — for the trade phase. Today the engine allows exactly **one open trade offer at a
time** (`openTradeOffer?: TradeOffer`, `validate` rejects `TRADE_OFFER_ALREADY_OPEN`). S2.1.5 lets a
match run **multiple concurrent open offers** — gated by a new `parallelTrade` profile flag — so
negotiation isn't a one-at-a-time bottleneck. **Discard is already fully parallel** (all
`playersToDiscard` owers may discard in any order, `#queue`-serialized) — S2.1.5 CONFIRMS that with a
test and adds NO discard change.

**Two load-bearing constraints.** (1) **Classic stays byte-frozen**: with `parallelTrade:false` (every
shipping preset today) the engine behaves EXACTLY as M1 — one offer, `TRADE_OFFER_ALREADY_OPEN`
enforced, the singular `openTradeOffer` field and the client untouched. (2) The parallel path is
**purely ADDITIVE and gated** — a separate `openTradeOffers` collection used ONLY when the flag is on,
so the shipped single-offer path carries zero risk. Trade is not seed-derived, so there is **no RNG,
no `verify` change**; and the golden fixtures never reach the trade phase, so shape changes are
golden-safe.

## What to build

### 1. The `parallelTrade` profile flag (core)
Add a top-level boolean `parallelTrade` to `RuleProfile` (following the `randomness` flag pattern,
`ruleProfile.ts`), resolved via `loadRuleProfile(state.profileId ?? 'classic')`:
- **`false` on CLASSIC / BALANCED / BLITZ** (all shipping presets) — the M1 single-offer behavior,
  byte-frozen. **Do NOT enable it on a shipping preset in this story** — a mode that opens multiple
  offers the client can't yet render would be a broken UX (the client multi-offer HUD is deferred).
  Its liveness is proven by a **test-only `parallelTrade:true` profile** (the S2.1.1 Blitz-`vpToWin`
  precedent — prove the config path without shipping the mode).
- Documented as: enabling on a real preset (likely Blitz, for pace) is a one-line follow-up **once the
  multi-offer client HUD exists**.

### 2. Additive multi-offer state (core, `types.ts`)
- Keep **`openTradeOffer?: TradeOffer` UNCHANGED** (the non-parallel path + what the client reads —
  byte-frozen).
- Add **`openTradeOffers?: readonly TradeOffer[]`** — used ONLY when `parallelTrade:true`. At most **one
  open offer per proposer** (keyed by `proposerId`, which is already unique per offer — no new id
  generation, no determinism risk). The two fields are **mutually exclusive by the flag** (a match is
  either single-offer or parallel), so there is no ambiguity.
- The trade-response intents (`acceptTrade`/`rejectTrade`/`counterTrade`/`cancelTrade`) gain an
  **optional `offerProposerId`** (append-compatible) to name WHICH offer they act on in parallel mode;
  in single-offer mode it is ignored/defaults to the sole offer (M1 intents stay valid).

### 3. Gate validate + reduce on the flag (core)
- **`validate` (`validate.ts:1416–1539`):** branch on `parallelTrade`.
  - **false →** the CURRENT logic verbatim (byte-frozen): `TRADE_OFFER_ALREADY_OPEN` if `openTradeOffer`
    set; accept/reject/counter/cancel operate on the sole offer.
  - **true →** allow one open offer **per proposer** concurrently; `proposeTrade` rejects only if THAT
    proposer already has an open offer (not a global "already open"); accept/reject/counter/cancel
    resolve the offer by `offerProposerId`; the **per-offer `depth` counter-limit (0→1)** applies
    independently per offer; affordability is re-checked at accept time (already the case — `validate`
    runs against committed state, so an offer made unaffordable by an intervening swap simply fails to
    execute, never a stale swap).
- **`reduce` (`reduce.ts:476–540`):** branch on the flag.
  - **false →** current mutations verbatim (single `openTradeOffer`).
  - **true →** maintain the `openTradeOffers` list: `trade.offered` adds/replaces the proposer's entry;
    `trade.executed` removes that proposer's entry + performs the SAME atomic both-hands swap;
    `trade.rejected` updates that offer's `targets` (or removes it when empty); `trade.cancelled`
    removes it. **`turn.ended` clears ALL open offers** (both fields) — trades never persist across
    turns (matches the M1 defensive drop).
- **Contract unchanged:** `reduce(state,event)` / `validate(state,intent,playerId,seed)` signatures are
  LOCKED — the flag flows via `state.profileId`, never a new positional arg.

### 4. Confirm parallel discard (core — NO behavior change)
Discard is already order-independent + concurrent (`playersToDiscard` carve-out; `#queue`-serialized;
robber-move blocked until every ower has discarded). Add/point to a test asserting **N owers discard in
any order concurrently** and do NOT add a `parallelDiscard` flag — a "sequential discard" mode is not a
requirement (VULYK Law 2: no flag whose off-behavior must be newly built for no demand).

## Scope — build THIS, defer the rest

**Build:** the `parallelTrade` flag (off on presets, a test-true profile); the additive
`openTradeOffers` collection + optional `offerProposerId` on response intents; the flag-gated
validate/reduce branches (Classic verbatim / parallel per-proposer); the parallel-trade test suite +
the parallel-discard confirmation test; exports if any new type escapes. Core-only (+ nothing else).

**DEFER — do NOT build here:**
- **Client multi-offer HUD rendering** — the client reads the singular `openTradeOffer`
  (`TradeZone.tsx`, `store.ts` selectors); rendering 2+ concurrent offers is a HUD story. S2.1.5 makes
  NO client change; because no shipping preset enables the flag, the client never encounters the new
  field. Enabling `parallelTrade` on a preset is coupled to that HUD.
- **The full MARKETPLACE (non-current players PROPOSING new offers)** — S2.1.5 keeps M1 proposer
  semantics (the current player proposes; a counter still makes the countering player the proposer, as
  today). Letting any player originate an offer during another's turn changes turn authority — an
  OWNER product decision, its own story. Flag it, don't build it.
- **Retiring the singular `openTradeOffer`** — a cleanup once the multi-offer client lands (record as a
  carry-forward).
- Any `verify`/RNG change (trade isn't seed-derived), any Classic rule-value change, any server pipeline
  change (`#queue` already serializes concurrent offers — no new concurrency machinery).

## Key decisions (surface any deviation)

1. **Additive `openTradeOffers` behind the flag — NOT a rename of `openTradeOffer` to a collection.**
   Why: the additive path leaves the shipped single-offer path (validate/reduce/tests AND the client)
   100% untouched and byte-frozen, isolating all new behavior behind `parallelTrade`. A rename would
   force client-selector churn + reshape every existing trade test for zero benefit while the flag is
   off everywhere. Cost: two fields for one concept — mitigated by mutual exclusivity (the flag) and a
   documented cleanup (retire the singular field when the multi-offer client ships).
2. **Offers keyed by `proposerId`, one open offer per proposer.** Why: `proposerId` is already unique
   per offer — no id generation (which would need determinism care), a clean per-proposer cap prevents
   spam, and counters (which re-proposer to the countering player) slot in naturally. Response intents
   name the offer via `offerProposerId`.
3. **Flag OFF on all shipping presets until the client can render multi-offer.** Why: shipping a mode
   that opens offers the UI can't show is a broken UX; the flag's liveness is proven by a test profile
   (S2.1.1 precedent). Enabling it on Blitz/etc. is a one-line follow-up post-HUD.
4. **Parallel discard already satisfied — no flag, no change.** Why: it's order-independent +
   `#queue`-safe today; a `parallelDiscard:false` mode would require building sequential discard nobody
   asked for (Law 2). S2.1.5 only CONFIRMS it with a test.
5. **Marketplace (non-current proposing) deferred as an owner decision.** Why: it changes who holds
   turn authority — a product-feel decision beyond a config knob; S2.1.5 keeps M1 proposer semantics.
6. **No ADR needed** — "profiles as config" + atomic-swap are locked; this is their application. Flag
   for an ADR only if the two-field transitional shape proves contentious in review.
