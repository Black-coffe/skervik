# S2.3.2a — Resume on load (a page reload reconnects to the held seat)

## Goal

Follow-up to S2.3.2. S2.3.2 made an IN-TAB socket blip recover (the JS closure survives, `onLeave` fires,
`client.reconnect(token)` runs). But a **PAGE RELOAD** destroys the closure — `onLeave` never fires, and
`connect()` always does a fresh `joinOrCreate`, so the persisted `reconnectionToken` is never read in
production (it is write-only — S2.3.2 lead-review nit #1). This story makes reload-resume actually work: on a
cold load, `connect()` finds the persisted token and calls `client.reconnect(token)` BEFORE `joinOrCreate`, so
a reload within the S2.3.1 grace window rejoins the held seat and the server's existing resync unicast
(S2.3.2) restores a consistent board. It also widens the reconnect retry budget (nit #2) so a typical outage —
not just a sub-second blip — recovers.

**What makes this work (scout-confirmed):** `client.reconnect(token)` is **self-contained** — the token
encodes the room + seat, so NO `roomId` is needed to reconnect. The ONLY missing pieces are: (1) the app never
records WHICH roomId is current, so a cold load can't locate the token in the roomId-keyed store; (2) `connect()`
has no resume-first branch. Both are small, client-only. The server side (hold + reclaim + resync unicast) is
already done in S2.3.1/S2.3.2 — **NO server change**.

## What to build (all in `packages/client`, + tests)

### 1. Persist the "current room" pointer so a cold load can find the token
S2.3.2 stores the token as `sessionStorage['skervik:reconnect:{roomId}']` — but a cold-loaded app doesn't know
the `roomId`. Add a small **current-room pointer** so resume-on-load can resolve token→reconnect:
- On a successful join (in `connect()`, right after `joinOrCreate` returns and the existing token persist),
  ALSO persist the current `room.roomId` under a FIXED sessionStorage key (e.g.
  `skervik:reconnect:current-room`). Extend `reconnectToken.ts` with `persistCurrentRoomId(roomId)` /
  `readCurrentRoomId()` / `clearCurrentRoomId()` (mirror the existing guarded-no-op-without-sessionStorage
  pattern). Per-tab (sessionStorage) — one active match per tab, so a single pointer is correct (Key decision 1).
- **Clear** the pointer (+ the roomId-keyed token) on a clean game end / consented `disconnect()` so a reload
  AFTER the match won't try to resume a finished seat.

### 2. Resume-first branch in `connect()` (the seam @ `wsClient.ts:249-251`)
Between `new Client(url)` (249) and `joinOrCreate(GAME_ROOM_NAME)` (251):
```
const client = new Client(url);
const savedRoomId = readCurrentRoomId();
const savedToken = savedRoomId ? readReconnectionToken(savedRoomId) : null;
if (savedToken) {
  try {
    const room = await client.reconnect(savedToken);   // token self-contained; server resends the snapshot
    // wire it exactly like a fresh join (attachRoom + status 'connected'); the server's reclaim
    // unicast (S2.3.2) delivers the fresh StateSnapshotMessage → the store folds it → consistent board.
    return <handle>;
  } catch {
    clearCurrentRoomId(); clearReconnectionToken(savedRoomId);   // token expired / grace ran out
    // fall through to a fresh joinOrCreate below
  }
}
const room = await client.joinOrCreate(GAME_ROOM_NAME, {...});   // unchanged
```
- On resume SUCCESS: wire the reconnected room through the SAME `attachRoom(...)` path a fresh join uses (so
  sync handlers + the `ReconnectCapability` + the stable-handle indirection from S2.3.2 all apply), set status
  `'connected'`, and return the handle. Do NOT also `joinOrCreate`.
- On resume FAILURE (token invalid / grace expired): clear the pointer+token and fall through to the existing
  `joinOrCreate` (a fresh seat — the old held seat is bot-filled/left by S2.3.3; not this story's concern).
- Keep the resync race mitigation intact: attach the `state.snapshot` handler synchronously before the server's
  reclaim unicast can arrive (the S2.3.2 pattern — reuse `attachRoom`, don't hand-roll).

### 3. Widen the retry budget (nit #2)
`DEFAULT_RECONNECT_MAX_ATTEMPTS = 3` + `DEFAULT_RECONNECT_BACKOFF_MS = [250, 750]` (`wsClient.ts:93-94`) totals
~1s — far short of the 120s server grace, so most real outages give up while the server still holds the seat.
Widen to a BOUNDED budget that spans a useful fraction of grace (e.g. ~8 attempts with capped exponential
backoff totalling on the order of ~20-40s — worker picks concrete values; MUST stay well-bounded, NOT hammer
for the full 120s, and NOT block the UI). Applies to the in-tab `attemptReconnect` path; the cold-load resume
is a single `reconnect()` attempt (a reload already happened — no retry loop needed there, just success/fallback).

### 4. Tests (the FORCING criterion — prove reload-resume actually works)
In `packages/client/src/net/wsClient.test.ts` (+ `reconnectToken.test.ts`):
- **[MUST — the anti-write-only guard] Cold-load resume:** with a mock sessionStorage pre-seeded with a
  `current-room` pointer + a matching token, calling `connect()` at COLD START calls `client.reconnect(token)`
  (NOT `joinOrCreate`), wires the reconnected room, and a subsequent `state.snapshot` folds into the store
  (board consistent). This test is the acceptance gate — it proves the token is READ + USED in the production
  `connect()` path, not merely persisted.
- **Cold-load fallback:** with a pointer+token present but `reconnect()` rejecting (expired), `connect()` clears
  the pointer+token and falls through to `joinOrCreate` (fresh join), status ends `'connected'`, no crash.
- **No pointer → plain join:** with empty sessionStorage, `connect()` goes straight to `joinOrCreate`
  (unchanged behavior — no regression).
- **Pointer persisted on join + cleared on game-end/consented-disconnect.**
- **Widened retry:** the in-tab `attemptReconnect` honors the new bounded budget (assert attempts/backoff),
  still terminates to `'disconnected'` on exhaustion.

## Key decisions (surface any deviation)

1. **A single fixed "current-room" pointer (per-tab), not a scan of all `skervik:reconnect:*` keys.** One active
   match per tab (sessionStorage is per-tab), so a single `current-room` pointer is unambiguous and cheap.
   **Rejected: scanning all reconnect keys** — fragile (which one? most-recent by what clock?) and pointless
   for a one-match-per-tab model.
2. **Resume is a single attempt on cold load; the retry LOOP stays on the in-tab path.** A reload already spent
   the round-trip; `connect()` tries `reconnect(token)` once and falls back to `joinOrCreate` on failure. The
   widened retry budget (nit #2) applies to the LIVE in-tab drop (`attemptReconnect`), where retrying a
   transient blip makes sense.
3. **Token self-contained → no roomId needed to reconnect; the pointer only LOCATES the token.** Confirmed by
   the scout (`client.reconnect(token)` takes only the token). The `current-room` pointer exists solely so the
   cold app can find the roomId-keyed token entry — it is not passed to `reconnect`.
4. **Client-only; the server already does the hard part.** Hold (S2.3.1) + reclaim + resync unicast (S2.3.2)
   fire on ANY reconnect the server detects, including a cold-load one. So this story adds ZERO server code.
5. **The Goal has a forcing test (anti-regression on the S2.3.2 lesson).** [[spec-goal-must-match-acceptance-criteria]]:
   the cold-load resume test is an ACCEPTANCE CRITERION, not optional — it proves the token is read+used in
   the real `connect()` path, so reload-resume can't ship as write-only scaffolding again.
