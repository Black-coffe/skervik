# S2.3.2 — Full state resync (client reconnects within grace, server pushes the missed state)

## Goal

Second story of E2.3. S2.3.1 made the SERVER hold a dropped seat for a grace window; but the CLIENT still has
no way to come back — there is no `client.reconnect(token)` call and no token persistence anywhere (scout:
"client reconnect scaffolding = NONE"). This story closes the loop: on an unexpected drop the client persists
its `reconnectionToken`, reconnects within grace, re-attaches its sync handlers, and the server **unicasts a
fresh authoritative snapshot** to that one client so the board it renders is consistent with the game that
kept moving while it was away (forced defaults advanced its turns per S2.3.1). The result: a real network blip
or page reload no longer costs you the game — you rejoin your seat mid-match.

**What resync IS (locked by the invariants):** the server already mints a `StateSnapshotMessage` (full
`PublicGameState`, NO seed) and sends it on a fresh join (`GameRoom.ts:617-622`). Colyseus does NOT call
`onJoin` on a reconnect (it takes the `onReconnect` path), so the reclaimed client would otherwise get only
the auto-re-synced Colyseus `RoomSchema` projection, NOT the authoritative core `gameState` (which the client
reconstructs from snapshot+batches). So S2.3.2 sends the SAME snapshot again, **unicast**, at the S2.3.1
reclaim seam (`GameRoom.ts:656-659` `.then()`). The client folds it through the isomorphic core `reduce` (the
existing `state.snapshot` handler + store fold) to reset to authoritative state. **No new protocol message, no
seed exposure, no server `gameState` mutation, no new event** — resync is transport + a state-projection reuse.

**Scope of THIS story = the client reconnect wiring + the server reclaim-branch unicast + tests.** NO bot-fill
on expiry / deliberate safe-leave (S2.3.3); NO net-new grace-countdown banner (reuse the existing
ConnectionIndicator — Key decision 4); NO core / protocol-message change.

## What to build

### 1. Server: unicast a fresh snapshot at the reclaim seam (small)
In `GameRoom.ts`, the S2.3.1 `onDrop` reclaim branch (`~656-659`):
```
this.allowReconnection(client, this.#reconnectGraceSeconds)
  .then(() => {
    if (seat) seat.connected = true;
    // S2.3.2: unicast a fresh authoritative snapshot to THIS reclaimed client
    this.#sendSnapshot(client);   // reuse the exact join-snapshot minting (617-622)
  })
```
- **Reuse the existing join-snapshot logic** (`GameRoom.ts:617-622`): extract a private `#sendSnapshot(client)`
  helper that mints a `StateSnapshotMessage` from the CURRENT `this.gameState` (+ `roomId`) and `client.send(
  snapshot.type, snapshot)` — then call it from BOTH `onJoin` (existing behavior, unchanged) and the reclaim
  `.then()` (new). DRY, behavior-identical on the join path. **Unicast (`client.send`), never `broadcast`** —
  only the reclaimed client needs it.
- The snapshot is the CURRENT authoritative state (post-any-forced-actions that ran during the absence) — the
  client replays from the snapshot's `eventIndex`; batches it missed between drop and resync are superseded by
  the snapshot (acceptable for M2's short grace; async-mode event-log replay is M4). NO seed in the snapshot
  (it is `PublicGameState`).

### 2. Client: persist the reconnection token + reconnect on an unexpected drop (the bulk)
In `packages/client/src/net/wsClient.ts` (+ a small persistence helper):
- **Declare `reconnectionToken`** on the `RoomLike` interface (`:63-70`) — SDK 0.17 exposes it on the joined
  `room`; the minimal surface must include it.
- **Capture + persist the token on join** (`connect()` @ `150-171`): immediately after a successful
  `joinOrCreate`, read `room.reconnectionToken` and persist it (see Key decision 3 — **sessionStorage keyed by
  `roomId`**), and keep an in-memory copy (the drop fires async — the token must already be saved BEFORE the
  socket closes).
- **Reconnect on an UNEXPECTED drop:** the existing `onLeave` → `statusForLeaveCode` (`connection.ts:50-52`)
  already maps an unexpected close to `'reconnecting'`. On that path, attempt `client.reconnect(token)` within
  the grace window (a small bounded retry — e.g. a few attempts with short backoff, capped well under the
  server's 120s grace); on a CONSENTED/deliberate `disconnect()` do NOT reconnect (mirror the S2.3.1 consented
  boundary — clear the persisted token).
- **Re-attach synchronously on reconnect success:** when `reconnect(token)` resolves with the room, re-run
  `attachRoom(room)` (`:79-129`) SYNCHRONOUSLY (before any further await) so the `onMessage('state.snapshot')`
  handler is registered BEFORE the server's resync unicast can arrive (Key decision 5 — the race). Transition
  status back to `'connected'`; the incoming snapshot folds through the existing store path (`store.ts:199-214`)
  and resets `gameState` to authoritative.
- **On reconnect failure / grace expiry:** transition to `'disconnected'` (terminal), clear the persisted
  token. (A fresh re-join as a NEW seat is a lobby concern, out of scope.)

### 3. i18n + UX (reuse, minimal)
- **Reuse the existing `reconnecting` i18n key** (`keys.ts:104`, localized `ru.ts:119`/`en.ts:109`/`uk.ts:118`)
  + the existing ConnectionIndicator on the Players rail (`DESIGN.md:166`). If a NEW string is genuinely needed
  (e.g. a terminal "reconnect failed / disconnected" notice not already present), add the key + ALL THREE
  locales (ADR-0008 — never fewer than 3; ADR-0010 typed catalogue, missing key fails build). Do NOT invent a
  grace-countdown banner (Key decision 4).

### 4. Tests
- **Client (`packages/client/src/net/wsClient.test.ts` — extend the mock-`RoomLike` pattern):**
  - Token is captured + persisted on join (assert the persistence write).
  - An UNEXPECTED `onLeave` (non-consented code) → `client.reconnect(token)` is called with the persisted token;
    on resolve, `attachRoom` re-subscribes and a subsequent `state.snapshot` folds into the store (gameState
    reset to the snapshot). Status goes `reconnecting → connected`.
  - A CONSENTED `disconnect()` does NOT call `reconnect` and clears the token.
  - Reconnect failure (reject) → status `disconnected`, token cleared.
- **Server (`packages/server/src/room/GameRoom.test.ts` — extend the S2.3.1 reconnect tests):**
  - On reclaim within grace, the reclaimed client receives a `state.snapshot` whose payload is the CURRENT
    `gameState` (mint-from-current, post any forced actions). Assert the unicast (only that client), and that
    `onJoin`'s snapshot behavior is UNCHANGED (the `#sendSnapshot` extraction is behavior-preserving).
  - Determinism guard still holds: resync appends ZERO events + mutates no `gameState` (a drop+reconnect+resync
    cycle leaves the server event stream identical to the no-drop match).

## Key decisions (surface any deviation)

1. **Reuse the existing `StateSnapshotMessage` — no new protocol.** The full-`PublicGameState` snapshot already
   exists and is already sent on join; resync is the same message, unicast, at the reclaim seam. A new "resync"
   message would duplicate it. **Tradeoff:** the client replays from the snapshot's `eventIndex` and loses the
   individual missed batches — fine for M2's short grace; async replay is M4.
2. **Server side is a behavior-preserving extraction + one unicast.** Extract `#sendSnapshot(client)` from the
   join path (617-622) and call it from both `onJoin` (unchanged) and the reclaim `.then()`. Unicast, not
   broadcast. No `gameState` mutation, no event, no seed — determinism untouched.
3. **Token persistence = sessionStorage keyed by `roomId`.** Per-tab, survives a page reload (the common
   reconnect case), auto-cleared on tab close, and scoped per match so a stale token can't leak into another
   game. **Rejected: localStorage** — cross-tab/cross-session persistence is a different lifetime (durable
   resume = S2.6.5) and risks reconnecting into a match the user meant to leave. Keep an in-memory copy too
   (the drop is async — persist on join, before the socket can close).
4. **Reuse the existing reconnect UX — no new banner.** The Players-rail ConnectionIndicator + the
   `reconnecting` status/i18n already exist (`DESIGN.md:166`, `keys.ts:104`). A grace-countdown banner is
   net-new UI without DESIGN guidance → OUT of scope (owner/DESIGN sign-off required). This keeps S2.3.2 a
   tight T2 and DESIGN-compliant. **Rejected: designing a countdown banner now** — that's an unrequested UI
   feature (Law 2) needing design authority.
5. **Beat the resync race with a SYNCHRONOUS re-attach; escalate only if it manifests.** The server sends the
   snapshot in the reclaim `.then()` (fires when Colyseus detects the reconnect); the client must have its
   `onMessage('state.snapshot')` handler registered by then. Mitigation: re-run `attachRoom` SYNCHRONOUSLY the
   instant `reconnect()` resolves, before any await. **If** a test shows the snapshot can arrive before the
   handler (a real race in `@colyseus/testing`), the clean fix is a client-initiated `resync.request` →
   server-reply (a new protocol message) — but that is a deliberate escalation: **STOP + report** rather than
   adding it silently. Start with the synchronous re-attach + a test that proves the snapshot is folded.
6. **Resync is a PublicGameState projection — the seed never leaves the server.** The snapshot is `PublicGameState`
   (no seed, ADR-0009). The client renders/predicts; the server stays authoritative. Commit-reveal integrity is
   untouched.

## Acceptance criteria

- [ ] On a fresh join the client persists `room.reconnectionToken` (sessionStorage, keyed by `roomId`) + keeps
      an in-memory copy; the join snapshot path is UNCHANGED (`#sendSnapshot` extraction behavior-preserving).
- [ ] On an UNEXPECTED drop the client calls `client.reconnect(token)` within grace (bounded retry) and, on
      success, re-attaches its sync handlers synchronously and returns to `'connected'`; a CONSENTED
      `disconnect()` does NOT reconnect and clears the token.
- [ ] On reclaim, the server UNICASTS a fresh `StateSnapshotMessage` (current `gameState`, NO seed) to only the
      reclaimed client; the client folds it and its `gameState`/board resets to authoritative (consistent with
      forced actions that ran during the absence).
- [ ] Determinism intact: resync appends ZERO events, mutates no server `gameState`; a drop+reconnect+resync
      match has an identical server event stream to the same match without a drop.
- [ ] The resync snapshot handler is registered before the snapshot can arrive (no race drops the message) —
      proven by a test that the reconnected client actually folds the snapshot.
- [ ] Reconnect failure / grace expiry → client `'disconnected'`, token cleared (no crash, no stuck state).
- [ ] Any new user-facing string ships RU/UA/EN (ADR-0008); the existing `reconnecting` indicator is reused; NO
      net-new grace-countdown banner.
- [ ] NO core / protocol-message / `RoomSchema` / bot / verify change; core stays zero-runtime-deps (unaffected).
- [ ] DEFERRED not built: bot-fill on expiry + safe-leave (S2.3.3); grace-countdown banner; async event-log
      replay; localStorage cross-session token.
- [ ] Full verify chain green; all pre-existing suites (incl. the S2.3.1 reconnect tests + client suite) pass.
