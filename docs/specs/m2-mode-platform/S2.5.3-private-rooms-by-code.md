# S2.5.3 — Private rooms by code / invite link

**Epic:** E2.5 Lobby, matchmaking, presence · **Tier:** 2 · **Model:** Sonnet
**Status:** materialized 2026-07-10 · depends on S2.5.4 (merged `a2d1f77`) · blocks nothing

## Goal

A host creates a **private** match, gets a shareable code / invite link, and a friend joins
that exact room by pasting the code or opening the link — instead of being dropped into a random
public room. Today every client lands in any open seat via `joinOrCreate` (`wsClient.ts:332`);
there is no way to say "make me a room only my friend can join".

## Owner decision (2026-07-10): the code IS the raw Colyseus `roomId`

Chosen over a bespoke short human-readable code. Rationale, under the locked "start cheap, one
VPS, do not over-engineer" constraint: a short code needs a `code → roomId` registry, i.e. new
server state that a single node can hold in memory but that **S2.5.1 (Redis, multi-node) would
then have to rewrite**. The raw `roomId` needs **zero new server state** — Colyseus already mints
and routes it. It is ~9 characters, fine to type or drop in a URL. If a prettier code is wanted
later, it is a clean additive story on top of Redis, not a thing to build-then-migrate now.

**Privacy model, stated honestly in the story and a code comment:** the `roomId` is an
*unguessable-enough* invite token for "play with a friend", **not** a security boundary. Anyone
holding the id can join until the room fills. That is the intended semantics of an invite link.
No auth, no per-code secret — that would be over-engineering for this feature.

## How it maps to Colyseus (transport-only)

- **Create private:** `client.create(GAME_ROOM_NAME, options)` (always a fresh room, unlike
  `joinOrCreate`) with an `isPrivate: true` option. In `onCreate`, when that flag is set, call
  `this.setPrivate(true)` — Colyseus then excludes the room from `joinOrCreate`/listing, so no
  stranger is auto-matched into it. The host reads `room.roomId` synchronously after create.
- **Join by code:** `client.joinById(roomId, options)`. The id rides the matchmaking URL
  (`/matchmake/joinById/{roomId}`), **not** the options body — so it does NOT go through
  `JoinOptionsSchema`.
- **Quick match:** unchanged — `joinOrCreate` with no `isPrivate`, lands in a public room.

## 🔴 Interaction with the S2.5.4 `.strict()` gate (do not miss this)

`JoinOptionsSchema` is `.strict()` (`messages.ts:709`) — any wire option key outside the
allow-list hard-rejects the join. Therefore the new `isPrivate?: boolean` option **must be added
to `JoinLobbySelectionSchema`** (`messages.ts:667`), or every private-room create is rejected by
the very gate S2.5.4 just installed. This is the whole protocol change: one optional boolean.
`roomId` needs no schema change (it is a method argument, above the body).

## Acceptance criteria (each forcing — fails if the capability is scaffolding)

1. **A private room is excluded from quick-match.** Client A `create` with `isPrivate:true`;
   Client B then `joinOrCreate` — B must land in a **different** room (assert distinct `roomId`),
   never in A's private room. This test fails if `setPrivate(true)` is not called.
2. **Join-by-code reaches the exact room.** Client B `joinById(A.roomId)` lands in A's room
   (assert same `roomId`, seats now 2/4). A wrong/expired id rejects cleanly (the join promise
   rejects; nothing crashes).
3. **`isPrivate` survives the strict allow-list.** A wire create carrying `isPrivate:true` is
   accepted (not rejected by `JoinOptionsSchema.strict()`), and the resulting room reports
   `private === true`. This is a regression guard on the S2.5.4 gate — it fails if the schema
   was not widened.
4. **Quick match is unchanged.** A `joinOrCreate` with no `isPrivate` still auto-matches into a
   public room exactly as today; every existing matchmaking/E2E test passes untouched.
5. **The invite link round-trips on the client.** A cold load with `?room=<roomId>` in the URL
   drives `joinById(roomId)` instead of showing the quick-match lobby — and must NOT collide
   with the S2.3.2a resume-first path: if a live reconnect pointer exists, resume wins over the
   URL code (assert: reconnect pointer present + `?room=` present → resumes the held seat, does
   not `joinById` a fresh one).
6. **Trilingual.** Every new UI string in `ru.ts` / `uk.ts` / `en.ts` (build guard enforces).
7. **Core & seed frozen.** `packages/core` untouched (exactly 334 tests). No `GameState` field,
   no event carries `roomId`/`isPrivate`, no seed/verify change — replay is byte-identical
   whether a match was joined by code or auto-matched.

## Implementation notes (verified by recon, 2026-07-10)

- **Server:** `boot.ts:116` `gameServer.define(GAME_ROOM_NAME, GameRoom, roomOptions)` — single
  room type, no filtering today. The private/public split is **not** a second `define`; it is
  `this.setPrivate(true)` inside `GameRoom.onCreate` gated on the `isPrivate` option. `onCreate`
  already reads the (now zod-parsed) options — add the flag read next to the existing
  `profileId`/`bots` reads (near `GameRoom.ts:356`).
- **Client connect:** `connect(url, callbacks, guest?, lobby?)` (`wsClient.ts:291`). Add an
  optional join-mode so it can branch to `client.create(...)` (private host) or
  `client.joinById(roomId, ...)` (code) instead of `joinOrCreate` (`wsClient.ts:332`). Keep the
  three branches explicit. The resume-first branch (`wsClient.ts` reconnect path, S2.3.2a) stays
  ahead of all of them and is untouched.
- **Reconnect pointer precedence:** `reconnectToken.ts` — `readCurrentRoomId()` (`:57`) and
  `readReconnectionToken()` (`:30`). `main.tsx` cold-load already resumes before the lobby
  (`main.tsx:70`); the `?room=` URL code slots in **after** that resume check, never before
  (criterion 5).
- **Lobby UI:** `LobbyScreen.tsx` currently renders preset + bot-count radiogroups and a Start
  button (`:166`). Add a join-mode control (Quick match / Create private / Join by code) and,
  for the code mode, a text input. `lobbyStore.ts` (`:33`) gains `joinMode` + `roomCode` fields;
  `selectLobbySelection` (`:43`) includes `isPrivate` when the mode is create-private. Follow
  the established roving-tabindex radiogroup pattern; selection never colour-only (a11y law).
- **Host's shareable link:** after `create`, show `room.roomId` as both a copyable code and a
  `${location.origin}?room=${roomId}` link. `PRODUCT.md`/`DESIGN.md` binding for the UI.
- **i18n:** add keys to `keys.ts` (`TRANSLATION_KEYS`) then all three locales. Accessor
  `useTranslation().t` (`I18nProvider.tsx:71`).

**Surprise (cost ~30 min):** my first `LobbyScreen.test.tsx` draft mutated
`useLobbyStore.setState(...)` then rendered via `renderToStaticMarkup` to prove
the join-by-code / invite-link conditionals — and silently always saw the
STORE'S INITIAL state. Root cause: zustand v5's `useStore` feeds React's
`useSyncExternalStore` a `getServerSnapshot` backed by `getInitialState()`
(`zustand/vanilla.js`), which is captured ONCE at module load and never
updates — `renderToStaticMarkup` (this codebase's only render path; no jsdom
anywhere) can therefore never observe a test's `setState()` call. Fix: extracted
the three conditionals into a pure `deriveLobbyViewState(state, connectedRoomId)`
in `lobbyStore.ts`, unit-tested directly (no React) — mirrors the existing
`hud/trade.ts` "pure helper, separately tested" split. This is a real, general
constraint on how ANY zustand-store-reading component in this codebase can be
tested for non-default state via the existing convention — worth a note in
`memory/` for the next UI story that tries the same thing.
