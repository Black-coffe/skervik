# S2.5.2 — Ready-up: host-started private matches

**Epic:** E2.5 · **Tier:** 2 · **Model:** Sonnet · **Priority: playability (private rooms)**
**Status:** materialized 2026-07-10 · depends on S2.5.3 + S2.5.4a (merged `6bc24c3`)

## Goal

A host creates a private room, shares the invite link, waits for friends to join by code, and
**presses "Start" to begin the match** — filling any still-empty seats with bots. All players in
the room transition to the game together the moment it starts. Today a private room with 2 humans
and 2 empty seats **never starts**: `#maybeAutoStart` (`GameRoom.ts:523`) fires only when
`seats.length >= maxClients`, bots included, and there is no manual trigger — so "invite a friend"
(S2.5.3) currently dead-ends in the lobby.

This story also closes the transition seam S2.5.4a deliberately left open: `createPrivate` /
`joinByCode` joins have no path to `<GameScreen>`.

## Design decisions (owner-directed ready-up; defaults chosen, not asked)

1. **Host = the private room's creator** (the `createPrivate` client; seat 0). Only the host sees
   and can press "Start match". Joiners see a "waiting for host to start" state. The host signal
   is transport-only — derive it from seat 0 / the creating session; do NOT add it to `GameState`.
2. **Private rooms are manual-start only.** For a room created with `isPrivate:true`, disable
   auto-start-on-seats-full and start **only** on the host's explicit message. (Quick-match is
   unchanged — it still auto-starts when seats fill, so a fast match never waits.) This gives the
   host control to wait for a third friend rather than starting the instant a seat fills.
3. **Empty seats fill with bots at start.** When the host presses Start with N humans in a
   `maxClients`-seat room, the remaining seats are bot-filled, then the match starts. **Reuse the
   existing `#botFillSeat` + `#startMatch`** (S2.3.3 / S2.4.3) — do not write a second start or
   bot-mint path. If `#botFillSeat` cannot be reused as-is for pre-start fill, STOP and report
   rather than duplicating it.
4. **The client transitions on `phase`, not on connect.** `RoomSchema.phase` is already mirrored
   to clients as a Colyseus schema patch (`GameRoom.ts` ~615) and leaves `'lobby'` exactly when
   the match starts (`match.started` → `phase:'setup'`). Flip the client to `<GameScreen>` when
   the observed room `phase !== 'lobby'`. **This is the single, uniform transition signal for
   every join mode** — quick-match, create-private, and join-by-code all show the game the moment
   the room actually starts, and no one ever sees a blank `<GameScreen>` before `gameState`
   exists (the current quickMatch connect-time flip can show that empty window; folding it into
   the phase signal removes it). See "Unify vs. keep" below.

### Unify vs. keep the S2.5.4a quickMatch flip

**Preferred:** replace S2.5.4a's connect-success flip with the phase-based transition for ALL
modes — it is strictly better (no empty-GameScreen window, one mechanism, and it's what makes
private rooms work anyway). If you do this, adapt S2.5.4a's forcing tests to assert the
phase-driven transition instead of deleting them, and keep their intent (failed connect / waiting
private room → stays on lobby; started room → shows game).

**Fallback (only if unifying proves risky):** keep the quickMatch connect flip and ADD a
phase-observer for createPrivate/joinByCode. Say which you chose and why. Do not ship both firing
for the same mode.

## Acceptance criteria (each forcing)

1. **Host start begins a 2-human private match.** E2E: host `create`s a private room (4 seats),
   one client `joinById`s (2/4 seats), the match does NOT auto-start; the host sends the start
   message; assert `match.started` is emitted, the 2 empty seats are now bot seats (`isBot:true`),
   and `phase` leaves `'lobby'`. This fails today (no manual start exists).
2. **A non-host cannot start.** The joiner sending the start message is rejected/ignored; the
   room stays in `'lobby'`. Binds the host-only rule.
3. **Private room does not auto-start on a partial fill.** 2/4 seats in a private room stays in
   `'lobby'` with no `match.started` until the host acts. (Guard against accidentally leaving
   auto-start on for private rooms.)
4. **Quick-match is unchanged.** A quick-match room still auto-starts on seats-full; every
   existing GameRoom/e2e/matchmaking test passes untouched.
5. **Client shows the game when phase leaves lobby — every mode.** Pure/unit-testable transition:
   given an observed `phase !== 'lobby'`, the client flips to `<GameScreen>`; given `phase ===
   'lobby'`, it stays on the lobby / waiting view. Test via the pure helper (per
   [[zustand-store-not-observable-in-static-render]] — no `<App/>` static render). A host and a
   joiner both flip when the host starts. This is the criterion that closes the S2.5.4a seam.
6. **Failed connect / waiting room stays on lobby.** Preserve the S2.5.4a guarantees: a null
   handle stays on the lobby; a joined-but-not-started private room stays on the waiting view,
   never a blank GameScreen.
7. **Trilingual.** New strings ("Start match", "waiting for host", …) in ru/uk/en.
8. **Core & seed frozen.** `packages/core` untouched (exactly 334). No `GameState` field for
   host/ready/lock — all transport (Colyseus room state / a room message). No event-shape or seed
   change; replay byte-identical.

## Implementation notes (verified by recon, 2026-07-10)

- **Server start predicate:** `#maybeAutoStart` (`GameRoom.ts:523`) `if (this.#matchStarted ||
  this.state.seats.length < this.maxClients) return;`. Gate this on a private flag so private
  rooms skip it; add a host-start message handler that bot-fills then calls `#startMatch`
  (`GameRoom.ts:552`). Colyseus's native `room.lock()`/`unlock()` exists but you likely don't
  need it — the private/manual split is cleaner as an explicit branch. Bot-fill reuse:
  `#botFillSeat` (S2.3.3).
- **Host identity:** the `createPrivate` creator is seat 0 (bots are minted after; a private room
  starts empty of bots). Derive host from the creating `sessionId` / seat 0 — transport only.
- **Client phase observer:** `RoomSchema.phase` arrives as a schema patch; `hud/store.ts`
  (`applySnapshot`/`applyEventBatch`) already folds `gameState.phase`. Add a pure
  `shouldShowGame(phase)` (`phase !== 'lobby'`) and drive the `<App>` switch from it. `App.tsx`
  today is `started ? <GameScreen/> : <LobbyScreen/>` — extend so a joined-but-waiting private
  room shows a waiting view, and any started room shows the game.
- **No forced-action hang added** (S2.4.3 closed all legs; the turn timer only arms once phase
  leaves `'lobby'` — a ready-up stall before turn 1 arms no timer). [[turn-timer-forced-action-hang-risk]]
- **Matchmaking-by-mode segregation is OUT of this story** (quick-match players picking different
  presets still share a room — a real gap, but it's the separate `filterBy` seam on `boot.ts:116`,
  owned by a matchmaking story, and it wants Redis-awareness for multi-node). Note it, don't fix it.

## Out of scope

Matchmaking-by-mode `filterBy` segregation. Redis / presence / multi-node (S2.5.1). Per-room
`maxSeats` chosen from the lobby UI (a separate small story — wire it through `onAuth` as an
intentional config override with guards, NOT a security bypass; the invite host getting a
"table of 2" can come later). Accounts (E2.6). Any `reduce`/`validate`/event/seed change.
