# S2.8.5b — Ventures: the two board-pick plays (Конвой / Попутный ветер)

**Epic:** E2.8 (final story) · **Tier:** 3 (client) · **Depends on:** S2.8.5a (the
`VenturePanel` + `devCardActions` gating this extends), S2.8.4a (the robber
tile+victim flow the knight reuses), S2.8.3b (the road-edge legality mirror) ·
**Status:** DISPATCH-READY.

Completes S2.8.5 (dev cards). 5a shipped buy + the two **resource-picker** plays
(yearOfPlenty/monopoly). 5b adds the two plays that **hijack a board pick**:

- **Конвой (knight)** → move the robber (tile) + optional steal (victim) — the SAME
  resolution as S2.8.4a's `moveRobber`, but dispatched as a dev-card play and armed
  OUTSIDE the `robber` phase.
- **Попутный ветер (road-building)** → up to **2 free road edges** in one play.

After this the full Classic ruleset is human-playable in the browser.

## Goal

From the `VenturePanel` (S2.8.5a) a human on their `main`-phase turn clicks «Разыграть»
on a held **Конвой** or **Попутный ветер** and completes it by clicking the board — the
panel's knight/roadBuilding rows currently show a count with NO play button (5a left them
for this story). This needs a **venture-armed board-pick source** that overrides
`GameScreen`'s phase-driven picker while a knight/road-building play is armed.

## Core contract (verified — client never calls `validate`; advisory hints only)

Both dispatch through the generic `store.dispatchIntent` (proven live); the server
re-validates. **No protocol/net/server work** (protocol already round-trips these —
`packages/protocol/src/messages.test.ts`).

- **Knight:** `{ type:'intent.playDevCard', card:'knight', tileId: TileId, victimId?: PlayerId }`
  (`core/types.ts:978`). Routes through `resolveRobberMove` (`validate.ts:1506-1552`) — the
  SAME relocate+steal as `moveRobber`, **no discard step** (knights never trigger discards).
  Core allows it in `'roll'` OR `'main'` (`validate.ts:1072`), but see the scope note below —
  5b exposes it in `main` only.
- **Road-building:** `{ type:'intent.playDevCard', card:'roadBuilding', edgeIds: readonly EdgeId[] }`
  (`core/types.ts:985`). Core is **tolerant** (`validate.ts:1554-1588`): it takes the first ≤2
  edges that are unoccupied, network-connected, and within road supply, and silently places
  FEWER if some don't qualify — so a slightly-off client selection still succeeds partially.
  `main`-phase only.
- **Play gating (both, `validate.ts:1486-1503`)** — already mirrored by `hud/devCardActions.ts`
  `canPlayVenture` from 5a (`!devCardPlayedThisTurn` + `playableCount(kind) > 0` + main + my turn):
  `DEV_CARD_ALREADY_PLAYED` (one Venture/turn), `CARD_NOT_HELD`, `BOUGHT_THIS_TURN`.
- **Knight legality** reuses `board/robberLegality.ts` (S2.8.4a): `legalRobberTiles(state, topology)`
  (all tiles but the robber's current one) + `stealVictims(state, topology, tileId, myPlayerId)`
  (building owners on the tile ≠ me with cards, `isStealable`). Same reject surface as moveRobber:
  `ROBBER_SAME_TILE` if the picked tile already holds the robber (advisory — let it dispatch, server
  rejects → `NoticeBar`).
- **Road-building legality** reuses `board/buildLegality.ts` `legalBuildRoads(state, topology,
  myPlayerId)` (S2.8.3b) for the advisory edge highlight.

## Requirements

### 1. `hud/store.ts` — UI-only venture-play state
Add (all UI-only, never in `gameState`, never sent except inside the resolved intent):
- `venturePlayMode: 'none' | 'knight' | 'roadBuilding'` + `setVenturePlayMode`.
- `knightPendingTile: TileId | null` + `setKnightPendingTile` — the tile awaiting a knight
  steal-victim choice (mirrors `robberPendingTile`; do NOT reuse `robberPendingTile` — its
  fold-clear keys on the `robber` phase, which a knight play is never in).
- `roadBuildingEdges: readonly EdgeId[]` + `setRoadBuildingEdges` — the 0–2 edges picked so far.
- **Reset ALL THREE** (`'none'` / `null` / `[]`):
  - in `applySnapshot` (fresh join — same discipline as `robberPendingTile`);
  - in `applyEventBatch`, on the fold that makes the armed play no longer valid — i.e. when
    `venturePlayMode !== 'none'` AND the NEW state is no longer `(phase==='main' &&
    currentPlayerId===myPlayerId && !devCardPlayedThisTurn)`. This is the safety net for a
    completed play (server sets `devCardPlayedThisTurn`), a turn-timeout, or the turn ending —
    mirror the `robberPendingTile` phase-out-clear reasoning (clear on the transition OUT of
    validity, never while still valid, so an in-progress pick isn't wiped).

### 2. `hud/useVenturePlacement.ts` (new — mirror `useRobberPlacement`/`useBuildPlacement`)
A pure derivation + pure resolvers + a thin hook, unit-tested WITHOUT a render. It drives BOTH
knight and road-building off `venturePlayMode`. Cache `buildTopology()` module-level (same as the
sibling hooks). Active ⇔ `venturePlayMode !== 'none'` AND `phase==='main'` AND my turn AND
`!devCardPlayedThisTurn` (defensive; the store clear should already cover the last two).

- **Knight** (`venturePlayMode==='knight'`): near-clone of `useRobberPlacement`, but keyed on
  `knightPendingTile` and dispatching a knight play instead of `moveRobber`.
  - No pending tile → `pickMode:'tile'`, prompt `knightMove`. On tile pick → if
    `stealVictims(...)` non-empty, set `knightPendingTile` (→ victim picker); else dispatch
    `{ type:'intent.playDevCard', card:'knight', tileId }` immediately and clear the mode.
  - Pending tile → `pickMode:'none'`, prompt `knightChooseVictim`, `victims` from `stealVictims`.
    Same empty-victims self-heal fallback to tile-pick as `deriveRobberPlacement` (never render a
    zero-button picker). Victim pick → dispatch `{ …card:'knight', tileId, victimId }`, clear mode.
  - «Отмена» on the victim step → clear `knightPendingTile` (back to tile-pick), keep the mode.
- **Road-building** (`venturePlayMode==='roadBuilding'`): `pickMode:'edge'`, `legalTargets =
  { kind:'edge', ids: legalBuildRoads(state, topology, myPlayerId) }` (advisory highlight —
  computed from the CURRENT state; it need NOT simulate the first pending edge into the network,
  so an edge reachable only via the pending edge may not highlight — the human can still click it
  and the server's tolerant branch accepts it; note this in a comment). On edge pick → append to
  `roadBuildingEdges` (dedupe; cap at 2; ignore a 3rd). Prompt reflects progress
  (`roadBuildingFirst` at 0 picked, `roadBuildingSecond` at 1). A **«Разыграть»** confirm (enabled
  when `roadBuildingEdges.length >= 1`) dispatches `{ type:'intent.playDevCard', card:'roadBuilding',
  edgeIds: roadBuildingEdges }` and clears the mode; «Отмена» clears the mode. (Confirm allows 1 OR
  2 edges — the core is tolerant and sometimes only 1 edge is legal.)
- **After any dispatch**, clear `venturePlayMode` (+ the pending tile / edges) IMMEDIATELY in the
  hook (like `useBuildPlacement`'s `setBuildMode('none')`) — don't wait for the server fold; the
  fold-based store clear (§1) is the safety net.
- Unit-test the pure derive/resolvers: knight no-victim tile → dispatch; knight with-victim tile →
  pending; victim → dispatch-with-victim; empty-victims-pending → self-heal to tile-pick;
  road-building append/dedupe/cap-at-2; confirm builds the `edgeIds` intent; inactive off-turn / off-mode.

### 3. `hud/VenturePanel.tsx` — wire the knight/roadBuilding «Разыграть»
The knight (Конвой) and roadBuilding (Попутный ветер) rows currently render a count with NO play
button (5a). Add a **«Разыграть»** button to each, enabled per `canPlayVenture(state, me, kind)`.
On click → `setVenturePlayMode(kind)` AND `setVentureOpen(false)` (close the panel so the board is
clear for picking). Do NOT change the yearOfPlenty/monopoly/victoryPoint rows.

### 4. `hud/RobberPrompt.tsx` — parameterize for knight reuse (minimal), or a thin new component
The knight victim picker is visually identical to the robber's — reuse it. Prefer parameterizing
`RobberPrompt` with OPTIONAL prompt-label keys (e.g. `moveKey?`/`chooseKey?: TranslationKey`,
defaulting to the existing `robber.promptMove`/`robber.promptChooseVictim`), so the knight rendering
passes knight keys. (If parameterizing gets awkward, a small `KnightPrompt` that reuses the
`.robber-prompt` markup is acceptable — state your choice. Do NOT regress the robber's own usage.)
The road-building 2-edge prompt + «Разыграть»/«Отмена» confirm bar is a small new prompt element
(a `setup-prompt`-style status line + the confirm buttons); put it inline in `GameScreen` or a tiny
component — your choice.

### 5. `hud/GameScreen.tsx` — inject the venture-play pick source
Add `const venturePlay = useVenturePlacement();`. The venture play, when active, OVERRIDES the
phase-driven build picker (both are `main`-phase, but a knight/road-building play must take the
board while armed). Selection precedence:
```
const placement = isSetupPhase ? setup
  : venturePlay.active ? venturePlay        // NEW — overrides build while a venture play is armed
  : isMainPhase ? build
  : isRobberPhase ? robber
  : null;
```
Render the knight victim picker (reuse `<RobberPrompt>` with knight keys) when the knight play is
in its choose-victim step, and the road-building confirm bar when `venturePlayMode==='roadBuilding'`.
Keep the existing setup/build/robber prompts + `DiscardPanel`/`VenturePanel` rendering intact.
While a venture play is armed, the build selector in `BottomDeck` should not also be arming picks —
since `venturePlay` takes precedence in `placement`, the build hook's pick source is simply not fed
to `GameTable`; that's sufficient (no BottomDeck change required). Do NOT touch the phase-driven
picker logic beyond adding the `venturePlay.active` branch.

## Scope note — knight in `main` only (deferred: pre-roll knight)
Core allows a knight in `'roll'` too (move the robber off your tile before rolling). But the
`VenturePanel` is only openable in `main` (S2.8.5a's `hud.actionVenture` gate), so 5b exposes knight
in `main` only. Playing a knight PRE-roll is a deferred enhancement (would widen the panel-open gate
+ the venture pick override to `'roll'`) — note it in the epic follow-ups, don't build it here.
