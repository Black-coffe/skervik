# S2.6.4 — GDPR self-service: data export + right-to-erasure

The M2 accounts gate requires GDPR self-service. A user (including a guest — a guest is a `users`
row) can **export** all data held about them (data portability) and **erase** their account
(right to be forgotten). Both are authenticated to the caller's OWN `userId` via their session
token — never cross-user, no admin surface here.

**OUT OF SCOPE:** admin/moderator deletion; OAuth (S2.6.2b); ratings (M3); hard-deleting match
history (see the anonymize-not-cascade decision below); any UI beyond the REST endpoints + their
localized response codes.

## Design decisions (locked)

- **Erasure = soft-delete + anonymize, NOT cascade-delete.** Set `users.deleted_at = now()`, scrub PII
  (`display_name` → a neutral tombstone like `'[deleted]'`, `email` → null). **`match_players` rows are
  RETAINED** — a match's integrity/history (other players' records, VP, winner) must not be corrupted by
  one participant erasing themselves. The retained rows keep pointing at the tombstoned `users` row (its
  PII is gone), so match history stays consistent while the person is no longer identifiable. (Scout note
  from ADR recon: "No cascade to matches; a deleted user's historical matches remain (audit trail).")
- **Export = a machine-readable JSON** of everything keyed to the caller's `userId`: their `users` row
  (post-any-scrub fields as stored) + every match they participated in (join `match_players` → `matches`:
  seat, final_vp, result, profile, started/finished, status). GDPR data portability.
- **Auth = the caller's own session token.** The endpoint verifies the `sessionToken` (reuse S2.6.2a's
  `verifySessionToken`), resolves the `userId`, and operates ONLY on that `userId`. A missing/invalid
  token → 401. There is NO way to export/delete another user's data.
- **Post-erasure token is dead.** After erasure, the user's `userId` is soft-deleted; any live/re-presented
  session token for it resolves to a deleted user → treated as anonymous (the live-user reads filter
  `deleted_at IS NULL`). Do NOT invent token revocation infra (post-M2) — the `deleted_at` filter is the
  mechanism.
- **DB-gated, no regression.** These endpoints only function when `DATABASE_URL` is configured (they need
  the repos). Absent DB → the routes return a clear "not available" (or aren't registered) — the server
  still boots and every existing flow is unchanged.

## Scope — build exactly this

### A. Repository reads/writes for GDPR (`packages/server/src/db/repositories/`)
- `UserRepository.softDeleteAndAnonymize(userId)`: set `deleted_at=now()`, `display_name='[deleted]'`,
  `email=null`; idempotent (already-deleted → no-op / returns the tombstone). Returns the tombstoned row.
- A read that aggregates a user's match participation: `MatchPlayerRepository.findByUser(userId)` →
  rows; joined with `MatchRepository` to assemble the export (either a join query or two queries).
  (Verify exact S2.6.3 repo method names after that story merges — `findByMatch` exists; add `findByUser`.)

### B. Auth helper (reuse S2.6.2a)
- A small "resolve the authenticated userId from the request's session token" helper for the routes —
  reads the token (Authorization header `Bearer <token>` or a body/query field; pick one and document it),
  `verifySessionToken` → `userId`, or 401. Do NOT duplicate the JWT logic — call the S2.6.2a verifier.

### C. Routes (`packages/server/src/routes/`, registered in `boot.ts` gated on DATABASE_URL)
- `GET /account/export` → 200 with the JSON export for the authenticated `userId` (401 if unauthenticated).
- `POST /account/delete` (or `DELETE /account`) → soft-delete+anonymize the authenticated `userId`, 200 with
  a confirmation; subsequent `/account/export` for that (now-deleted) identity behaves as unauthenticated.
- Register both alongside the existing `/auth/guest` + verify routes; gate on the store/db being configured.
- **i18n (ADR-0008):** any user-facing string these endpoints return (confirmation/error messages) must be a
  structured CODE the client localizes RU/UA/EN — core/server emit codes, never localized prose (the
  S2.1.3 `warningCode` precedent). If the endpoints only return machine data + codes, note that no new
  client strings are needed here beyond the codes.

### D. Tests (PGlite-hermetic + route-level)
- Repo: `softDeleteAndAnonymize` sets deleted_at + scrubs display_name/email + is idempotent; a
  soft-deleted user is excluded from live reads but the row + its `match_players` persist.
- Route: authenticated export returns the user's data incl. their matches; unauthenticated/other-user →
  401/empty; delete tombstones the user and a follow-up export for that identity is unauthenticated.
- Match-integrity: after user A erases, a match A played in still has its other seats + winner intact
  (A's `match_players` row retained, pointing at the tombstoned user).

## Acceptance criteria
- **AC1 (erasure):** `POST /account/delete` (authed) sets `deleted_at`, scrubs `display_name`/`email`;
  the user vanishes from live reads; their `match_players` rows + the matches remain intact.
- **AC2 (export):** `GET /account/export` (authed) returns the user's `users` row + all their match
  participations (seat/final_vp/result + match profile/status/times). Assert the shape.
- **AC3 (authz — FORCING):** no token / invalid token / a token for a DIFFERENT user cannot export or
  delete this user's data (401 / only-own-data). A post-erasure token resolves as unauthenticated.
- **AC4 (no regression):** absent `DATABASE_URL` → routes not functional but server boots; all existing
  server tests pass unchanged; core git-byte-unchanged + zero-dep guard; PlayerId semantics unchanged.
