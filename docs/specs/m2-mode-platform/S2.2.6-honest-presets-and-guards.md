# S2.2.6 — Three profile-config guards + honest preset documentation

## Why this story shrank

It was planned as "assign the catch-up flags to Balanced/Blitz". Then S2.2.5 measured them and
the answer looked like "no flag earned a slot, but `vpToWin` is a powerful lever." Then
`lead-review` showed **the comeback metric was confounded with `vpToWin` itself** — the tie-set
for last place grows when the match shortens, and the metric counted "winner among the players
tied for last" as a comeback. H2, H3, and the hiddenVp finding are void (see S2.2.5a).

So this story now contains **only what is proven by code, not by sampling**, plus documentation
that does not overclaim. The Balanced preset is **not** changed here. Whether any preset gains a
catch-up flag or a lowered VP threshold waits on S2.2.5a's re-run and, for two of the flags, on
S2.4.4.

## What survives the retraction (and drives this story)

Two findings are code-proven and independent of any statistic:

1. **`eventTiles` without `robinHood` is a dead mechanic.** `spendPovertyToken`
   (`reduce.ts:123-132`) has exactly ONE call site (`reduce.ts:729`), gated on
   `event.povertyDiscount`, which `validate.ts:1993` can only set behind a short-circuiting
   `profile.catchUp.robinHood &&`. With `robinHood:false`, granted poverty tokens can never be
   spent by any player, bot or human. `EVENT_TILES_TEST_PROFILE` inherits `robinHood:false`.
2. **The robin-hood discount executed 0 times in 3000 bot matches** — `bankTradeToward`
   (`bots/src/heuristic/v1.ts:259-291`) proposes `count: bestBankRate(...)`, the same function
   `validate.ts:1984` uses for the legality check, so `validate.ts:1986`'s `intent.count !== rate`
   is never true for a bot. A bot limitation, not an engine bug — it becomes S2.4.4.

## Goal

Three load-bearing guards so an incoherent profile config can never silently mean nothing, plus
per-preset documentation that claims only what the engine delivers.

## Scope — exact changes

### 1. Three guards, validated ONCE at registry initialization

**Do not put these in `loadRuleProfile`.** It is called from `reduce`/`validate` on every event;
the profiles are frozen constants that cannot change between calls. Add a pure
`validateRuleProfile(profile: RuleProfile): void` (throws on violation) in
`packages/core/src/ruleProfile.ts`, and run it over every entry of `PROFILE_REGISTRY` at module
initialization, so an incoherent profile fails loudly at import, not at turn 200 of a live match.

- **G1 — `catchUp.eventTilesInterval >= 1`.** `validate.ts:1169` computes
  `((state.sevensRolled ?? 0) + 1) % interval === 0`. At `interval: 0` that is `NaN === 0` →
  always false: the mechanic silently never fires. No crash, no error — a dead flag.
- **G2 — `catchUp.eventTiles === true` implies `catchUp.robinHood === true`.** Finding 1 above.
- **G3 — `1 <= catchUp.robinHoodExchangeRate < bankTrade.baseRate`.** The discount must beat the
  universal base rate (4:1) or it is a surcharge. It need **not** beat a 2:1 port — in that case
  `intent.count === bestBankRate`, the normal path handles the trade, and no token is spent, which
  is harmless. Assert only what must hold; a guard that rejects valid configs is a bug.

Each guard gets a test feeding a **violating** profile and asserting it throws:
`eventTilesInterval: 0`; `eventTiles:true, robinHood:false`; `robinHoodExchangeRate: 4` (==
`baseRate`). Plus one test asserting all four shipping presets pass. **A guard with no
failing-input test is decoration.**

Note G2 will reject the existing `EVENT_TILES_TEST_PROFILE` (it sets `eventTiles:true` with
inherited `robinHood:false`). That profile documents a config that cannot work. Give it
`robinHood: true`, or delete it in favour of `EVENT_TILES_ROBIN_HOOD_TEST_PROFILE`, and update
`eventTiles.test.ts` + `bots/src/sim/profiles.ts` accordingly. Say which you chose and why.

### 2. Remove the S2.2.5 measurement scaffolding

`VP9_TEST_PROFILE(_ID)` and `BALANCED_VP9_TEST_PROFILE(_ID)` were added as H3 scaffolding with a
comment saying they would be removed or promoted here. S2.2.5a's re-run is done by the time this
story runs; **remove both** from `ruleProfile.ts`, `PROFILE_REGISTRY`, `EXPERIMENTAL_PROFILE_IDS`,
and `bots/src/sim/profiles.ts` — unless S2.2.5a's corrected re-run found a real effect, in which
case STOP and report: promoting them is a preset change and needs the owner.

No dead config survives this story. That is precisely the rot G2 exists to prevent.

### 3. Documentation — say what each preset does, and only that

Update `docs/wiki/` and the profile doc-comments with one honest claim per preset:

- **Classic** — the reference rules. `vpToWin: 10`. Byte-frozen; the golden replay fixture and
  every seed-verification depend on it.
- **Balanced** — reduces **dice variance** (`balanced_deck`: a without-replacement draw from the
  36-outcome deck). It has **no measured effect on leader runaway** — a different pain with a
  different cure. Do not describe it as a catch-up mode.
- **Blitz** — a short match. `vpToWin: 8` + tight turn timers. Note that the sim is action-capped,
  not wall-clocked, so its timers have never been exercised by measurement.

Record, next to `catchUp.hiddenVp`, that it is an **information-hiding** mechanic whose value is
social (you cannot see whom to gang up on) and that a bot cohort reading full state **cannot
measure it at any sample size**. Its earlier "measurably harms comeback" label was an artifact and
is retracted. A future reader must not infer from its placement in the `catchUp` sub-profile that
enabling it helps trailing players — nor that it hurts them.

## Findings

**`computeAdaptiveDuration` does NOT hardcode `vpToWin: 10`** (constraint 6, report-only). It reads
`base.victory.vpToWin` from whichever `RuleProfile` it is given (`adaptiveDuration.ts:115-116`) and,
if the estimate exceeds the ceiling, decrements FROM that value one point at a time
(`adaptiveDuration.ts:131-139`) down to `ADAPTIVE_VP_FLOOR` (5). So it is parametric in `vpToWin`,
not anchored to Classic's 10 — a Blitz-based estimate (`vpToWin: 8`) would start its search from 8,
not 10. What it DOES assume, undocumented as a limitation: `ROUNDS_PER_VP = 1.2` and
`PLAYER_TURN_MINUTES = 1` are single global constants, not profile- or catch-up-aware — so the
S2.2.5a finding that catch-up flags are largely unmeasurable by the current bot harness also means
this calculator cannot yet account for whatever wall-clock cost/saving a live catch-up flag would
add. Not fixed here (out of scope, Law 3) — noted for whoever next touches S2.1.3/S2.5.4.

**`name: 'Balanced'` / `'Two-Player'` are English strings inside core** (`ruleProfile.ts`), which
contradicts "core emits structured codes, never localized prose." Confirmed present, confirmed
out of scope per hard constraint 5 — S2.5.4 (lobby UI, ADR-0008 trilingual mandate) owns replacing
`RuleProfile.name` with a structured i18n key.

## Decisions

**`EVENT_TILES_TEST_PROFILE` — DELETED**, not given `robinHood: true`. Setting `robinHood: true`
on it would have made it byte-identical to the already-existing
`EVENT_TILES_ROBIN_HOOD_TEST_PROFILE` (same `catchUp` object) — two exported constants for one
config is exactly the "dead config surviving by accident" this story exists to prevent (Law 2).
Deleted `EVENT_TILES_TEST_PROFILE`/`_ID`, dropped the `eventTiles` key from
`EXPERIMENTAL_PROFILE_IDS` (kept `eventTilesRobinHood`), and repointed every consumer:
`eventTiles.test.ts`'s first describe block (cadence/grant/cap/no-hang tests), `liveness.test.ts`'s
forcing test, and `bots/src/sim/profiles.ts`'s sweep row (`SWEEP_PROFILES`: 12 → 9, also dropping
`vp9`/`balancedVp9`). This is behavior-preserving for every repointed test: the event-storm GRANT
path (`validate.ts:1167`) is not gated on `robinHood` — only SPENDING a token (the bank-trade
discount, `validate.ts:1993`) is — so switching the profile's `robinHood` from `false` to `true`
does not change any grant-side assertion. Verified by running the full suite green after the
change (below).

**Sensitivity-outcome — KEEP, not code-touched.** S2.2.5a already implemented and documented the
decision (its own `## Findings`): the sensitivity outcome (unique-last at the OLD, endogenous
midpoint) is structurally unable to arbitrate the primary question — it conditions on tie-freeness
at a treatment-dependent cut, a post-treatment collider. It earns its keep anyway as a
cross-implementation check: its null reproduces the reviewer's independently-computed tie-free
numbers, which is a useful "did we build the same thing the reviewer built" signal that the
primary/matched-cut metric alone cannot provide. Nothing to change in `pairing.ts`/`report.ts` for
this story — S2.2.5a already reports it, already labeled correctly. Recorded here, explicitly, per
this story's instruction not to inherit the decision silently.

**Historical story docs (`S2.2.4-*.md`, `S2.2.5-*.md`) left untouched.** They cite
`EVENT_TILES_TEST_PROFILE`/`__vp9_test__`/`__balanced_vp9_test__` as records of what was built and
measured AT THE TIME — rewriting them would falsify history, not correct it (S2.2.5a already did
the one legitimate rewrite: retracting specific void conclusions in its OWN target file, under
explicit instruction). AC4's "no longer exist anywhere in the repo" is read as scoped to live code
(registry entries, exported ids, executable config) — the interpretation used throughout this
story — not to prose citing them as past measurements.

**Documentation went slightly beyond the literal ask.** While updating `BALANCED_PROFILE`'s
doc-comment for the S2.2.5a-corrected claim, found its EXISTING comment was independently stale
and wrong: it said "play is byte-identical to Classic until [S2.1.2] lands" — S2.1.2 (the
`balanced_deck` draw mechanic) shipped in E2.1 (closed, per `memory/MEMORY.md`), so Balanced has
NOT been byte-identical to Classic for several stories now. Corrected as part of the same edit
(same file, same constant, same "honest preset documentation" scope item) rather than filing a
separate finding — flagging here per Law 4 (surfacing the tradeoff): this is a small drift beyond
"add the S2.2.6 claim," but leaving a preset's doc-comment affirmatively wrong while adding a
correct claim two lines below it would be worse.

**2. `docs/wiki/rule-profiles.md`'s `hiddenVp` section proved a right conclusion with a false
premise.** It claimed the bot cohort reads FULL `GameState` including hidden VP, so the social
effect is unmeasurable. **The bot does not read hidden VP** — every VP read in `@skervik/bots` goes
through `computePublicVictoryPoints` (`eval/features.ts:184`, called from `heuristic/v1.ts:436,475`;
the one `state.devCards` read in v1, `v1.ts:448`, is the bot's OWN hand, for knight-play legality,
never an opponent's hidden VP). Corrected the premise in both places it appeared — the wiki AND my
own `ruleProfile.ts` `hiddenVp` doc-comment carried the identical error, caught while fixing the
wiki (not separately reported by the reviewer, but the same defect and the same fix). The TRUE
reason the effect is unmeasurable: `hiddenVp`'s value is that opponents cannot see who is about to
win and so cannot coordinate against them, and our bot cohort never coordinates against a leader at
all — visible or not. There is no collusion channel for hidden information to disrupt, independent
of what the bots can see.

**3. G3's lower bound (`< 1`) had no forcing test.** Deleting `robinHoodExchangeRate < 1 ||` left
all 331 tests green — the guard existed, the property was not bound to a test, same disease as G1's
`0` case. The leg is not decorative: at rate `0`, a trailing token-holder's `intent.count === 0`
satisfies the discount branch (`validate.ts:1986`), `canAfford({give:0})` trivially passes, and the
bank hands over a resource for free. Added the violating-input test (rate `0`). **Verified it forces
the guard**: reverted the code to the un-guarded `>=`-only check, ran the test, confirmed it failed
with the expected message, restored the guard, reran green.

**4. G1 accepted `NaN` and `Infinity`.** `NaN < 1` and `Infinity < 1` are both `false`, and neither
`(s+1) % NaN` nor `(s+1) % Infinity` is ever `0` — the exact permanently-dead-flag defect the guard
exists to prevent, reachable through the same check meant to prevent it. The real invariant is not
`>= 1` but "the cadence can fire": `Number.isInteger(v) && v >= 1`. Tightened the check, added two
violating-input tests (`NaN`, `Infinity`). **Verified both force the tightened check**: reverted to
the bare `< 1` check, ran the two new tests, confirmed BOTH failed (2 failed / 332 passed), restored
the tightening, reran green (334).

## What this episode is really about

Every fix in this round-2 pass was the same shape: an assertion or a comment bound to a SYMPTOM
(a specific string, a specific numeric threshold direction, an observed absence of an event) rather
than the PROPERTY that symptom was supposed to stand for. The test to apply before landing any
assertion, per the team-lead: **what is the smallest change that restores the underlying bug and
keeps this green?** If an answer exists, the assertion is decoration, not a guard.

**Guard placement.** `validateRuleProfile` is a plain exported function, called in a
`for...of Object.values(PROFILE_REGISTRY)` loop placed at the BOTTOM of the file, after
`PROFILE_REGISTRY`'s `const` (so every profile constant above it has already been evaluated) — not
inside `loadRuleProfile`, per the hard constraint. Module-level top-level code in a `.ts` file runs
once, at first import, before any test or app code that imports from `ruleProfile.ts` can execute —
this is what makes "an incoherent profile fails at import" true without a dedicated test harness
for the loop itself; a broken registry would have failed EVERY test file in the repo that
transitively imports `@skervik/core`, not just this story's own tests.
