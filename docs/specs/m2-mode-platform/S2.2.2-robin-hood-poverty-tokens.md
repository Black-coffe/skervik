# S2.2.2 — Robin Hood / poverty tokens (self-compensation for empty rolls)

## Goal

Second catch-up mechanic (roadmap principle 3 — *catch-up over runaway-leader*). **Owner decision
2026-07-07 ([[robinhood-poverty-tokens-design]]): OPTION A — self-compensation, NOT a rich→poor
transfer.** When `robinHood` is on, a **trailing** player earns a **poverty token** each time a dice
roll produces **zero resources for them** ("compensation for empty rolls"); a token lets them make a
bank trade at a **favorable rate** ("обменивает её по льготному курсу", `research-phase.md:93`). It is a
**profile-gated `CatchUpProfile` flag**, off on every shipping preset for now (liveness via a test
profile, the S2.1.5/S2.2.1 discipline).

**This is a DETERMINISTIC-from-state mechanic** — the token counter derives entirely from the roll
outcome + public standing, and the discounted trade is a fixed ratio. **NO seed slot, NO new PRNG,
`verify.ts` UNCHANGED** (the S2.2.1 precedent for catch-up rules that change legality/economy, not
randomness). The seed-derived draws (dice, steal) are untouched.

**Why T3 (three things make it more than a flag):**
1. **Persistent per-player state.** Poverty tokens live in `GameState` (a counter per player). Adding a
   `GameState` field risks the golden byte-freeze — it MUST be additive and absent/empty under
   `robinHood:false`, so Classic/replay/verify produce byte-IDENTICAL state.
2. **Two touch-points in the economy path.** Accrual on the roll (who got zero) + spend on the bank
   trade (discounted ratio consumes a token). Both must be no-ops when the flag is off.
3. **The plan-mandated dedup refactor** ([[robber-steal-eligibility-dedup]], plan §4/§181): extract a
   shared `isStealable(state, id, robber)` used by validate + forcedAction, and express
   `computeVictoryPoints = computePublicVictoryPoints + hiddenVP`. This story owns that cleanup because
   it reuses `computePublicVictoryPoints` for "trailing" and touches the same VP code.

## Mechanic (Option A — precise, provisional numbers tunable in playtest)

- **"Trailing":** a player whose **public VP** (reuse `computePublicVictoryPoints` — NO hidden-VP leak,
  S2.2.1) is at least `robinHoodVpGap` below the current leader's public VP. Default `robinHoodVpGap = 2`.
- **Accrual:** on a **non-7** dice roll (a 7 is the robber, no production), for each **trailing** player
  who receives **zero** resources from that roll's production, grant **+1 poverty token**, capped at
  `robinHoodTokenCap` (default **3**, prevents farming). Accrual is **automatic** (system-emitted during
  roll resolution) — NO player intent, so it adds NO new forced-action path (see Key decision 4).
- **Spend:** a bank trade by a player with **≥1 poverty token** may use the discounted ratio
  `robinHoodExchangeRate` (default **2**:1, vs the normal 4:1/3:1); executing a discounted trade
  **consumes 1 token**. Discounted trades are OPTIONAL — the player chooses; normal bank trade is
  unchanged and always available.
- **Determinism:** every step is a pure function of `state` + the roll's already-drawn production. No
  new randomness.

> These numbers are **provisional balance knobs** (flag is off on all presets → they change no shipping
> behavior). They will be tuned by the M2 balance-sim/playtest workstream. Set them, don't agonize.

## What to build

### 1. The `CatchUpProfile` sub-profile + `robinHood` flag (core, `ruleProfile.ts`)
Tech-spec §180 names `RuleProfile.catchUp.robinHood`. Introduce it now (S2.2.1's `friendlyRobber` stayed
in `RobberProfile` pragmatically — **leave it there, do NOT churn/byte-freeze-risk it**; note that
S2.2.3/S2.2.4 catch-up flags will also join `catchUp`, and `friendlyRobber` MAY migrate later — not now):
```
export interface CatchUpProfile {
  readonly robinHood: boolean;            // poverty tokens for trailing players
  readonly robinHoodVpGap: number;        // trailing = public VP <= leader's public VP - this
  readonly robinHoodTokenCap: number;     // max tokens a player can hold
  readonly robinHoodExchangeRate: number; // discounted bank ratio when a token is spent (N:1)
}
```
Add `readonly catchUp: CatchUpProfile` to `RuleProfile` (the flat aggregate at ~128-176). Set on
`CLASSIC_PROFILE.catchUp` as `{ robinHood:false, robinHoodVpGap:2, robinHoodTokenCap:3,
robinHoodExchangeRate:2 }`; BALANCED/BLITZ/twoPlayer inherit via `...CLASSIC_PROFILE` → all four shipping
presets `robinHood:false` (byte-frozen). Add a test-only `ROBIN_HOOD_TEST_PROFILE` (spread CLASSIC,
`catchUp.robinHood:true`) under registry key `'__robin_hood_test__'` (NOT in `RuleProfileId`/
`SHIPPING_PROFILES`, not re-exported from `index.ts` — clients can't select it), mirroring
`FRIENDLY_ROBBER_TEST_PROFILE`.

### 2. Poverty-token state on `GameState` (core, `types.ts`)
Add `readonly povertyTokens?: Readonly<Record<PlayerId, number>>` to `GameState` — **optional, additive,
absent when never granted** (the "absent key = fact never happened" convention, types.ts comments). Under
`robinHood:false` this field is NEVER written → serialized state is byte-IDENTICAL to today → golden
frozen. Drop-key-if-zero on spend (mirror the `playersToDiscard`/resource `subtractResources`
drop-empty convention) so a spent-to-zero player doesn't leave a `0` that diverges state shape.

### 3. Accrual event + reducer (core, `types.ts` + `reduce.ts`)
Add a new `GameEvent` member `PovertyTokensGrantedEvent extends BaseGameEvent` (template:
`MonopolyPlayedEvent` types.ts:584-589) carrying the explicit fact, e.g.
`grants: Readonly<Record<PlayerId, number>>` (per-player +N). `reduce`'s new
`case 'poverty.tokensGranted'` applies `addResources`-style increments capped at `robinHoodTokenCap`
(reduce applies the FACT; the cap/trailing decision is computed in `validate`, per the codebase pattern
— reduce never recomputes who is trailing). Emit it from the roll-resolution path in `validate` **right
after `resources.produced`**, ONLY when `robinHood` is on and ≥1 trailing player got zero. When off, the
event is never emitted → existing roll events unchanged.

### 4. Discounted bank trade (core, `validate.ts` bank-trade path + `reduce.ts`)
In the existing bank-trade legality (`WRONG_RATE_COUNT`), when `catchUp.robinHood` is on AND the actor is
trailing AND holds ≥1 token, ACCEPT the `robinHoodExchangeRate` ratio in addition to the normal ratios,
and mark the resulting bank-trade event so `reduce` decrements one token. Recommended shape: an optional
`povertyDiscount?: true` field on the bank-trade event (both-or-neither with the discounted ratio) that
`reduce` uses to `-1` the actor's token (drop-key-if-zero). If the worker finds a companion
`poverty.tokenSpent` event cleaner/more auditable, that's acceptable — flag the choice. When
`robinHood:false`, the bank-trade path is byte-IDENTICAL to today.

### 5. Discharge the dedup carry-forward (core, `validate.ts` + server `forcedAction.ts`)

## Key decisions (surface any deviation)

1. **Option A, deterministic → verify untouched.** Poverty tokens derive from the roll outcome + public
   standing; the discounted trade is a fixed ratio. No new PRNG slot, no verify branch. ([[robinhood-poverty-tokens-design]])
2. **PUBLIC VP for "trailing", never true VP.** Reuse `computePublicVictoryPoints` — using hidden VP would
   leak it. Same discipline as S2.2.1.
3. **Additive GameState field, absent when off.** `povertyTokens` optional + drop-key-if-zero → golden
   byte-frozen under `robinHood:false`. This is the headline determinism risk; lead-review verifies it.
4. **Accrual is automatic → NO new forced-action path.** Tokens are system-granted during roll
   resolution (no intent); the discounted trade is optional. So the [[turn-timer-forced-action-hang-risk]]
   does NOT re-open here — the forced defaults (rollDice/endTurn/discard/moveRobber) are unaffected.
   Confirm no forced action touches poverty tokens.
5. **Introduce `catchUp` sub-profile now** (tech-spec §180); leave `friendlyRobber` in `RobberProfile`
   (no churn). S2.2.3/S2.2.4 flags join `catchUp`.
6. **Bundle the dedup refactor here** (plan-assigned) — but keep it BEHAVIOR-PRESERVING (existing tests
   green unchanged prove it). If it balloons the diff or risks byte-freeze, STOP + report to split it out.
7. **No ADR needed.** Profiles-as-config + catch-up-profile-gating are locked; this is their application.
