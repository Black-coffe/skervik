# S2.1.3 — Adaptive-duration calculator (players × mode → fit the ≤60-min ceiling)

## Goal

Turn the LOCKED product rule — *"60 min is a hard ceiling for synchronous online play; the lobby
computes the profile from player count × mode to fit the target window, and if a config risks exceeding
60 min the engine lowers VP / tightens timers and warns in the lobby"* (CLAUDE.md · roadmap principle 4)
— into a real, pure **decision function**. Given a base mode (`RuleProfileId`) and a player count, it
**estimates the match length** and, if the estimate exceeds the ceiling, **lowers the one lever the
engine already honors — `victory.vpToWin`** — step by step until it fits (or a floor is hit), returning
the adjusted `RuleProfile` to use plus a structured summary the lobby can render.

This is the game's realization of the anti-"dead time" principle: a 6-player game to 10 VP that would
run ~85 min gets recommended at 8 VP (~55 min) instead of dragging. The **timer / parallel-phase /
board-size levers named in the roadmap are added to this calculator WHEN their mechanics ship**
(S2.1.4 timers, S2.1.5 parallel, S2.1.6 board) — S2.1.3 wires the ONE lever that is live today (VP),
faithfully to VULYK Law 2 (add a knob when the behavior exists, not before). It is a **pure core helper**
— it does NOT touch `reduce`/`validate`/`verify`/`GameState`/events, so it carries no determinism or
fairness risk; Classic/Balanced/Blitz play is byte-unchanged.

## What to build

### 1. The pure calculator (core, NEW `packages/core/src/adaptiveDuration.ts`)

- **`estimateMatchMinutes(profile: RuleProfile, playerCount: number): number`** — a documented, TUNABLE
  heuristic (v1). Indicative form (worker picks coefficients that satisfy the anchors + monotonicity
  below — the exact numbers are v1 placeholders to be calibrated against real match-length telemetry in
  M3, NOT part of the contract):
  ```
  estimatedMinutes ≈ SETUP_MINUTES
                   + PLAYER_TURN_MINUTES × playerCount × (profile.victory.vpToWin × ROUNDS_PER_VP)
  ```
  **Required behavior (the contract, test these — NOT exact minutes):**
  - **Monotonic ↑ in `playerCount`** (more players ⇒ ≥ estimate) and **monotonic ↑ in `vpToWin`**.
  - **Calibration anchors:** `4 players × Classic (10 VP)` is **within** the 60-min ceiling;
    `6 players × Classic (10 VP)` is **over** it (so the adjuster has something to do). Pin these two.
  - Pure, deterministic, no wall-clock / no RNG / no deps.
- **`computeAdaptiveDuration(baseProfileId: RuleProfileId, playerCount: number, targetMinutes = ADAPTIVE_CEILING_MINUTES): AdaptiveDurationResult`**
  — resolve `base = loadRuleProfile(baseProfileId)`; if `estimateMatchMinutes(base, playerCount) <=
  targetMinutes` return it unchanged (empty `adjustments`, `withinCeiling: true`). Else lower
  `vpToWin` by 1 repeatedly (re-estimating each step) until it fits OR `vpToWin` would drop below
  **`ADAPTIVE_VP_FLOOR`**; return the adjusted profile via the proven deep-merge
  `{...base, victory: {...base.victory, vpToWin: adjusted}}` (readonly-safe), an `adjustments` entry per
  step (or one net entry `{knob:'vpToWin', from, to}` — surface the choice), and — **only if even the
  floor still exceeds the ceiling** — `warningCode: 'exceeds_ceiling_at_vp_floor'` with
  `withinCeiling:false` (the lobby will note that timers/parallel — S2.1.4/.5 — are needed to fit).
  Validate `playerCount` against `[ADAPTIVE_MIN_PLAYERS, ADAPTIVE_MAX_PLAYERS]` (2–6): throw a typed
  error on out-of-range (or clamp + flag — surface the choice; recommend throw, mirroring
  `loadRuleProfile`'s loud-fail).

- **Exported, documented, tunable constants:** `ADAPTIVE_CEILING_MINUTES = 60`,
  `ADAPTIVE_MIN_PLAYERS = 2`, `ADAPTIVE_MAX_PLAYERS = 6`, `ADAPTIVE_VP_FLOOR` (a sensible minimum, e.g.
  `5` — never recommend a shorter game; note Blitz already sits at 8), and the heuristic coefficients
  (`SETUP_MINUTES`, `PLAYER_TURN_MINUTES`, `ROUNDS_PER_VP`). Each with a one-line comment that it is a
  v1 estimate for later calibration.

### 2. The result types — STRUCTURED, i18n-safe (core)
```
type AdaptiveWarningCode = 'exceeds_ceiling_at_vp_floor';   // extensible; NOT a localized string
interface AdaptiveAdjustment { readonly knob: 'vpToWin'; readonly from: number; readonly to: number; }
interface AdaptiveDurationResult {
  readonly profileId: RuleProfileId;         // the base mode requested
  readonly profile: RuleProfile;             // the profile to actually use (adjusted, or base unchanged)
  readonly playerCount: number;
  readonly targetMinutes: number;
  readonly baselineMinutes: number;          // estimate for the UNADJUSTED base profile
  readonly estimatedMinutes: number;         // estimate for the RETURNED profile
  readonly withinCeiling: boolean;
  readonly adjustments: readonly AdaptiveAdjustment[];
  readonly warningCode?: AdaptiveWarningCode; // structured; lobby (S2.5.4) localizes to RU/UA/EN
}
```
**No user-facing English string anywhere in the return** (ADR-0008) — the lobby maps `warningCode` +
the numeric fields to localized copy in S2.5.4. `knob` is `'vpToWin'` only for now; the union grows
(`'turnTimer'`, `'parallelPhases'`, `'boardSize'`) as S2.1.4/.5/.6 add those levers.

### 3. Exports (core, `index.ts`)
Export `computeAdaptiveDuration`, `estimateMatchMinutes`, the constants, and the types
(`AdaptiveDurationResult`, `AdaptiveAdjustment`, `AdaptiveWarningCode`) following the existing
ruleProfile/balancedDeck export pattern.

## Scope — build THIS, defer the rest

**Build:** the pure `adaptiveDuration.ts` (estimator + `computeAdaptiveDuration` + constants + structured
types); exports; behavioral tests. That is all — one new self-contained module.

**DEFER — do NOT build here:**
- **Applying an adjusted (non-preset) profile to a LIVE match / any `GameRoom` or engine wiring.** The
  engine resolves rules via `loadRuleProfile(state.profileId)` — an id→preset lookup — and `GameState`
  carries only `profileId`, NOT a full profile. An adaptively-adjusted profile has a non-preset
  `vpToWin`, so it has no id to store; delivering it to the pure engine needs a **profile-override
  mechanism** that S2.1.1 deliberately avoided (id + loader, not the whole object in state). That seam
  is a real future decision — see Key decision 4; **record it as a carry-forward, do NOT solve it here.**
  `GameRoom` stays hardcoded `'classic'`; S2.1.3 is proven purely by unit tests.
- **Lobby UI that surfaces the estimate/warning + LOCALIZES `warningCode`** — S2.5.4. This story returns
  structured data only.
- **Turn-timer / parallel-phase / board-size levers** — S2.1.4 / S2.1.5 / S2.1.6. Add each `knob` to
  the calculator (and its `AdaptiveAdjustment` union member + estimate term) WHEN that mechanic exists.
  Do NOT add dead knobs now (VULYK Law 2).
- **Board-size topology variation & the verify BOARD-leg** ([[verify-profile-blindness-carryforward]]) —
  S2.1.3 does NOT make the board diverge, so both stay deferred to the first story with a variable board.
- **Coefficient calibration against real telemetry** — M3 (analytics). v1 uses documented estimates.

## Key decisions (surface any deviation)

1. **Only the `vpToWin` lever is live; the others are added with their mechanics.** Why: the engine
   honors `victory.vpToWin` today (S2.1.1) but has no turn timers (S2.1.4), parallel phases (S2.1.5), or
   variable board (S2.1.6). Emitting adjustments for knobs nothing enforces would be dead config
   (Law 2). The `AdaptiveAdjustment.knob` union + the estimate model grow as those land — same
   "field lands with the behavior" discipline as S2.1.1/S2.1.2.
2. **The duration model is a simple, documented, tunable heuristic — behavior is the contract, not the
   minutes.** Why: no real match-length telemetry exists yet (comes with M3 analytics); a simulation
   would be overengineering (Law 2). Tests pin monotonicity + the two calibration anchors + the
   clamp/floor behavior, so re-tuning coefficients later can't silently break the feature.
3. **Warning + adjustments are STRUCTURED codes, never localized strings.** Why: ADR-0008 — every
   user-facing string ships in RU/UA/EN, authored at the UI layer. A calculator returning an English
   warning would bake an untranslated string into core. The lobby (S2.5.4) localizes `warningCode` +
   the numbers.
4. **S2.1.3 COMPUTES the recommendation; it does NOT apply a non-preset profile to a live match — that
   is an unresolved delivery seam, recorded as a carry-forward.** Why: `GameState` intentionally carries
   only `profileId` + a pure `id→preset` loader (S2.1.1 rejected storing the whole profile object). An
   adaptive result has a custom `vpToWin` with no preset id. Bridging that (a profile-override in state,
   or the lobby applying a computed config, likely with S2.5.4) is its own decision — flag it, don't
   pre-build it. The calculator is useful standalone: the lobby can DISPLAY "recommended 8 VP for 6
   players, ~55 min" the moment this ships, and feed it into a live match once the apply-mechanism lands.
5. **Tier 2, Sonnet worker.** Why: a pure, self-contained module with NO determinism/fairness/contract
   surface (it never touches `reduce`/`validate`/`verify`/`GameState`/events) — the token-economy
   bookend puts this squarely on Sonnet, with Opus reserved for the deterministic-core/verifier stories.
6. **No ADR needed.** The ≤60-min ceiling + "profiles as config" are already locked; this is
   implementation. If the profile-override delivery seam (Key decision 4) needs resolving, THAT may
   warrant an ADR when its story is picked up — flag it there, not here.
