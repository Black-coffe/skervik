# S2.2.1 — Friendly robber (can't steal from a trailing player)

## Goal

First catch-up mechanic (roadmap principle 3 — *catch-up over runaway-leader*): when `friendlyRobber`
is on, the robber **cannot steal from a player at or below a low VP threshold** (default **≤2 public
VP**), so the trailing player isn't kicked while down. It is a **profile-gated `RobberProfile` flag** —
one config knob, resolved via `state.profileId`, off on every shipping preset for now (its liveness
proven by a test profile, the S2.1.5 discipline). This is a **validate LEGALITY rule**, not a
randomness change: the seed-derived steal DRAW is untouched, so `verifyMatchRandomness` is unchanged.

**Two cross-checks that make this more than a one-liner** (surfaced by the M2 plan's seam ledger):
1. **Forced-action hardening ([[turn-timer-forced-action-hang-risk]]).** S2.1.4's `resolveForcedAction`
   robber branch names a victim "only when stealable". Friendly robber SHRINKS the eligible set, so the
   forced move MUST use the SAME friendly-aware eligibility — else a timed-out turn could inject a
   moveRobber naming a now-protected victim, `validate` rejects it, and the turn HANGS. S2.2.1 MUST
   thread the rule through the forced path too.
2. **Public VP, not true VP.** The protection threshold must count **PUBLIC/visible VP** (settlements +
   cities + public awards) and **EXCLUDE unrevealed VP dev cards** — otherwise "you can't rob X" leaks
   that X holds a hidden VP card. (Hidden VP itself is S2.2.3; this story just must not use true VP.)

## What to build

### 1. The `friendlyRobber` flag (core, `ruleProfile.ts`)
Add to `RobberProfile` (the sub-profile that already holds `handLimit`/`halfDivisor`):
```
readonly friendlyRobber: boolean;        // when true, protect trailing players from the steal
readonly friendlyRobberVpCeiling: number; // protect players with PUBLIC VP <= this (default 2)
```
Set `friendlyRobber:false` on **CLASSIC / BALANCED / BLITZ / twoPlayer** (byte-frozen). Do NOT enable
it on a shipping preset — prove liveness with a test-only `friendlyRobber:true` profile (S2.1.5
precedent). `friendlyRobberVpCeiling` present on all presets (value irrelevant while the flag is off).

### 2. A PUBLIC-VP helper (core)
Add (or reuse if one exists — confirm at dispatch) a `computePublicVictoryPoints(state, playerId)` that
counts ONLY visible VP: settlements (1) + cities (2) + public awards (longest road / largest army) —
**NOT** unrevealed VP dev cards. (`computeVictoryPoints` used for VICTORY includes hidden VP and must
stay as-is for the win check.) Document that this helper is the "visible standing" and that S2.2.3
hidden-VP will refine what "public" means.

### 3. Gate the steal in `validate` (core, robber-move path)
In the eligible-victim computation for `moveRobber` (the `eligibleWithCards`/`NO_SUCH_VICTIM` logic),
when `loadRuleProfile(state.profileId ?? 'classic').robber.friendlyRobber` is true, **exclude any
candidate whose `computePublicVictoryPoints ≤ friendlyRobberVpCeiling`**. Consequences (reuse existing
M1 behavior — do NOT invent new events):
- If a protected player is the ONLY adjacent card-holder → **no steal** (`robber.moved` with no
  `stolenFrom`/`stolenResource`, exactly as M1 handles "no eligible victim"). The move itself is still legal.
- A `moveRobber` intent that NAMES a protected victim → reject (a new `RejectReason`, e.g.
  `VICTIM_PROTECTED`, or the existing `NO_SUCH_VICTIM` — surface the choice).
- **`friendlyRobber:false` → the M1 path verbatim** (byte-frozen).

### 4. Thread the rule through the S2.1.4 forced action (core/server — the cross-check)
`resolveForcedAction`'s robber branch (the deterministic auto-move) must select its victim with the
SAME friendly-aware eligibility, so a forced moveRobber under `friendlyRobber:true` NEVER names a
protected victim (which validate would reject → hang). If every adjacent card-holder is protected, the
forced move steals from no one (legal). Add a test that a timed-out robber turn under `friendlyRobber`
still produces a LEGAL forced move (no hang).

### 5. Tests
- Under a `friendlyRobber:true` test profile: cannot steal from a ≤2-public-VP player (reject or
  no-steal); CAN steal from a >2-VP player; the protection uses PUBLIC VP (a player with 2 public VP +
  a hidden VP card is STILL protected — no leak); the forced-action robber picks only unprotected
  victims (no hang); no eligible victim → clean no-steal.
- `friendlyRobber:false` (Classic/Balanced/Blitz/twoPlayer): robber steal behavior byte-IDENTICAL to
  today — existing robber tests + golden/replay/verify green UNCHANGED.
- `verifyMatchRandomness` UNCHANGED (the steal DRAW is unaffected; only victim legality changed).

## Key decisions (surface any deviation)

1. **A validate LEGALITY rule, not a randomness change → verify untouched.** Why: friendly robber
   restricts WHO may be robbed; the seed-derived WHAT (which resource) is unchanged, and `verify` audits
   the draw, not victim legality. No new PRNG slot, no verify branch.
2. **PUBLIC VP, never true VP.** Why: using true VP (incl. hidden VP cards) for protection would leak
   hidden VP ("can't rob X ⇒ X has a hidden VP"). The dedicated public-VP helper prevents that; S2.2.3
   will formalize hidden VP.
3. **Forced-action victim selection MUST respect the rule (hang-risk cross-check).** Why:
   [[turn-timer-forced-action-hang-risk]] — a forced moveRobber naming a protected victim would be
   rejected by validate and hang the turn. The forced path reuses the same eligibility.
4. **Flag off on all presets; test-profile proves liveness.** Why: which mode carries which catch-up
   flags is a product decision to batch once E2.2's mechanics exist (S2.1.5 precedent — no premature
   preset behavior change).
5. **Dispatch AFTER S2.1.6 merges.** Why: S2.1.6 edits the same robber-victim eligibility (neutral
   exclusion) + ruleProfile + the forced-action robber branch — a concurrent branch would conflict.
6. **No ADR needed.** Profiles-as-config + catch-up-profile-gating are locked; this is their application.
