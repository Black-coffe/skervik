# S2.3.3 — Bot-fill on grace expiry + safe leave/rejoin (close E2.3)

## Goal

Last story of E2.3. S2.3.1/2/2a made a dropped human able to reconnect within grace (in-tab + page reload) and
resync; during grace the turn timer covers their turns with forced defaults (S2.3.1). But if grace EXPIRES and
they never come back, the seat sits `connected:false` forever — the match can limp on forced-endTurn defaults
but the absent player contributes nothing and the game never really finishes well. This story installs a **bot
to drive the abandoned seat once grace expires** (owner-chosen Fork B), so the remaining humans play a real
match to a real finish against a competent opponent — "no dead time." It also fixes the carried **game-end
consented-close nit** so a page reload after the match ends doesn't waste a resume attempt.

**What bot-fill IS (locked by the invariants + Fork B):** when `allowReconnection` REJECTS (grace ran out with
no reconnect — the `onDrop` `.catch()` at `GameRoom.ts:687-692`), the room mints a `createHeuristicBot(...)`
for that seat's EXISTING `playerId`, adds it to the `#bots` map, and triggers the S2.4.3 drive loop. Because
`#nextBotActorId` gates on `#bots.has(playerId)` ALONE (scout-confirmed), the existing
`#scheduleBotTurnIfNeeded`/`#driveBotTurn` machinery picks the seat up on the next commit and drives it through
the SAME authoritative `#queue` tail — no new pipeline, no core change, no GameState change. The fill-bot holds
NO authority and is match-seed-blind (S2.4.3 discipline); its moves are ordinary events → replay byte-identical.
**Fork B (owner-chosen 2026-07-08):** the bot fills ONLY on expiry — during grace, forced-defaults cover the
seat and the human can still reconnect, so there is NO mid-game bot→human hand-back (the reconnect window is
already closed once the bot takes over).

**Scope of THIS story:** bot-fill on grace expiry (drops) + bot-fill on a deliberate (consented) leave + the
game-end consented close. Server-only (+ the bot dep, already present). NO core / protocol-message / GameState
change; the fill-bot reuses S2.4.3 entirely.

## What to build (all in `packages/server`, + tests)

### 1. Bot-fill at the grace-expiry seam (the epic-closing capability)
Replace the no-op `.catch()` in `onDrop` (`GameRoom.ts:687-692`) with bot-fill:
- Find the seat by `client.sessionId` (as the `.then()` reclaim branch does). It is already `connected:false`.
- Mint `const bot = createHeuristicBot({ difficulty: this.#botFillDifficulty, seed: \`bot-fill-${seat.seatIndex}\` })`
  (match-seed-blind seed, distinct from genesis `bot-${i}`; import `createHeuristicBot` — already a server dep).
- `this.#bots.set(seat.playerId, bot)` — this alone makes `#nextBotActorId` treat the seat as a bot actor.
- Set `seat.isBot = true` + `seat.botDifficulty = this.#botFillDifficulty` — the client's existing signal that
  the seat is now bot-driven (reuse the S2.4.3 fields; NO new SeatSchema field — Key decision 2). Note: a
  genesis bot has `isBot:true` + `connected:true`; a filled seat has `isBot:true` + `connected:false`, so the
  two remain distinguishable.
- Call `this.#scheduleBotTurnIfNeeded()` so the bot acts immediately if it is (or becomes) the current actor /
  owes a discard. If it is not the current player, the existing drive loop picks it up on the next commit.
- **Idempotency/guard:** only install if the seat still exists and isn't already in `#bots` (avoid a double
  install if the terminal `onLeave` also fires — see part 3).

### 2. Bot-fill on a deliberate (consented) leave
A player who deliberately leaves is not coming back to reclaim mid-match, so their seat should be bot-driven
immediately (so the remaining humans aren't stalled). In `onLeave`'s CONSENTED branch (the S2.3.1 consented
path — currently just marks `connected:false` + clears nothing to hold): ALSO install the fill-bot (same mint +
`#bots.set` + `isBot`/`botDifficulty` + `#scheduleBotTurnIfNeeded` as part 1). Keep the S2.3.2a client behavior
(a consented leave clears the client's reconnect pointer — the leaver is done). **Do NOT grace-hold a consented
leave** (Key decision 3 — a deliberate leaver is bot-filled at once, not held). Guard against double-install
with part 1 / the terminal notice.

### 3. Game-end consented close (fix the S2.3.2a nit #3)
Today the room does NOT close client connections with a consented code at game end (scout: `game.ended`
detected ~`GameRoom.ts:869-875`, no `.leave()`/close; `onDispose` only clears the timer). So a page reload
after the match ends makes the client try to resume a finished seat (server rejects → wasted attempt →
fallback join). Fix: when `game.ended` is applied (the commit tail where it's detected), close the room's
clients with a **CONSENTED close code (4000)** — confirm the Colyseus 0.17 API (`this.disconnect(closeCode?)`
closes all clients + disposes; or per-client `client.leave(4000)`). The client's S2.3.2a logic clears its
reconnect pointer on a 4000 close → no wasted resume on a post-match reload. Verify the close is CONSENTED from
the client's perspective (matches the code the S2.3.2a client treats as "clear the pointer").

### 4. A bot-fill difficulty option
Add `botFillDifficulty?: 'easy' | 'medium' | 'hard'` to `GameRoomOptions` (default `'medium'` — a reasonable
competitor for an abandoned seat), stored in `#botFillDifficulty` at `onCreate`. Keep it a ROOM option (infra),
not a rule-profile field. A lobby (E2.5) can override later.

### 5. Determinism / no-hang discipline (bind the invariants)
- The fill-bot drives via the EXISTING `#driveBotTurn` (S2.4.3) → its moves are ordinary events (no timestamp/
  marker) → replay byte-identical. The grace-expiry TRIGGER is wall-clock + server-only (never logged), exactly
  like the S2.1.4 timer. Confirm a match-with-a-drop-then-bot-fill replays byte-identically from its event log.
- The fill-bot is match-seed-blind (`bot-fill-${seatIndex}` seed, never the match seed) — no authority, no
  commit-reveal leak (S2.4.3 discipline).
- No-hang: the fill-bot inherits S2.4.3's `resolveForcedAction` fallback + per-turn cap (it drives via the same
  `#driveBotTurn`), so a stuck fill-bot fails loud, never spins. The [[turn-timer-forced-action-hang-risk]] is
  already fully closed; do not reopen it.
- Classic byte-frozen: a match with NO drops installs no fill-bot → `#bots` holds only genesis bots (or none) →
  behavior identical to today.

## Key decisions (surface any deviation)

1. **Fork B — bot fills ONLY on grace expiry (owner-chosen 2026-07-08).** During grace the game keeps moving via
   forced-defaults (S2.3.1) and the human can reconnect (S2.3.2/2a); the bot takes over only once grace expires
   with no return. **Rejected: bot-fill from the moment of disconnect + hand-back** — richer "no dead time" but a
   reconnecting human would return to a seat the bot advanced strategically (surprising), and it needs a
   bot→human handoff race on a live seat. Fork B is simpler, less surprising, and closes the epic. Consequence:
   NO hand-back (post-expiry the reconnect window is already closed).
2. **Reuse `isBot`/`botDifficulty` + the `#bots` map — NO new SeatSchema field.** `#nextBotActorId` gates on
   `#bots.has(playerId)` alone (scout-confirmed), so adding the seat to `#bots` is what makes the drive work;
   flipping `isBot:true` + `botDifficulty` is just the client signal. A filled seat = `isBot:true` +
   `connected:false` (distinguishable from a genesis bot's `connected:true`). Keeps SeatSchema unchanged.
   **Rejected: a new `botFilledAt` field** — unneeded for the drive + risks the botFill.e2e genesis-only
   assumptions; the existing fields suffice.
3. **A consented leave is bot-filled immediately (not grace-held).** A deliberate leaver isn't coming back
   mid-match, so their seat becomes a bot at once so the remaining humans continue. The S2.3.2a client already
   clears its pointer on a consented leave — consistent. **Rejected: grace-holding a consented leave** — that
   contradicts the client's pointer-clear-on-consented model and adds a rejoin race for a player who chose to
   leave; a distinct "leave-but-hold" is a future story.
4. **Wall-clock trigger, deterministic result.** Grace expiry (wall-clock) triggers the fill, but the fill-bot's
   moves are ordinary log events (no timestamp/marker) → replay byte-identical. The trigger is server-only,
   exactly like the S2.1.4 turn timer. No determinism-of-replay violation.
5. **Game-end consented close is a real fix, not cosmetic.** Without it, the S2.3.2a reload-resume wastes an
   attempt after a finished match (server rejects → fallback). Closing with code 4000 at `game.ended` makes the
   client clear its pointer. This is the last open reconnect nit (plan §4).
