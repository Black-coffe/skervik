# S2.5.4 — Lobby UI: preset selection, bot fill, ready-up

**Epic:** E2.5 Lobby, matchmaking, presence · **Tier:** 2 · **Model:** Sonnet
**Status:** materialized 2026-07-10 · depends on nothing open · blocks nothing

## Goal

A human opens the client, **chooses a rule preset** (`classic` / `balanced` / `blitz` /
`twoPlayer`) and how many bots fill the table, presses **Start**, and plays that preset.
Today the client cannot express any of this: `joinOrCreate` sends no room options
(`wsClient.ts:311`) and the room silently defaults to `'classic'` (`GameRoom.ts:356`).

Every user-facing string ships in **ru / uk / en** (ADR-0008); `keys.ts` makes a missing
key a build failure, so this is enforced, not aspirational.

## Why this cut

The plan's S2.5.4 bundled four things. Only the first is in scope here:

| | In / out | Why |
|---|---|---|
| preset selection + bot fill + start | **IN** | `state.profileId` already fully determines the rules and is already carried in `match.started` (`GameRoom.ts:522`). No core change, no seed/event change, no verify change. |
| **adaptive-duration override delivery** | **OUT** → own story + ADR | `computeAdaptiveDuration` (`core/src/adaptiveDuration.ts:104`) has **no caller today**. Wiring it produces a profile that is *not in the registry*, so `profileId` stops determining the rules and the override must enter the genesis event — a seed/event-contract change. That is a separate story with an ADR, per [[adaptive-profile-override-delivery-seam]]. |
| map preview | **OUT** → own story | Pure presentation; needs the board generator on the client pre-join. |
| localized `turnDeadline` / `warningCode` countdown | **OUT** → own story | In-match HUD, not lobby. |

## 🔴 Security requirement (the reason this story is not trivial)

`PROFILE_REGISTRY` (`ruleProfile.ts:725`) is keyed by **`string`**, not `RuleProfileId`, and
holds the four shipping presets **plus six measurement-only profiles**
(`EXPERIMENTAL_PROFILE_IDS`, `ruleProfile.ts:749` — `robinHoodTest`, `hiddenVpTest`,
`finalRoundTest`, …). `loadRuleProfile` resolves them all. `GameRoom.ts:356` reads
`options?.profileId` and trusts it at the TypeScript type level only — **there is no runtime
check**. Harmless today solely because the client sends no room options.

The moment this story lets the client choose, a hand-rolled client can request
`hiddenVpTest` and play by different rules, or send an unknown id and take the room down
(`loadRuleProfile` throws). The authoritative server never trusts client input.

**Therefore:** the wire-supplied `profileId` MUST be validated at runtime against an explicit
allow-list of the four shipping ids, before it reaches `loadRuleProfile`. An experimental id
arriving over the wire is rejected exactly as an unknown one is.

## Acceptance criteria

Each is a **forcing** criterion — it fails if the capability is scaffolding
(per [[spec-goal-must-match-acceptance-criteria]]).

1. **Preset reaches the match.** An E2E test joins with `profileId: 'blitz'` and asserts the
   resulting `match.started` event and `gameState.profileId` are `'blitz'`, and that a
   blitz-specific rule is actually in force (e.g. its `victory.vpToWin`), not merely that the
   string was echoed.
2. **An experimental profile id is rejected over the wire.** A join carrying
   `profileId: EXPERIMENTAL_PROFILE_IDS.hiddenVp` is refused; the room does not start and does
   not crash. Same for an unknown string (`'nonsense'`). This test must fail if the allow-list
   is removed.
3. **Default is unchanged.** A join with no `profileId` still yields `'classic'` — the M1
   client and every existing server test keep passing untouched.
4. **Bot fill is selectable.** Choosing N bots seats N bot players; the match starts with
   `4 - N`… humans as configured. Reuses the existing `bots:[{difficulty}]` option
   (`GameRoom.ts:417`) — no new bot machinery.
5. **The human is seated first.** Discharges the S2.4.3 lead-review nit: bots are minted at
   genesis and the human joins after, so today the human never takes the first snake-draft
   placement. Assert `seatIndex === 0` for the human in a 1-human + 3-bot room.
6. **Grace floor.** `reconnectGraceSeconds` is clamped to `Math.max(120, …)` when it arrives
   from outside, with a test passing `60` and asserting `120`. Discharges the S2.3.1 nit — the
   ≥120s no-karmic-ban window is a product law (`CLAUDE.md`), not a default.
7. **Trilingual.** Every new key exists in `ru.ts`, `uk.ts`, `en.ts`. A missing one fails the
   build (existing S1.6.6 guard) — add a test only if the guard does not already cover the new
   keys.
8. **Determinism untouched.** `packages/core` is not modified except, if strictly needed, an
   **additive re-export** in `core/src/index.ts` so the client can enumerate the shipping
   preset ids without importing internals. No engine logic, no event shape, no seed. Classic
   stays byte-frozen: the core determinism suite passes unchanged (334 tests).

## Design constraints

- `PRODUCT.md` + `DESIGN.md` are **binding** (OKLCH tokens, typography, zoning, a11y).
  Reference mockup: `docs/design/mockups/game-table.html`. Deviations need owner sign-off.
- Resources/modes must be distinguishable by **more than colour** (a11y law).
- Each preset needs a one-line, human-readable description of what it changes — authored in
  all three locales at creation (lore-primer glossary pattern).

## Implementation notes (verified by recon, 2026-07-10)

- **Client has no lobby/menu screen at all today.** React screens live in
  `packages/client/src/hud/` (`GameScreen.tsx`, `TopBar.tsx`, …); the Pixi canvas is in
  `packages/client/src/board/`. Add `packages/client/src/lobby/` and keep it out of the canvas.
- **Connect path:** `wsClient.ts:271 connect()` → resume-first via `client.reconnect(token)`
  (`:292`, S2.3.2a) → falls through to `joinOrCreate(GAME_ROOM_NAME, {...})` (`:311`).
  The lobby's selections must ride that `joinOrCreate` options object. **Do not break the
  resume-first branch:** a reload with a live reconnect pointer must still resume the existing
  match and must NOT re-apply lobby selections.
- **Protocol:** `ConnectOptionsSchema` (`protocol/src/messages.ts:628`) already validates
  `{protocolVersion, guestId?, displayName?}`. Extend it (or add a sibling schema) with the
  optional `profileId` + bot selection, and **use the zod parse result server-side** — that is
  where criterion 2 is enforced. Colyseus passes options to `onCreate` opaquely; zod is the
  only gate.
- **Ready-up / start gate:** the match auto-starts the instant seats fill
  (`#maybeAutoStart`, `GameRoom.ts:479`), and bots count toward the cap — so a 1-human +
  3-bot room starts immediately. That is acceptable for this story. A real ready-up gate
  belongs to **S2.5.3 private rooms** (multi-human). If a gate is added, it is **transport-only**
  (a Colyseus `this.state` field): no `GameState` mutation, no event, no seed impact.
- **Zustand:** `hud/store.ts` (`UiStore`) holds in-match state. Lobby selections exist
  *before* a room; keep them in a separate slice, not smuggled into `gameState`.
- **i18n:** add keys to `packages/client/src/i18n/keys.ts` (`TRANSLATION_KEYS`), then to
  `locales/{ru,uk,en}.ts`. Accessor `translate(...)` (`i18n/translate.ts:25`) / `useTranslation()`.

## Out of scope (do not touch)

Matchmaking, Redis, presence, private rooms/codes (S2.5.1–S2.5.3). Any change to
`reduce`/`validate`, event shapes, the seed, or `verify`. Bot difficulty tuning. The S2.4.4 nit
(`bankTradeToward` discounts only trades already affordable at the natural rate).

## Implementation notes (2026-07-10)

Verify chain green: build/lint/typecheck clean on all 5 packages; tests — core
**334** (unchanged), protocol **34** (unchanged), bots **82** (unchanged), server
**129** (120+9), client **175** (163+12).

- **Security gate lives in `GameRoom.onAuth`, not `onCreate`.** Read `@colyseus/core`
  0.17.10's `MatchMaker.ts` source directly: `joinOrCreate` awaits `callOnAuth`
  BEFORE `createRoom`→`onCreate`, using the SAME `clientOptions` object for both.
  A throw in `onAuth` aborts the join before `onCreate` (and thus `loadRuleProfile`)
  ever runs — no separate onCreate-side check needed for `profileId`/`bots`.
  `@colyseus/testing`'s `createRoom()` calls the LOW-LEVEL `matchMaker.createRoom`,
  which bypasses `onAuth` entirely — this is what keeps every existing
  `GameRoomOptions`-based test (fast fractional-second `reconnectGraceSeconds`,
  experimental profile-free bot rosters) byte-unaffected by the new gate.
- **`JoinLobbySelectionSchema` is a SIBLING of `ConnectOptionsSchema`, not a merge.**
  A bad `profileId`/`bots` is reported as a distinct rejection (code 4002,
  plain string message), never misreported as `PROTOCOL_VERSION_MISMATCH`
  (4001) — the client's existing `parseJoinError` already degrades anything
  that isn't a valid `error.version` JSON payload to a generic `error` status,
  so no client-side change was needed for that to work correctly.
- **`reconnectGraceSeconds` floor is enforced by mutating the raw `options`
  object inside `onAuth`**, in place, before `onCreate` reads it — the only
  seam available given `onAuth`/`onCreate` are independent calls sharing one
  object reference (verified against the framework source, not assumed).
  Proven directly: `packages/server/src/room/lobbySelection.e2e.test.ts` calls
  `room.onAuth(...)` on a `GameRoom` minted via `testServer.createRoom` and
  asserts the passed-in object's `reconnectGraceSeconds` flips 60→120.
- **Human-seated-first (criterion 5) required an `onJoin` reorder, not an
  `onCreate` reorder.** An existing test (`botFill.e2e.test.ts`) asserts bot
  seats exist IMMEDIATELY after `onCreate`, before any join — so bots stayed
  minted at genesis exactly as before. Instead, `onJoin` now unshifts the
  FIRST human to the front (renumbering existing bot `seatIndex`es) only when
  every seat minted so far is a bot; a no-bots room or any later join is
  unaffected. Verified against every existing `bots:[...]` test in the server
  suite — none inspect seat array order after a human joins.
- **Criterion 2's forcing property was verified by literally breaking it**:
  weakened `JoinLobbySelectionSchema.profileId` to `z.string()`, rebuilt
  protocol, re-ran `lobbySelection.e2e.test.ts` — the two rejection tests (and
  a third, downstream test that picked up a leaked experimental-profile room)
  failed exactly as expected. Reverted before finishing.
- **`SHIPPING_PROFILE_IDS`** (additive re-export, `core/src/ruleProfile.ts` +
  `index.ts`) is a plain `readonly RuleProfileId[]`, consumed by the CLIENT
  lobby (`LobbyScreen.tsx`) to enumerate presets. The protocol's own allow-list
  (`ShippingProfileIdSchema` in `messages.ts`) is a SEPARATE local zod literal
  — `z.enum` needs a `[string, ...string[]]` tuple, not the core export's
  array type, and `messages.ts` already had a hardcoded copy of the same 4
  ids at `MatchStartedEventSchema` (now refactored to share the one constant).
- **`App.tsx` (new, top-level) + `lobby/lobbyStore.ts`** (a separate zustand
  slice from `hud/store.ts`) gate the screen: `main.tsx` synchronously checks
  `readCurrentRoomId()`/`readReconnectionToken()` BEFORE the first render and,
  if resumable, flips `lobbyStore.started` before mounting — so a resuming
  reload never flashes the lobby screen and never constructs a lobby
  selection at all (the resume branch of `connect()` structurally never reads
  the `lobby` parameter).
- **Deviation:** added a `reconnectGraceSeconds` field to the wire schema even
  though this story's own UI never exposes a grace control (out of scope per
  the plan). Criterion 6 requires the floor to be provably testable "from
  outside," which needs SOME wire-reachable field; the doc comment on
  `GameRoomOptions.reconnectGraceSeconds` already anticipated exactly this
  ("a future lobby (E2.5) can override it per match" — this IS that lobby).
  No lobby UI control was added for it, matching the out-of-scope list.
- **Found, not fixed (reported, not solved unilaterally):** `onCreate` trusts
  several OTHER `GameRoomOptions` fields (`seed`, `maxSeats`, `botActionCap`,
  `botFillDifficulty`) directly off the client-supplied `joinOrCreate` options
  object, with zero runtime validation — same class of gap as the profileId
  issue this story fixes, but wider (e.g. a malicious client could in
  principle supply its own `seed`, undermining commit-reveal fairness). Not
  in this story's named scope (which calls out `profileId` specifically) and
  not touched; flagging for a follow-up story/ADR.
