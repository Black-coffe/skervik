# S2.4.3 — Single-player + bot-fill integration (wire the v1 bot into the authoritative `#queue`)

## Goal

Last story of E2.4. The v1 bot (`createHeuristicBot({difficulty})`) exists and provably terminates a full
match in-process (S2.4.2 harness). This story gives it a **real authoritative home**: the server creates
**bot seats** and drives each bot's turn **through the same `#queue` / `#applyAuthoritativeIntent` pipeline a
human client goes through** — `validate → persist → commit → broadcast`. The deliverable is **single-player**:
a room a lone human shares with N bots that plays a full deterministic Classic match to `game.ended`.

**What a bot seat IS (locked by the invariants):** a `SeatSchema` whose `playerId` is a server-minted bot id
(e.g. `'bot-0'`) with **no `sessionId` / no live `Client`**. When it becomes that seat's turn (or a
sub-phase where that seat must act — discard-on-7, robber move, setup placement), the room asks the bot
`bot.decide(state, playerId)` and injects the returned `PlayerIntent` into the `#queue` **exactly like the
S2.1.4 forced action does** (`#applyAuthoritativeIntent(playerId, intent)` with `client === undefined`). The
bot is "a client's brain without a socket" — it holds NO authority, never sees the seed, and its events are
indistinguishable in the log from a human's.

**Scope of THIS story = bot seats + the drive loop + single-player, server-side.** NO disconnect bot-fill /
reconnect handback (that is E2.3 — it needs reconnect tokens + grace that don't exist yet); NO lobby UI /
matchmaking selection (E2.5); NO core / engine-contract change; NO new randomness in the event log.

## What to build (all in `packages/server`, + tests)

### 1. A bot-seat type (distinguish a bot seat from a human seat)
Extend `SeatSchema` (`packages/server/src/schema/RoomSchema.ts:19-46`) with a minimal, ADDITIVE marker so the
room (and later the client/UI) can tell bot seats from human seats:
- Add `isBot: boolean` (default `false`) — set `true` for bot seats.
- Add `botDifficulty?: string` (present only on bot seats) — the STRUCTURED difficulty code
  (`'easy' | 'medium' | 'hard'`) the UI localizes into a display name (ADR-0008 — never a localized bot name
  in the schema). Do NOT put a human-readable/localized label in core/protocol/schema.
Keep it a Colyseus-schema-compatible additive change (schema4, [[colyseus-version-alignment]]) — optional
fields the client can ignore. A human seat stays exactly as today (`isBot:false`, no difficulty). Confirm the
existing seat projection (the broadcast of `state.seats`) still serializes byte-safe.

### 2. Room options + bot-seat creation at genesis (NOT via onJoin)
`onJoin` requires a live `Client` (`GameRoom.ts:471`) → bot seats CANNOT be created there. Create them at room
setup instead:
- Extend `GameRoomOptions` (`GameRoom.ts:83-132`) with a bot spec — prefer the explicit form
  `bots?: Array<{ difficulty: 'easy' | 'medium' | 'hard' }>` (each entry = one bot seat). (A `botCount +
  botDifficulty` shorthand is acceptable if simpler, but the explicit array lets a room mix difficulties and
  is what a future lobby maps onto — Key decision 2.)
- In `onCreate` (or wherever seats are assembled before match start), for each requested bot: mint a unique
  `playerId` (`'bot-0'`, `'bot-1'`, … — stable, deterministic, `isBot:true`, `botDifficulty` set), push a
  `SeatSchema` to `state.seats`, and store the bot instance in a new private `#bots: Map<PlayerId, Bot>` via
  `createHeuristicBot({ difficulty })`. Import `createHeuristicBot` from `@skervik/bots` (dep already present,
  `package.json:18`).
- **Bot seed (match-seed-blind + reproducible):** give each bot a STABLE, deterministic own-noise seed that is
  NOT derived from the match seed — e.g. `createHeuristicBot({ difficulty, seed: \`bot-\${seatIndex}\` })` — so a
  single-player match is reproducible from the same room options WITHOUT ever coupling the bot to the secret
  match seed. (The bot's RNG never enters the event log — the events it causes are logged, not its dice — so
  this is a reproducibility nicety, not a determinism requirement. Do NOT feed the match seed to the bot.)

### 3. Single-player start condition
A room with 1 human + N bot seats must START the match deterministically (bots fill the remaining seats at
genesis). Confirm the current match-start trigger (seats filled to `maxSeats` / an explicit start) and make it
fire when human + bot seats fill the room — reuse the existing `#startMatch` path (`GameRoom.ts:347` builds
`playerIds` from `state.seats`), so bot seats naturally take part from the genesis `match.started`. Do NOT
invent a second start path; single-player is "the room is full once the bots are seated."

### 4. The drive loop — bots act PROACTIVELY through the existing `#queue` (the heart of the story)
Add a single method — `#scheduleBotTurnIfNeeded()` (name at worker's discretion) — that inspects the CURRENT
`this.gameState` and, if a bot seat must act, **enqueues** that bot's decision onto `this.#queue` (never a
floating async callback — [[server-intent-pipeline-serialization]]). "Must act" =:
- `currentPlayerId` is a bot seat AND `phase` is an active main/roll/build/setup/robber-move phase, OR
- `phase` is the discard sub-phase and a bot seat is in `state.playersToDiscard`.
For that seat, call `intent = this.#bots.get(playerId)?.decide(this.gameState, playerId)` and fold it through
the EXISTING tail `#applyAuthoritativeIntent(playerId, intent)` with `client === undefined` (the same
forced-injection signal S2.1.4 uses). Call `#scheduleBotTurnIfNeeded()` from **two** trigger points:
- at the END of the `#applyAuthoritativeIntent` commit tail (after re-arm), so after ANY commit — human or bot
  — the room re-checks whether a bot should now move (this is what lets a bot play its whole turn: roll →
  build → … → endTurn, one enqueued step at a time, and what lets a human's commit hand off to a bot's turn);
- once after `#startMatch` (so a bot placing FIRST in setup, or acting first, gets driven).

**Re-entrancy is through the queue, not the stack:** each bot step is a fresh `#queue` link; applying it
re-triggers the check, which enqueues the next step. This naturally terminates when `currentPlayerId` becomes
a human seat, the phase becomes `'finished'`, or no bot must act.

### 5. No-hang / termination discipline (bind [[turn-timer-forced-action-hang-risk]])
A bot turn MUST make legal progress or fail loud — never spin, never hang the room:
- If `bot.decide` returns `null` (or an intent that `validate` REJECTS), **fall back to the existing
  `resolveForcedAction(this.gameState)`** (the S2.1.4 default — `endTurn` / default discard / default robber),
  applied through the same tail. The bot never leaves the turn stuck; the forced-action safety net already
  exists and is legal by construction (S2.2.1 aligned it with `validate`).
- Add a **per-turn bot-action cap** (small constant — mirror the harness `maxTurns` discipline) so a bot that
  somehow can't end its turn forces `endTurn` and, if even that fails, the room surfaces a loud error rather
  than looping. Reuse `state.consecutiveMisses` / the generation guard where natural; do NOT invent a parallel
  timer system.
- The **turn timer path stays UNTOUCHED**: arming a hard-timeout for a bot seat is a harmless no-op because
  the proactive drive acts first and bumps the generation (the stale timeout becomes a no-op via the existing
  guard, `GameRoom.ts:804`). Do NOT special-case the timer for bots unless leaving it armed causes a real
  double-action (it should not — verify with a test). Prefer the SMALLEST change.

### 6. Determinism / replay (bind the core invariant — but core is UNTOUCHED)
Bot-driven events are ORDINARY events (`turn.ended`, `dice.rolled`, `settlement.placed`, …) with NO timestamp
and NO bot marker in the log — so `replay(events)` from genesis reproduces `finalState` byte-identically,
exactly as for a human match. The determinism boundary is unchanged: the bot's noise `BotRng` lives server-
side only, never enters the log. Verify a single-player match's persisted `events` replay-fold deep-equals its
`finalState` (the event-sourcing gate).

## Key decisions (surface any deviation)

1. **Bots act PROACTIVELY on their turn, not only via the timeout.** The S2.1.4 forced-action seam is the
   INJECTION MECHANISM (a server-authored intent through the `#queue`, `client===undefined`), but the TRIGGER
   for a bot is "it is the bot's turn now" — checked after every commit + after start — not "the turn timer
   expired." Driving a bot only on timeout would make every bot move wait the full timer (unplayable). The
   forced-timeout path remains as the safety net for a bot that returns null/illegal. **Tradeoff:** proactive
   driving is the only sane single-player UX and reuses the exact same authoritative tail; it adds a re-check
   at the commit tail (one method call), no new concurrency primitive.
2. **Explicit `bots: Array<{difficulty}>` room option (not a global toggle).** Lets a room mix difficulties and
   is what a future lobby (S2.5.4) maps a UI selection onto. Single-player = 1 human + this array filling the
   rest. **Rejected:** a boolean `singlePlayer` flag — too rigid; bot-fill (E2.3) and mixed lobbies need
   per-seat difficulty anyway.
3. **`isBot` + `botDifficulty` on `SeatSchema` (additive, structured).** A convention like
   `playerId.startsWith('bot-')` is fragile (parsing identity) and leaks a naming rule into every consumer; an
   explicit flag is unambiguous and gives the client a clean signal. `botDifficulty` is a STRUCTURED code
   (ADR-0008) — the UI localizes it; no localized string in the schema.
4. **Bot seed is match-seed-blind + deterministic-per-seat** (`\`bot-\${seatIndex}\``). Keeps the bot's noise
   reproducible for a single-player replay WITHOUT coupling it to the secret match seed (the authoritative-
   server + commit-reveal invariant: a bot must be unable to predict future rolls). The bot's RNG never enters
   the log; only the events it causes do.
5. **Reuse the forced-action fallback for termination.** A bot that returns null/illegal falls back to
   `resolveForcedAction` (the existing legal default) + a per-turn cap → the turn always ends legally; a truly
   stuck bot fails loud (mirrors the harness `maxTurns` discipline, [[e2e-scripted-driver-expansion]]). No new
   watchdog — reuse S2.1.4's generation guard + re-arm.
6. **Core + verify + contract UNTOUCHED; determinism intact.** No `packages/core` diff, no `verify.ts` diff, no
   engine-signature change, no new event type (bots emit the existing events). Replay stays byte-identical
   because bot events carry no timestamp/marker. The ONLY schema change is the two additive `SeatSchema` fields.
